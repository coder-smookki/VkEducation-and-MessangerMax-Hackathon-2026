# Поведение дизайн-прототипа

Актуальная спецификация переходов, серверных данных, отказов и задач - [docs/screens.md](../docs/screens.md). Полные правила интерфейса - [docs/design.md](../docs/design.md), предметные переходы - [docs/domain.md](../docs/domain.md).

Автор: A01/A02 → A03 → уточнение A04 при необходимости → review A05/A06 либо manual A07 → A08/A09 → приём A10 → отчёт A11 → наблюдение A12 → частичный итог A13, детали A14, история A15. Поздний успех A16, отзыв A17/A18 и архив D09/D10 - отдельные альтернативы, а не одна timeline.

Диспетчер: D01/D02 → приём D03 → следующий шаг D04 → сохранение отчёта D05 → проверка/выбор D06 → отдельное подтверждение D07 → D08. Архив D09 относится к выбранному пункту о двери; D10 сохраняет неподтверждённый остаток и прошлый план. Отчёт, link, observation и admin независимы.

Бот B01..B04 вызывает те же серверные команды. Прототип только иллюстрирует сообщения, не подтверждает MAX API. Display №124 не ID; реальное открытие использует разрешённый UUID через startapp и серверную авторизацию.

X01..X10 охватывают ввод/409/unknown outcome/ML fallback/ошибку чтения/пустоту/клавиатуру/pending/наблюдения/invite. R01..R04 проверяют представление тех же данных на других размерах. C01..C06 показывают reusable-компоненты. S01/S02 - необязательный поиск, никаких автоматических слияний.

Локальный prototype storage/выбор экранов не переносится в приложение как авторизация. Для theme/text предпочтений допустимо безопасное локальное хранение; реальные тексты и права остаются серверными. Фактическая реализация и результаты тестов находятся в docs/memory/PROJECT_STATE.md, а не выводятся из кликабельности HTML.
