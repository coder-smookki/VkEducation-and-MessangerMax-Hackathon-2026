# Сквозной пример для трёх разработчиков

Это **спецификация будущего рабочего API на синтетических данных**, не журнал выполненных запросов. Кирилл строит по ней UI, Семён - команды/проверки, Никита - сравнение текста. Текущий `/api/v1/demo/case` показывает только фиксированную часть истории и не исполняет эти шаги.

## Участники и исходные данные

Тестовые акторы: A - автор с Membership дома H1; B - другой житель H1; C - житель H2; D - диспетчер H1; E - исполнитель H1. Вход каждого проверен сервером. Контекст A в JSON-команду не передаётся.

Для согласования используются IDs текущего учебного примера: case `00000000-0000-0000-0000-000000000001`, автор `...0002`, report `...0003`, свет `...0004`, дверь `...0005`. В настоящем API IDs выдаёт Java; тесты берут их из response, а не ожидают фиксированные UUID на сервере. Сокращённые IDs ниже - обозначения, не допустимые UUID в запросе.

Исходный текст: «На третьем этаже темно, и входная дверь не закрывается». Пункт света: LIGHTING, «Подъезд 1, этаж 3», «Не горит свет». Пункт двери: ENTRANCE_DOOR, «Подъезд 1, вход», «Дверь не закрывается».

## Ожидаемая история

В этой таблице нет параллельных команд. Числа показывают выбранную политику версий: caseVersion меняется каждой командой; itemVersion - при изменении/подтверждении конкретного пункта. Реальный клиент всегда использует версии из ответа.

| Шаг | Актор и команда | Case version | Item versions свет/дверь | Раунды свет/дверь | Результат |
|---|---|---:|---|---|---|
| 1 | A создаёт draft | 1 | Пунктов ещё нет | Нет | DRAFT сохранён без Python |
| 2 | A сохраняет два пункта | 2 | 1 / 1 | 0 / 0 | Оба NOT_ASSIGNED, NOT_RECEIVED, ACTIVE |
| 3 | A подтверждает список | 3 | 2 / 2 | 0 / 0 | CONFIRMED, содержание зафиксировано |
| 4 | D сохраняет report про лампу | 4 | 2 / 2 | 0 / 0 | Рабочие факты обоих пунктов прежние |
| 5 | D подтверждает link только света | 5 | 3 / 2 | 1 / 0 | Свет REPORTED_DONE, дверь NOT_ASSIGNED |
| 6 | A отвечает RESTORED после отчёта света | 6 | 4 / 2 | 1 / 0 | Подтверждён только свет |
| 7 | A добровольно сообщает PERSISTS по двери | 7 | 4 / 3 | 1 / 0 | Дверь не подтверждена; фиктивного отчёта нет |
| 8 | A отзывает пункт двери с причиной | 8 | 4 / 4 | 1 / 0 | Дверь WITHDRAWN, не считается выполненной |
| 9 | D сохраняет новый report о свете | 9 | 4 / 4 | 1 / 0 | Сам текст не меняет наблюдение |
| 10 | D подтверждает новый link света | 10 | 5 / 4 | 2 / 0 | Старое RESTORED в истории, актуальное NOT_RECEIVED |

SourceRevision и contentVersion здесь равны 1: содержание не правилось. При изменении draft-текста до шага 3 выросла бы sourceRevision; при изменении symptom/location/category - contentVersion соответствующего пункта. После шага 3 попытка заменить список в обязательном MVP отклоняется.

## Запросы для подготовки фикстур

У всех изменяющих запросов текущая session cookie, CSRF header и Idempotency-Key. JSON ниже соответствует целевому [api.md](api.md). Host/секреты в примерах отсутствуют.

Шаг 1, POST `/api/v1/cases`; H1 в этой фикстуре имеет тестовый UUID:

```json
{
  "houseId": "00000000-0000-0000-0000-000000000010",
  "sourceText": "На третьем этаже темно, и входная дверь не закрывается."
}
```

Шаг 2, PATCH `/api/v1/cases/{caseId}/items`:

```json
{
  "expectedCaseVersion": 1,
  "items": [
    {"category": "LIGHTING", "location": "Подъезд 1, этаж 3", "symptom": "Не горит свет"},
    {"category": "ENTRANCE_DOOR", "location": "Подъезд 1, вход", "symptom": "Дверь не закрывается"}
  ]
}
```

Шаг 3, POST `/api/v1/cases/{caseId}/confirm`:

```json
{"expectedCaseVersion": 2, "sourceRevision": 1}
```

Шаг 4, POST `/api/v1/cases/{caseId}/reports`. Диспетчер обозначает допустимую область разбора; это ещё не links:

```json
{
  "expectedCaseVersion": 3,
  "reportText": "Лампу на третьем этаже заменили, освещение работает.",
  "targetItemIds": [
    "00000000-0000-0000-0000-000000000004",
    "00000000-0000-0000-0000-000000000005"
  ]
}
```

Шаг 5, POST `/api/v1/reports/{reportId}/links`, отдельное действие D:

```json
{
  "expectedCaseVersion": 4,
  "links": [{
    "itemId": "00000000-0000-0000-0000-000000000004",
    "contentVersion": 1,
    "expectedWorkRound": 0,
    "workStatus": "REPORTED_DONE"
  }]
}
```

Шаг 6, POST `/api/v1/items/{lightId}/observations`:

```json
{
  "expectedCaseVersion": 5,
  "expectedItemVersion": 3,
  "contentVersion": 1,
  "workRound": 1,
  "value": "RESTORED",
  "source": "AFTER_REPORT"
}
```

Шаг 7 для двери использует expectedCaseVersion=6, expectedItemVersion=2, contentVersion=1, workRound=0, value=PERSISTS, source=INDEPENDENT. Шаг 8 - administrative-decisions с версиями 7/3, action=WITHDRAW и причиной «Пункт был добавлен ошибочно». Это не доказывает ремонт двери.

## Что показывает UI

После шага 5: у света «Исполнитель сообщил о выполнении», наблюдения нет. У двери «Нет сведений о работах», наблюдения нет. Нельзя написать, что обращение выполнено.

После шага 6 сервер возвращает такой progress:

```json
{"total": 2, "confirmed": 1, "withdrawn": 0, "remaining": 1, "allConfirmed": false}
```

После шага 8:

```json
{"total": 2, "confirmed": 1, "withdrawn": 1, "remaining": 0, "allConfirmed": false}
```

После шага 10:

```json
{"total": 2, "confirmed": 0, "withdrawn": 1, "remaining": 1, "allConfirmed": false}
```

История сохраняет положительное наблюдение первого раунда, но карточка не использует его как подтверждение второго. Архивирование вместо отзыва тоже не создаёт положительное наблюдение.

## Где работает ML

После шага 4 Java может сохранить analysis job и немедленно вернуть report. Python получает snapshot, возвращает предложение по каждому переданному item. До шага 5 раунд света в snapshot равен 0; существующий `contracts/examples/compare-request.json` взят из более позднего состояния и содержит раунд света 1. Нельзя использовать этот fixture без изменения раунда для теста шага 4.

STUB возвращает отказ по обоим пунктам. NLI в удачном проверенном случае предлагает REPORTED_DONE для света с точным фрагментом; для двери сведений нет. В обоих случаях D сам выбирает связь. Если D успел выполнить шаг 5 до ответа модели, snapshot с раундом 0 устарел: предложение не применяется к новому раунду.

## Обязательные ответвления

- B, C или D пытается наблюдать вместо A - запрет; D может только выполнять свои диспетчерские действия.
- Две вкладки сохраняют список с одной caseVersion - один успех, другой 409; текст проигравшей вкладки не теряется.
- Повтор уже выполненного шага 6 с прежним key/body возвращает прежний результат после проверки доступа, без нового события, даже если появился следующий раунд.
- Ранее не применённый callback первого раунда после шага 10 отклоняется как устаревший; отправка с новым key не обходит версии.
- Тот же key, но value=PERSISTS вместо прежнего RESTORED - 409; новое добровольное наблюдение требует новой команды и актуальных версий.
- Python остановлен на шаге 4 - отчёт и оба пункта сохранены, ручной шаг 5 доступен.
- Процесс упал после commit шага 5, но до отправки MAX - outbox остаётся для восстановления, не создаётся второй раунд.

Доказательства этих сценариев фиксируются по [acceptance.md](acceptance.md), а не отметкой «экран нарисован».
