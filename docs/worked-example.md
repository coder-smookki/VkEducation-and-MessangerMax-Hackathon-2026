# Сквозной пример: свет и дверь

Синтетические роли: автор Анна (RESIDENT дома H1), диспетчер Марина (DISPATCHER H1). Не реальные люди/доступы. Обращение C содержит свет L и дверь D. Номер №124 здесь только подпись примера; в продукте Java выдаёт displayNumber, а API адресует обращение UUID. Это объяснение данных, а не seed публичной БД. Авторский/диспетчерский HTTP-путь реализован и проверяется frontend/tests/integration.spec.ts; полный G2 с двумя настоящими MAX-аккаунтами ещё требует отдельной приёмки.

|---|---|---|
| 1 | Автор вводит общий текст | DRAFT, исходник сохранён Java; caseVersion выдаёт сервер |

## Версии и альтернативы

Каждая команда использует **версию из последнего ответа**, а не произвольно выдуманное следующее число. CaseVersion повышается и при приёме/шаге/отчёте; itemVersion относится к конкретному пункту; sourceRevision - к исходному тексту, contentVersion - к содержанию пункта. Round повышает только новая подтверждённая связь. UI не инкрементирует эти значения сам.

Python не вызывается формой шага 2. Анализ сохранённого отчёта после шага 7 необязателен; его отказ не запрещает ручной выбор связей. Отсутствие сведений о D сохраняется; модель не получает права закрыть дверь.

Поздний отчёт по D и положительное авторское наблюдение могут дать 2 из 2. Это отдельная ветка A16. Если вместо этого автор отзывает D с причиной, остаётся total=2, confirmed=1, withdrawn=1, remaining=0, allConfirmed=false (A18). Если диспетчер архивирует D, total=2, confirmed=1, withdrawn=0, remaining=1; архивный остаток не ремонт (D10). Не соединять альтернативные макеты в одну выдуманную timeline.

Новый отчёт по L после шага 9 открывает новый round только после link: старое RESTORED остаётся в истории, текущая проверка снова NOT_RECEIVED. Callback прежнего round не меняет новый. Из двух одновременных конфликтующих команд с одной expectedCaseVersion проходит одна. Повтор той же команды с тем же key возвращает результат без нового события после проверки текущих прав.
