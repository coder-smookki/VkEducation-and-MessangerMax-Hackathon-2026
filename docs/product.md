# Продукт и границы MVP

Основание: отчёт КОРЕНЬ 2.0 от 06.09.2026, стр. 2, 5-21, 23. Концепция принята как основа каркаса по запросу Кирилла 12.09.2026. Закрытое ТЗ хакатона в эту работу не передавалось.

## Проблема

В одном обращении бывает несколько проблем. Общий статус «закрыто» скрывает, на какие именно пункты есть ответ и что наблюдает житель. Проверяем гипотезу: диспетчеру проще сверять ответ с исходным списком, а автору не приходится повторять потерянную часть.

## Целевой путь

1. Автор начинает диалог в MAX, открывает Mini App, указывает текст и место. Java сохраняет исходный черновик до анализа.
2. Система предлагает отдельные пункты; автор исправляет или подтверждает список. Если не хватает места/симптома, уточнение адресовано только ему. В текущей заготовке извлечение - STUB, ручной ввод сохраняется, проверка недостающих полей работает по правилам. [Контракты 01-03](../contracts/README.md).
3. Диспетчер принимает обращение и назначает работу по пунктам.
4. Исполнитель или диспетчер вводит отчёт. ML предлагает связи с точными фрагментами; диспетчер подтверждает их.
5. Только автор видит необязательную проверку по пунктам, где есть отчёт о выполнении: «Восстановилось», «Сохраняется», «Не могу проверить».
6. Непроверенные и неописанные пункты остаются видны. Архив, отзыв и положительное наблюдение отображаются раздельно.

Автор может независимо сообщить о восстановлении до каких-либо работ. Это наблюдение не приписывается исполнителю.

По поручению от 13.09.2026 добавлена основа сравнения одинаковых/похожих обращений: Java передаёт Python подтверждённый query и допустимых кандидатов, Python возвращает STUB без выдуманного score. [Контракт 04](../contracts/04-similar-cases.md). Модели, векторизация и автоматическое объединение не входят в эту подготовку. Сходство части пунктов не позволяет удалить остальные.

## Приёмочный пример

Исходный текст: «На третьем этаже темно, и входная дверь не закрывается».
Отчёт: «Лампу на третьем этаже заменили, освещение работает».

Ожидается два пункта. По свету есть заявление исполнителя; наблюдение автора пока неизвестно. По двери сведений нет. После подтверждения света результат частичный. Даже при отзыве двери нельзя написать «2 из 2 выполнено».

## Обязательный объём

Текст и подтверждаемые пункты; место; роли в одном или нескольких тестовых домах; отчёты и ручные связи; добровольные наблюдения; история; устойчивость к повторам; ML-подсказки с доказательными фрагментами; сравнение с ручным вариантом.

Начальные категории: освещение общих зон, входная дверь, уборка. `OTHER` сохраняется и обрабатывается человеком. MVP использует текст; вложения требуют отдельной защищённой реализации и относятся к расширению.

За пределами старта: прогноз причин аварий, граф стояков, массовые опросы соседей, собственное обучение модели, голос, анализ фото, платежи, рейтинги жильцов и интеграция с реальной УК без доступов.

## Условия старта

В T0 сверить концепцию с закрытым кейсом, требования к заранее подготовленному коду, допускаемые ML/LLM, доступы MAX и формат сдачи. Сроки и пункты правил из PDF являются историческим источником, не новым юридическим заключением. Если требуется разъяснение, Кирилл получает его у организаторов; приложение не должно зависеть от генеративного LLM.

Для пилота дополнительно нужны подтверждённые роли, правила обработки и хранения данных и согласованный аварийный маршрут. Продукт не является экстренной службой. Тексты про физическую безопасность утверждает ответственный владелец процесса.
