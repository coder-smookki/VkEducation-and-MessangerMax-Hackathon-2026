# Выпуск и самостоятельная проверка

Целевой домен **https://hackathon.lumnex.ru/**. Этот документ - требования к S-07/K-07/Q-07, а не утверждение о настроенном сервере. Доступность реального домена/бота подтверждается отдельным протоколом.

## До развёртывания

1. Закрепить SHA и минимальный набор функций; Should выключен, если не прошёл приёмку.
2. Настроить DNS/TLS, static frontend, proxy `/api/v1` и отдельный `/max/webhook`. API не должен fallback в index.html. Убедиться, что main lumnex.ru не затрагивается.
3. PostgreSQL/Python/Kafka/Chroma только в private network. Секреты передать окружением/секрет-хранилищем; токен не в URL, JS, образе, source map, Git и логах.
4. Завершить проверенную сессию/CSRF/Membership, выдать тестовые роли контролируемо. Никаких userId/role overrides для облегчения демонстрации.
5. Проверить поддержку HTTPS Mini App и webhook в фактически выданном боте, права на запуск, реальное имя бота и открытие через MAX. Не восстанавливать токен из screenshot/истории в публичные файлы.
6. Заполнить реальные support/privacy контакты и правила хранения. Синтетический стенд явно подписан. Массовые уведомления и рассылка соседям отсутствуют.

## Сборка и данные

Существующий Compose - dev. Отдельный release profile создаётся и проверяется; стандартный release не должен грузить необязательные embeddings/индекс ради ручного пути. Не отключать реально заявленный ML незаметно. Lock-файлы обязательны, `npm --force`/`--legacy-peer-deps` не скрывают несовместимость зависимостей.

Чистая source-build измеряется в изолированной среде: SHA, ОС/CPU/RAM, сеть, подготовленные базовые Docker images, время полной команды вместе с зависимостями. Цель ≤5 минут из Blueprint проверяется этим способом. Не очищать общий Docker cache/volume команды ради проверки. Если цель не достигнута, записать факт и оптимизировать ненужные зависимости.

Seed запускается отдельным явным шагом и только для synthetic data. Обычный restart/upgrade не удаляет существующие обращения. V1/V2 не переписываются. До миграции непустой среды backup, после - контроль ключевых counts/связей. Restore проверяется в отдельную БД, не поверх рабочей без разрешения.

## Кандидат backend (S-08, 26.09)

Факты на дату, а не план. SHA кандидата - merge-коммит S-08 в dev; при выпуске он записывается сюда командой `git rev-parse HEAD` на стенде (S-09), и стенд, исходники и API должны быть этой одной версией. Открытых дефектов P0/P1 на 26.09 не заявлено.

### Функции и режимы

| Функция | Переключатель | По умолчанию | Для кандидата |
|---|---|---|---|
| Ручной путь: обращение, пункты, приём, план, отчёт, связи, наблюдение, архив и отзыв, история | всегда | включён | включён; основной сценарий |
| Анализ отчёта в Python | `ANALYSIS_ENABLED`, `COMPARE_ANALYZER` | выключен, stub | выключен, пока holdout Софии не измерен; при включении - `rules` |
| Текстовый бот и уведомления | `MAX_WEBHOOK_SECRET`, `MAX_WORKERS_ENABLED` | маршрута нет, воркеры стоят | выключен до HTTPS-стенда и настоящего отправителя: сейчас отправитель отказывает, сообщения копятся в очереди |
| Разбор свободной фразы на пункты | - | STUB | автор вводит пункты сам |
| Похожие обращения, Kafka и Chroma | `KAFKA_ENABLED` и профиль Compose `similar` | не запускаются | не запускаются; backend их не ждёт |
| Demo-маршруты `/api/v1/demo/**` | `SPRING_PROFILES_ACTIVE` | `demo` в Compose для разработки | `release` на стенде - demo закрыт (QA-R09) |

### Окружение

Все переменные с пояснениями - в `.env.example`; секретов в нём нет. Секреты - только `DB_PASSWORD`, `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`: окружение стенда или хранилище секретов, никогда Git, образ, лог или чат. На HTTPS-стенде дополнительно `SESSION_COOKIE_SECURE=true`; `SESSION_COOKIE_SAMESITE` по умолчанию Lax - открытие Mini App внутри MAX проверить на настоящем устройстве, прежде чем менять. `koren.http.max-body-bytes` (256 КиБ) и `koren.analysis.poll-ms` менять не требуется.

### Seed стенда

Только синтетические данные и только отдельным явным шагом:

1. `python3 scripts/seed_stand.py house "Синтетическая, 1"` - печатает id дома.
2. `python3 scripts/seed_stand.py invite <houseId> --count 2` - печатает одноразовые коды жильцов на 7 дней. В базе только SHA-256 кода; коды передаются закрытым каналом. Жилец входит в Mini App и вводит код (POST `/memberships/claim`).
3. Диспетчер один раз входит в Mini App, затем `python3 scripts/seed_stand.py dispatcher <houseId> <maxUserId>`.

Seed ничего не удаляет. Ролей в обход сервера нет: RESIDENT - только через приглашение, DISPATCHER - только этим шагом оператора.

### Резервная копия и восстановление

- Перед любой миграцией непустой базы: `python3 scripts/db_backup.py backup`, затем `verify` на этом дампе. Verify восстанавливает в отдельную базу `koren_restore_check` и сравнивает версию миграции, число строк каждой таблицы и md5 всего аудита; рабочую базу не трогает.
- Восстановление рабочей базы: `docker compose stop backend`, затем `python3 scripts/db_backup.py restore <дамп> --confirm koren`, затем `docker compose start backend` и проверка `/actuator/health`. Без остановленного backend и без `--confirm` скрипт отказывается.
- Замер 26.09 на локальной базе: дамп 1,2 МБ за 0,3 с, verify 0,3 с. На стенде восстановление рабочей базы ещё не выполнялось.
- Дампы содержат тексты обращений: `backups/` в .gitignore, в общие папки не класть.

### Инварианты, на которых держится продукт

- Пункт, отчёт, связь, наблюдение и административное решение - разные факты; ответ о свете не закрывает дверь.
- Сохранённый текст отчёта не меняет ни одного пункта; раунд открывает только связь, подтверждённая диспетчером, и только у своего пункта.
- Наблюдение относится к текущим contentVersion и workRound; ответ о прошлом раунде отклоняется, а не применяется к новому.
- Отзыв идёт в withdrawn, архив остаётся в remaining; total не меняется, allConfirmed не становится true без подтверждения автора.
- Каждая команда идемпотентна по ключу и проверяет версии; повтор сначала проверяет права.
- Недоступный объект отвечает 404, чтобы не выдавать факт его существования.
- Python только подсказывает: подсказка не создаёт связь, устаревшая не показывается, STUB не выдаётся за анализ.
- Уведомление ставится в очередь в транзакции команды, несёт только идентификаторы, и права получателя проверяются заново перед отправкой.

### Фактические ограничения

G2 не пройден: вход и бот не проверены на настоящем MAX, нужен HTTPS-стенд. Нагрузка измерена на ноутбуке (p95 20 мс при 10 сессиях), а не на стенде. Анализатор оценён только на development и regression; holdout не написан. displayName и ownerDisplayName всегда null. Исполнителя и его кабинета нет. Подробно - [PROJECT_STATE](memory/PROJECT_STATE.md).
