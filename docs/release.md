# Выпуск и самостоятельная проверка

## Подготовленная release-конфигурация

`compose.release.yaml` - самостоятельный файл. Его нельзя объединять с `compose.yaml`: последний включает demo. По умолчанию поднимаются PostgreSQL, Java и собранный React в nginx. Web доступен только на loopback: `WEB_PORT`, по умолчанию `8090`; DB и Python не публикуют порты. Необязательный Python: `--profile analysis` одновременно с `ANALYSIS_ENABLED=true`; RULES включается внутри этого профиля, Kafka отсутствует. Отправитель MAX реализован. `MAX_WORKERS_ENABLED=false` безопасен для локальных проверок; на сервере включить после проверки токена, секрета webhook и получателя. Реальную доставку подтвердить отдельно входящим сообщением от проверяющего. `RELEASE_SHA` обязателен и должен совпадать с исходниками, из которых собраны образы.

27.09 пользователь разрешил развёртывание. Порядок выпуска:

1. Зафиксировать SHA, проверить существующий HTTPS-прокси и занятые порты. На сервере есть другие домены: если 80/443 уже используются, добавить отдельный virtual host `hackathon.lumnex.ru` в существующий прокси с upstream `http://127.0.0.1:8090`. Не запускать второй публичный прокси поверх первого и не менять чужие сайты.
2. Сохранить `deploy/release.env.example` как приватный файл **вне Git**, задать права 600, заполнить DB_PASSWORD, MAX_BOT_TOKEN, MAX_WEBHOOK_SECRET и RELEASE_SHA (полный `git rev-parse HEAD`). Пример пути ниже `/etc/koren/release.env`; оператор выбирает доступный ему защищённый каталог. SESSION_COOKIE_SECURE=true, SITE_ADDRESS=hackathon.lumnex.ru. На проверенном сервере `8090` занят другим проектом: для КОРНЯ выбран `WEB_PORT=8091` и отдельный host nginx из `deploy/nginx.hackathon.conf`. Не использовать `.env.example` учебного Compose как production-секреты.
3. Собрать основной стек:

```sh
docker compose --env-file /etc/koren/release.env -p koren-release -f compose.release.yaml up --build -d
```

4. Если существующего прокси нет и порты свободны, использовать подготовленный Caddy с отдельным профилем:

```sh
docker compose --env-file /etc/koren/release.env -p koren-release -f compose.release.yaml --profile https up --build -d
```

Caddy обслуживает только SITE_ADDRESS и сохраняет сертификаты в volume. DNS направляет домен на сервер, а 80/443 должны быть доступны для HTTPS/выпуска сертификата. Фактический выпуск сертификата пока не проверен.

5. Проверить HTTPS, HTTP→HTTPS, `/` и assets, API 401/CSRF/ошибки JSON, закрытые demo, роль/дом и cookies на реальных MAX web/mobile. Для MAX Web обе cookies используют `SameSite=None; Secure`; с `Lax` вход в iframe завершался `CSRF_TOKEN_INVALID` (воспроизведено 27.09). Java по-прежнему требует CSRF-заголовок и подписанный initData. CSP разрешает встраивание только своему origin, `https://web.max.ru` и `https://max.ru`.
6. Создать синтетический дом и выдать приглашения/диспетчера отдельным явным seed, пройти основной сценарий двумя аккаунтами. В MAX-боте должен быть привязан ровно HTTPS URL из раздела ссылок. Sender/webhook проверяются Семёном отдельно; публикация статического сайта их не реализует.

Для существующих seed/backup скриптов, которые вызывают `docker compose` без флагов, **в том же терминале** выбрать тот же project и env:

```sh
export COMPOSE_FILE="$PWD/compose.release.yaml"
export COMPOSE_PROJECT_NAME=koren-release
export COMPOSE_ENV_FILES=/etc/koren/release.env
docker compose ps
```

Только после проверки project применять команды seed/backup ниже. Эти переменные официально поддерживаются [Docker Compose](https://docs.docker.com/compose/how-tos/environment-variables/envvars/). Не запускать скрипты с настройками другого стенда. Остановка `docker compose down` сохраняет данные; `down -v` не является процедурой обновления/отката. Перед миграцией нужна проверенная резервная копия; откат кода не отменяет миграцию автоматически.

## Сборка и данные

`compose.yaml` - учебный dev; отдельный `compose.release.yaml` уже проверен локально; стандартный release не должен грузить необязательные embeddings/индекс ради ручного пути. Не отключать реально заявленный ML незаметно. Lock-файлы обязательны, `npm --force`/`--legacy-peer-deps` не скрывают несовместимость зависимостей.

Чистая source-build измеряется в изолированной среде: SHA, ОС/CPU/RAM, сеть, подготовленные базовые Docker images, время полной команды вместе с зависимостями. Цель ≤5 минут из Blueprint проверяется этим способом. Не очищать общий Docker cache/volume команды ради проверки. Если цель не достигнута, записать факт и оптимизировать ненужные зависимости.

Seed запускается отдельным явным шагом и только для synthetic data. Обычный restart/upgrade не удаляет существующие обращения. V1/V2 не переписываются. До миграции непустой среды backup, после - контроль ключевых counts/связей. Restore проверяется в отдельную БД, не поверх рабочей без разрешения.

### Окружение

Release-переменные - в `deploy/release.env.example`; `.env.example` относится к учебному dev. Секретов в шаблонах нет. Секреты - только `DB_PASSWORD`, `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`: окружение стенда или хранилище секретов, никогда Git, образ, лог или чат. На HTTPS-стенде дополнительно `SESSION_COOKIE_SECURE=true`; `SESSION_COOKIE_SAMESITE=None` в release для iframe MAX Web; CSRF cookie наследует ту же политику. `None` с выключенным `Secure` отклоняется при старте. Локальный HTTP runner задаёт `Lax` явно. Реальный MAX mobile проверить отдельно. `koren.http.max-body-bytes` (256 КиБ) и `koren.analysis.poll-ms` менять не требуется. Несекретные настройки MAX: `MAX_API_URL` (по умолчанию `https://platform-api2.max.ru`), `MAX_BOT_NAME` (по умолчанию `t109_hakaton_max_bot`, для кнопки «Открыть обращение»). `CASE_NUMBER_PREFIX` по умолчанию пуст; синтетический стенд может подписать номера, например `ДЕМО-`.

### Seed стенда

Только синтетические данные и только отдельным явным шагом:

1. `python3 scripts/seed_stand.py house "Синтетическая, 1"` - печатает id дома.
2. `python3 scripts/seed_stand.py invite <houseId> --count 2` - печатает одноразовые коды жильцов на 7 дней. В базе только SHA-256 кода; коды передаются закрытым каналом. Жилец входит в Mini App и вводит код (POST `/memberships/claim`).
3. Диспетчер один раз входит в Mini App, затем `python3 scripts/seed_stand.py dispatcher <houseId> <maxUserId>`.

Seed ничего не удаляет. Ролей в обход сервера нет: RESIDENT - только через приглашение, DISPATCHER - только этим шагом оператора.

### Резервная копия и восстановление

- Перед любой миграцией непустой базы: `python3 scripts/db_backup.py backup`, затем `verify` на этом дампе. Verify восстанавливает в отдельную базу `koren_restore_check` и сравнивает версию миграции, число строк каждой таблицы и md5 всего аудита; рабочую базу не трогает.
- Восстановление рабочей базы: `docker compose stop backend`, затем `python3 scripts/db_backup.py restore <дамп> --confirm koren`, затем `docker compose start backend` и проверка `/actuator/health`. Без остановленного backend и без `--confirm` скрипт отказывается.
- Замер 26.09 на локальной базе: дамп 1,2 МБ за 0,3 с, verify 0,3 с. На стенде восстановление рабочей базы ещё не выполнялось.
- Дампы содержат тексты обращений: `backups/` в .gitignore, в общие папки не класть.

### Инварианты, на которых держится продукт

- Пункт, отчёт, связь, наблюдение и административное решение - разные факты; ответ о свете не закрывает дверь.
- Сохранённый текст отчёта не меняет ни одного пункта; раунд открывает только связь, подтверждённая диспетчером, и только у своего пункта.
- Наблюдение относится к текущим contentVersion и workRound; ответ о прошлом раунде отклоняется, а не применяется к новому.
- Отзыв идёт в withdrawn, архив остаётся в remaining; total не меняется, allConfirmed не становится true без подтверждения автора.
- Доменные команды обращения идемпотентны по ключу и проверяют версии; повтор сначала проверяет права. Вход/выход/погашение приглашения имеют отдельную семантику: повтор погашенного кода может получить 403, тогда сначала обновить `/me`.
- Недоступный объект отвечает 404, чтобы не выдавать факт его существования.
- Python только подсказывает: подсказка не создаёт связь, устаревшая не показывается, STUB не выдаётся за анализ.
- Уведомление ставится в очередь в транзакции команды, несёт только идентификаторы, и права получателя проверяются заново перед отправкой.

### Фактические ограничения

G2 не пройден: вход и бот не проверены на настоящем MAX, нужен HTTPS-стенд. Отправка сообщений написана и проверена на локальной подмене MAX, но ни одно сообщение настоящему боту не отправлено. Нагрузка измерена на ноутбуке (p95 20 мс при 10 сессиях), а не на стенде. Анализатор оценён только на development и regression; holdout не написан. displayName и ownerDisplayName всегда null. Исполнителя и его кабинета нет. Подробно - [PROJECT_STATE](memory/PROJECT_STATE.md).
