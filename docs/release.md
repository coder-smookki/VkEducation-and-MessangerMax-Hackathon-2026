`compose.release.yaml` - самостоятельный файл. Его нельзя объединять с `compose.yaml`: последний включает demo. По умолчанию поднимаются PostgreSQL, Java и собранный React в nginx. Необязательный Python: `--profile analysis` одновременно с `ANALYSIS_ENABLED=true`; RULES включается внутри этого профиля, Kafka отсутствует. Отправитель MAX реализован. `MAX_WORKERS_ENABLED=false` безопасен для локальных проверок; на сервере включить после проверки токена, секрета webhook и получателя. Реальную доставку подтвердить отдельно входящим сообщением от проверяющего. `RELEASE_SHA` обязателен и должен совпадать с исходниками, из которых собраны образы.

Пример пути ниже `/etc/koren/release.env`; оператор выбирает доступный ему защищённый каталог. SESSION_COOKIE_SECURE=true, SITE_ADDRESS=hackathon.lumnex.ru. export COMPOSE_ENV_FILES=/etc/koren/release.env


Только после проверки project применять команды seed/backup ниже. Эти переменные официально поддерживаются [Docker Compose](https://docs.docker.com/compose/how-tos/environment-variables/envvars/). Не запускать скрипты с настройками другого стенда. Остановка `docker compose down` сохраняет данные; `down -v` не является процедурой обновления/отката. Перед миграцией нужна проверенная резервная копия; откат кода не отменяет миграцию автоматически.

## Сборка и данные

`compose.yaml` - учебный dev; отдельный `compose.release.yaml` уже проверен локально; стандартный release не должен грузить необязательные embeddings/индекс ради ручного пути. Не отключать реально заявленный ML незаметно. Lock-файлы обязательны, `npm --force`/`--legacy-peer-deps` не скрывают несовместимость зависимостей.

Чистая source-build измеряется в изолированной среде: SHA, ОС/CPU/RAM, сеть, подготовленные базовые Docker images, время полной команды вместе с зависимостями. Цель ≤5 минут из Blueprint проверяется этим способом. Не очищать общий Docker cache/volume команды ради проверки. Если цель не достигнута, записать факт и оптимизировать ненужные зависимости.

Seed запускается отдельным явным шагом и только для synthetic data. Обычный restart/upgrade не удаляет существующие обращения. Применённые V1..V11 не переписываются. До миграции непустой среды backup, после - контроль ключевых counts/связей. Restore проверяется в отдельную БД, не поверх рабочей без разрешения.

### Окружение

Снимок 28.09: `TRAINING_MODE=true`, `CASE_NUMBER_PREFIX=ДЕМО-`, `ANALYSIS_ENABLED=true`, `MAX_WORKERS_ENABLED=true`, `KAFKA_ENABLED=false`; Python `RULES / rules-baseline-v3`, Chroma включена. Внутренние stateless HTTP-probes Python **6/6 PASS**, engine SHA256 `79042f38b993e147964f414f9d02c421f01d2f126cfa1a281a1128c4343893ae`. Очереди: 0 draft / 3 confirmed; outbox pending/failed/sent 0/0/13, inbox pending/parked 0/0, analysis queued/ready/manual 0/0/0. Это снимок, не результат нового реального MAX-диалога.

Release-переменные - в `deploy/release.env.example`; `.env.example` относится к учебному dev. Секретов в шаблонах нет. Секреты - только `DB_PASSWORD`, `MAX_BOT_TOKEN`, `MAX_WEBHOOK_SECRET`: окружение стенда или хранилище секретов, никогда Git, образ, лог или чат. На HTTPS-стенде дополнительно `SESSION_COOKIE_SECURE=true`; `SESSION_COOKIE_SAMESITE=None` в release для iframe MAX Web; CSRF cookie наследует ту же политику, включая Partitioned на HTTPS через Tomcat. [Прогон с блокировкой сторонних cookies](qa/ui-cookies-2026-09-30.md). `None` с выключенным `Secure` отклоняется при старте. Локальный HTTP runner задаёт `Lax` явно. Реальный MAX mobile проверить отдельно. `koren.http.max-body-bytes` (256 КиБ) и `koren.analysis.poll-ms` менять не требуется. Несекретные настройки MAX: `MAX_API_URL` (по умолчанию `https://platform-api2.max.ru`), `MAX_BOT_NAME` (по умолчанию `t109_hakaton_max_bot`, для кнопки «Открыть обращение»). `CASE_NUMBER_PREFIX` по умолчанию пуст; синтетический стенд может подписать номера, например `ДЕМО-`.

### Seed стенда

Только синтетические данные и только отдельным явным шагом:

1. `python3 scripts/seed_stand.py house "Синтетическая, 1"` - печатает id дома.
2. `python3 scripts/seed_stand.py invite <houseId> --count 2` - печатает одноразовые коды жильцов на 7 дней. В базе только SHA-256 кода; коды передаются закрытым каналом. Жилец входит в Mini App и вводит код (POST `/memberships/claim`).
3. Диспетчер один раз входит в Mini App, затем `python3 scripts/seed_stand.py dispatcher <houseId> <maxUserId>`.

Seed ничего не удаляет. Ролей в обход сервера нет: RESIDENT - только через приглашение, DISPATCHER - только этим шагом оператора.

#### Тестовые роли для проверки (R24)

Для G2 нужны два синтетических дома: `author` - жилец дома А, `dispatcher` - диспетчер дома А, `stranger` - жилец дома Б без доступа к дому А. У каждой роли отдельный реальный MAX-аккаунт; идентификаторы и коды передаются приватно.

Два дома, роли и адреса с пометкой «тестовые данные» описаны в [scripts/seed/seed.json](../scripts/seed/seed.json); id домов постоянные.

1. Каждый аккаунт один раз открывает Mini App из бота.
2. `cp scripts/seed/accounts.private.example.json scripts/seed/accounts.private.json` и вписать MAX user id трёх аккаунтов. Файл в `.gitignore`; у каждой роли свой аккаунт, иначе скрипт откажется.
3. `python3 scripts/seed_stand.py apply` - создаёт оба дома (повтор не создаёт новых), назначает диспетчера дома А и печатает одноразовые коды жильцам, которые ещё не подключены. Жильцы вводят код в Mini App, как настоящие. Коды - только закрытым каналом.
4. Повторный `apply` безопасен: подключённым кодов не выдаёт, не входившим подсказывает открыть Mini App.
5. `python3 scripts/seed_stand.py check` - по каждому тестовому дому OK/MISSING/EXTRA; `PASS` и код 0, только если все роли на месте и ни у кого нет лишних прав в этих домах. Независимо от этого София проверяет `/me` каждого аккаунта и 404 постороннего на карточке дома А.
6. Существующие обращения и историю не удалять: seed ничего не удаляет и не выполняется автоматически при выпуске.

### Резервная копия и восстановление

- Перед любой миграцией непустой базы: `python3 scripts/db_backup.py backup`, затем `verify` на этом дампе. Перед verify проверить, что имя `koren_restore_check` свободно или принадлежит только завершённой проверке, и никто параллельно не запускает verify: скрипт удаляет БД с этим именем. Verify восстанавливает в эту отдельную базу и сравнивает версию миграции, число строк каждой таблицы и md5 всего аудита; рабочую базу не трогает.
- Восстановление рабочей базы: `docker compose stop backend`, затем `python3 scripts/db_backup.py restore <дамп> --confirm koren`, затем `docker compose start backend` и проверка `/actuator/health`. Без остановленного backend и без `--confirm` скрипт отказывается.
- Замер 26.09 на локальной базе: дамп 1,2 МБ за 0,3 с, verify 0,3 с. 27.09 на сервере: dump 57 КБ за 1,0 с, verify за 1,6 с, 20 таблиц и миграция V11 совпали. Рабочая база при проверке не восстанавливалась. Сравнение идёт с текущей живой базой: между backup и verify не должно быть записей, иначе изменение данных после снимка даёт ожидаемое расхождение.
- Перед выпуском 28.09: `koren-20260927T222953Z.dump`, 66 147 байт, backup 0,9 с; restore-check в отдельной БД 1,7 с, 20 таблиц, V11, количества строк и аудит совпали. Выполнен также автоматический откат runtime к `2833443` после ошибки операторской проверки и успешный повтор выпуска; это не восстановление рабочей БД.
- Дампы содержат тексты обращений: `backups/` в .gitignore, в общие папки не класть.

### Инварианты, на которых держится продукт

- Пункт, отчёт, связь, наблюдение и административное решение - разные факты; ответ о свете не закрывает дверь.
- Сохранённый текст отчёта не меняет ни одного пункта; раунд открывает только связь, подтверждённая диспетчером, и только у своего пункта.
- Наблюдение относится к текущим contentVersion и workRound; ответ о прошлом раунде отклоняется, а не применяется к новому.
- Отзыв идёт в withdrawn, архив остаётся в remaining; total не меняется, allConfirmed не становится true без подтверждения автора.
- Доменные команды обращения идемпотентны по ключу и проверяют версии; повтор сначала проверяет права. Вход/выход/погашение приглашения имеют отдельную семантику: повтор погашенного кода может получить 403, тогда сначала обновить `/me`.
- Недоступный объект отвечает 404, чтобы не выдавать факт его существования.
- Python только подсказывает: подсказка не создаёт связь, устаревшая не показывается, STUB не выдаётся за анализ.
- Уведомление ставится в очередь в транзакции команды, несёт только идентификаторы, и права получателя проверяются заново перед отправкой.
