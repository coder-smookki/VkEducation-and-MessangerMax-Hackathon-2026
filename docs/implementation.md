## Авторизация и сессия

MAX доказывает аккаунт, а `membership` - полномочия в конкретном доме. Серверный Principal несёт внутренний `app_user.id`; сведения о роли/доме читаются из БД при доступе к ресурсу. Долгая сессия не должна сохранять отозванное право до следующего входа.

Начальная политика K1: одна Java-инстанция, стандартная серверная HttpSession, 30 минут бездействия. Рестарт может потребовать повторного входа; сохранённые обращения остаются в PostgreSQL. JWT, Redis и своя таблица сессий для этого не нужны. Если позже понадобится несколько инстанций, механизм сессий меняется отдельным решением.

В публичном окружении session cookie имеет HttpOnly и Secure. SameSite и работу cookies во встраиваемых MAX-клиентах проверить в K1, до разработки всех экранов. Один origin упрощает web/API, но не гарантирует поддержку third-party cookies. При блокировке вход считается незавершённым; не заменять его доверенным `userId` или токеном в URL. Обоснованное изменение механизма входа согласуют Кирилл и Семён и фиксируют в DECISIONS.

Для собственного REST-входа использовать штатные механизмы Spring Security: запуск session authentication strategy и сохранение контекста через SecurityContextRepository. Одного помещения Authentication в текущий поток недостаточно. Проверка - следующий HTTP-запрос после login действительно авторизован; старый идентификатор сессии не даёт новый вход. [Spring Security: session management](https://docs.spring.io/spring-security/reference/servlet/authentication/session-management.html).

CSRF остаётся на cookie-командах. React получает токен от Java, отправляет его в заголовке, обновляет после входа/выхода. Webhook имеет отдельную проверку секрета и не использует пользовательскую cookie-сессию. Проверить реальный порядок фильтров и ответы ошибок; не отключать защиту глобально. [Spring Security: CSRF](https://docs.spring.io/spring-security/reference/servlet/exploits/csrf.html).

Диспетчер входит через MAX своим аккаунтом. Внешняя вкладка без проверенного входа показывает инструкцию открытия, а не выбор роли. Начальные дома и Membership назначаются контролируемой серверной операцией для тестовых аккаунтов; публичного self-service назначения ролей в MVP нет.

## Одна рабочая команда

Все изменения одного обращения проходят через его application service. Общая `caseVersion` увеличивается на 1 при каждой успешной бизнес-команде; версии затронутых пунктов также увеличиваются. Это осознанно сериализует редкие правки одного обращения и упрощает согласование отчёта с наблюдением.

1. Ограничить размер тела, разобрать DTO, аутентифицировать актора. Проверить доступ к конкретному дому/обращению/пункту, включая чтение результата повтора.
2. Начать транзакцию. Найти `processed_command` по actor + operation + key. Hash включает HTTP-операцию, целевой ресурс и каноническое тело с версиями; JSON-пробелы и порядок ключей не должны менять смысл. Разное тело при прежнем key - 409.
3. Если повтор найден и доступ сохранился, вернуть сохранённый status/body без нового эффекта. Результат может содержать старую version; клиент перечитывает карточку перед новой командой.
4. Проверить `expectedCaseVersion` условным UPDATE агрегата. Затем проверить `expectedItemVersion`, contentVersion и workRound там, где они нужны. Затронутые строки пунктов блокировать в устойчивом порядке UUID.
5. Выполнить переход, записать историю/редакцию и необходимый outbox/job. Сохранить результат идемпотентной команды в той же транзакции. Commit является границей успеха.
6. Если ответ потерян, повтор с прежним key возвращает прежний результат. Новое пользовательское действие получает новый key.

Конкурентное создание с одинаковым key может столкнуться с уникальностью `processed_command` в конце транзакции: проигравшая транзакция полностью откатывается, затем в новой транзакции читается результат победителя после проверки прав. Аналогично при конфликте version сначала проверить, не завершился ли идентичный повтор. Нельзя продолжать SQL в уже аварийной транзакции или возвращать 500 на ожидаемый duplicate. Ошибка другой уникальности не считается успешным повтором.

Для команд над существующим обращением сохранять порядок: агрегат → пункты → история/очередь. Внешних HTTP-вызовов внутри транзакции нет. Неверная команда не оставляет ни новых версий, ни строк истории, ни outbox.

## Правки и отчёты

В обязательном MVP исходный текст и список меняются только в DRAFT. Правка текста увеличивает sourceRevision; правка category/location/symptom увеличивает contentVersion затронутого пункта. Подтверждение фиксирует ровно текущий непустой список. После CONFIRMED список не заменяется и пункты не удаляются; отзыв с причиной сохраняет знаменатель. Согласованный сложный пересмотр принятого обращения - отдельное расширение, пока API отвечает `CASE_ALREADY_CONFIRMED`.

Сохранение `work_report` само по себе **не** меняет workRound, workStatus или observation. Изменение происходит только при подтверждении диспетчером конкретной связи report → item. Один новый link создаёт один новый раунд; повтор не создаёт ещё один. Один report/item нельзя связать второй раз новым ключом. Нет связи с дверью - нет изменения двери.

Отчёт неизменяем. Ошибка исправляется новым отчётом; старый остаётся в истории. Отчёт исполнителя принимается только для назначенных ему пунктов. Диспетчер не может использовать его отчёт для чужих назначений. Для этого в S2 сохраняется явно разрешённая область `targetItemIds` отчёта.

Отзыв блокирует новые наблюдения и связи. Архив сохраняет наблюдения и не превращается в успех; позднее авторское наблюдение допустимо, автоматические напоминания для архива не создаются. Архив не меняет сам workStatus.

## Надёжные задачи и ограничение нагрузки

Простой выбор строки с `FOR UPDATE SKIP LOCKED` защищает только транзакцию. Если commit выполнен до сетевого вызова, нужно сохранить lease и уникальный ownership token. Это наша схема обработки поверх транзакционных блокировок PostgreSQL. [PostgreSQL 17: locking clause](https://www.postgresql.org/docs/17/sql-select.html).

1. В короткой транзакции выбрать доступную задачу, увеличить attempts, записать token/lease_until и commit.
2. Выполнить ограниченный по времени сетевой вызов вне транзакции.
3. В новой транзакции завершить задачу только при совпадении token. Просроченный worker не может перезаписать результат нового владельца.
4. Если процесс упал, после истечения lease задачу забирает другой worker. После последней попытки остаётся видимая терминальная причина без полных текстов/секретов.

Начальная политика S4/S5 для проверки, ещё не runtime-конфигурация: один активный inference-вызов на Java-процесс, неограниченной очереди в RAM нет; задания остаются в PostgreSQL. Lease 60 секунд при сетевом deadline не более 10 секунд. Для анализа максимум 3 попытки, задержки 5 и 30 секунд; для доставки максимум 5 попыток, задержки 1/5/30/120 секунд. Добавить небольшой jitter; MAX Retry-After учитывать, если он предоставлен. Политику времени inference сверить с N5; сегодняшний demo-client имеет timeout чтения 3 секунды и не меняется только из-за этого плана.

Неверная схема/выдуманное evidence - ручной разбор без повторов того же ошибочного ответа. Перегрузка/временная сеть могут повторяться ограниченно. Ошибка credentials требует исправления конфигурации, а не бесконечного retry.

Рабочий Java API принимает JSON до 512 KiB до десериализации, затем применяет символьные лимиты API. Для ответа inference установить предел 2 MiB до полного разбора JSON. Это выбранные стартовые пределы MVP; проверить escaped Unicode, chunked ответ и отсутствие Content-Length. Python также ограничивает фактический вход и число одновременно работающих inference. Лимиты символов и байтов решают разные задачи.

## Актуальность анализа

Job сохраняет полный snapshot: caseId, sourceRevision, reportId, точный reportText, itemId/contentVersion/workRound. Hash snapshot участвует в уникальности. Python анализирует только этот вход.

Перед сохранением/выдачей READY Java сравнивает snapshot с актуальными строками и полным набором доступных пунктов. При изменении раунда, состава или версии результат STALE и не предлагается к применению. Сам валидатор JSON не узнаёт о правке в БД.

Жизненный цикл: QUEUED → RUNNING → READY либо MANUAL_REQUIRED/STALE; повтор временной ошибки возвращает задачу в очередь с available_at. Состояния задачи не смешиваются с mode анализа и четырьмя фактами пункта. При READY человек всё равно отправляет отдельную обычную команду связи с актуальными версиями.

## Inbox, outbox и callback

Кирилл проверяет ограниченное тело webhook и секрет, строит ключ только из реально проверенного типа MAX Update и стабильных идентификаторов, записывает inbox. Лишь после commit отдаётся 200. Совпавший key с другим payload_hash не затирает событие; конфликт фиксируется и обрабатывается отдельно. Неподдержанный тип не превращается в предметную команду.

Семён обрабатывает событие через те же application services. Callback содержит непрозрачную server-side ссылку; сервер заново проверяет sender, автора, Membership, item, contentVersion, workRound, ожидаемую itemVersion, срок и действие. Текущую caseVersion обработчик читает перед транзакцией и проверяет при записи; изменение другого пункта не делает старую кнопку полномочием обойти CAS. Клиентская кнопка не является разрешением. Повторный callback использует стабильный ключ той же команды.

Hash команды callback строится из неизменного входного действия/ссылки и сохранённого контекста кнопки. Заново прочитанная сервером caseVersion не включается в этот hash: иначе повтор одного события получил бы другое тело. Для браузерной команды, напротив, присланная expectedCaseVersion является частью пользовательского запроса и hash. Проверка разрешённого replay выполняется до применения к текущим версиям.

Для одного автора/пункта/contentVersion/workRound создаётся максимум одно логическое приглашение проверить результат после REPORTED_DONE. Нет соседских опросов. Наблюдение уже получено, пункт отозван/архивирован или включён opt-out - новая отправка не нужна. Повторные доставки одного outbox не считаются новыми приглашениями.

Перед фактической отправкой worker проверяет актуальность и настройки ещё раз. Opt-out отменяет ожидающие отправки; уже начатый сетевой вызов нельзя надёжно отозвать. Таймаут после принятия сообщения MAX может привести к повторной доставке: exactly-once внешней сети не обещается, кнопка остаётся идемпотентной. Логи содержат event ID, попытку и код ошибки, без токена и текста обращения.
