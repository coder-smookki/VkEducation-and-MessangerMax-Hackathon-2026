# План реализации по слоям

Это инструкция расширения существующего dev, а не перечень готовых сервисов. Владение - [план команды](plan.md), исходные пробелы - [состояние](memory/PROJECT_STATE.md).

## 1. Согласовать данные, прежде чем соединять экраны

S-01/K-01/Q-01: проверить Java CaseView и машинные схемы. Отдельно добавить целевые receipt/nextAction/allowedActions/displayNumber. Сохранить itemId/версии и формат problem+json. Перечислить целевые endpoints явно: наличие строки в docs/api.md не открывает контроллер. Кирилл начинает на валидируемых fixtures, после S-02 переключает вызовы на тот же контракт.

Не создавать 62 backend endpoints под 62 изображения. Это состояния небольшого числа маршрутов: вход, список, редактор, карточка, отчёт, настройки. Данные каждого состояния задаёт [матрица](screens.md).

## 2. Вход и HTTP на имеющемся ядре

Переиспользовать MaxInitDataValidator и MaxUserProvisioner. Валидация сырого initData → внутренний user ID → серверная сессия. Не принимать actor/роль из тела. `/me` отдаёт только текущие действующие memberships. Роль AUTHOR не создавать: это отношение авторства, enum жителя RESIDENT.

Семён добавляет HTTP-адаптер к CaseService, не пишет новый CRUD рядом. Валидация request до application, объектный доступ/версия внутри команды. 404 скрывает чужую сущность; 403 обозначает недопустимое действие без раскрытия закрытого контекста. Cookie-команды защищены CSRF. Public MAX webhook исключается из cookie-механизма точечно и защищается своим протоколом.

Членство/приглашения требуют безопасного persistence: активность, отзыв, одноразовое атомарное потребление кода, срок, ограничение попыток. Исторические FK сохраняются. Секрет приглашения не включать в лог, аудит хранит результат без кода.

## 3. Транзакция команды и повтор

1. Найти actor из проверенной сессии/события; проверить текущие права на target.
2. Проверить структуру запроса, operation и Idempotency-Key. Scope: actor + operation + key; canonical request hash включает target, тело и исходные expected versions.
3. Если результат уже сохранён - сверить hash, повторно проверить доступ, вернуть тот же результат без второго изменения.
4. Выполнить CAS/блокировку согласно существующему паттерну репозитория. Проверить caseVersion и нужные item/content/round версии. Конкурентный проигрыш - 409.
5. Записать mutation, audit, command result и необходимые outbox события в одной транзакции. COMMIT.
6. Вернуть серверную проекцию. Внешний Python/MAX/Kafka вызывается вне транзакции.

При гонке уникального processed_command нельзя продолжать SQL в уже aborted PostgreSQL-транзакции: откатить и прочитать результат победителя в новой транзакции. Не увеличивать счётчики при повторе. Same key/different body - конфликт. Новый key не исправляет старую expectedVersion.

Для бот-кнопки canonical command строится из сохранённого callback context, а не текущей версии, прочитанной при каждом retry: иначе один и тот же callback меняет смысл. Для browser retry повторяется исходное тело. Новое осознанное действие после перечитывания получает новый ключ и версии.

## 4. Приём, следующий шаг, отчёт, наблюдение

Приём - отдельная команда только для CONFIRMED. NextAction - отдельный пункт, действующий owner дома, текст и updateDueAt. Эти поля не изменяют наблюдение. Отчёт immutable; сохранение не меняет workRound. Явная подтверждённая связь проверяет весь набор links атомарно и открывает раунд только выбранных пунктов. Новый раунд сохраняет старое наблюдение в истории, сбрасывая текущую проекцию.

Наблюдение автором: текущие item/content/round, AFTER_REPORT только при REPORTED_DONE; INDEPENDENT допускает самостоятельное наблюдение по предметным правилам. DISPATCHER не отвечает за автора. Архив/отзыв выбранного пункта требуют причины; оба не сокращают исходный total и не создают успех. Aggregate progress вычисляется одним CaseProgress.

## 5. Python и анализ текста

HTTP-клиент уже умеет fallback и проверку ответов; сохранить. Сначала снимок разрешённого контекста Java, затем ограниченный по времени запрос, затем повторная сверка прав/версий перед выдачей подсказки. Изменившийся snapshot помечать STALE; не применять старый ответ к новым пунктам.

Извлечение сейчас STUB: интерфейс обязан дать ручное создание. Clarify проверяет недостающие поля; вопросы только автору. Compare RULES исправить по классу смешанных субъектов, не по одной демонстрационной строке. Любое неточное evidence/неизвестный itemId/неполный список означает отказ от подсказки. Никакого исполнения команд из reportText.

Необязательный поиск: Java отбирает до 20 разрешённых подтверждённых кандидатов, Python сравнивает пары пунктов, Java заново сверяет все snapshots. Chroma не является источником прав и не заменяет БД. NOT_EVALUATED/null не превращать в «совпадений нет».

Для Must не нужен новый универсальный workflow engine. Если анализ асинхронный, его job действительно сохраняется и имеет lease/terminal state; если синхронный, API честно описывает timeout/fallback и не обещает несуществующий job endpoint. Выбранный вариант закрепить вместе с UI, не делать GET запускающим новый анализ.

## 6. Текстовый бот и очереди

Webhook проверяет секрет/размер/тип события, формирует стабильный dedup key по фактическому формату MAX. Не переносить Telegram update_id по предположению. Durable inbox сохраняется до ACK. Повтор после ACK/перезапуска не исполняет команду дважды. Диалог имеет серверный шаг/контекст/срок, привязан к конкретному пользователю.

Outbox сохраняется вместе с командой. Worker атомарно захватывает запись, отмечает lease/попытку, освобождает или доводит до terminal error. Сетевой deadline меньше lease. На 429 учитывать фактический Retry-After, на 5xx ограниченный backoff; точные значения конфигурации закрепить и проверить, не бесконечный retry. Перед отправкой перепроверить получателя, актуальность раунда и отказ от уведомлений. Новое сообщение с кнопками содержит адресуемый пункт и версии; старое объясняет конфликт и предлагает открыть актуальную карточку.

Доставка во внешний API не гарантирует exactly-once, если ответ потерян после отправки; документировать возможный повтор сообщения. Повтор сообщения не должен означать повтор бизнес-команды. Метрики: возраст очереди, число попыток, ошибки, requestId без текста обращения/токена.

## 7. Frontend как потребитель состояния

Один API client с понятными 401/403/404/409/422/429/503 и unknown outcome. Сохранить Idempotency-Key/тело pending-команды в памяти до выяснения результата. После 409 сохранить незаписанный ввод, перечитать, дать человеку сравнить и решить; не автоперезаписывать.

На смене дома/карточки отменять или игнорировать старый ответ по request context. Pending/loading не рисует успешный статус. Изменение темы не стирает форму. Theme/text preference можно сохранять локально с обработкой недоступного storage; реальные тексты/секреты/права не сохранять так из design-прототипа.

Использовать общий ItemCard/Progress/NextAction/ReportEvidence/History и формы. Не делать отдельные копии карточки для каждого PNG. Полный текст доступен при 200%; footer не скрывает поля/фокус. Route guard удобен, но не заменяет Java authorization.

## 8. Доказательство перед выпуском

Миграции на clean DB и с V2, реальные HTTP команды, обязательные QA-E/A/R, MAX двумя ролями и два последовательных прогона. Независимая сборка из исходников/lock и backup restore. Profile demo/no-db отсутствует в публичном запуске. Непроверенное пометить NOT_RUN и оставить конкретный блокер, а не дописывать README «всё готово».
