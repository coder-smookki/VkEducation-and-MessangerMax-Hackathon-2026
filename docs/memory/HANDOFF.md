## Как начать параллельно

Прочитать [parallel-development.md](../parallel-development.md): за первый час сверить C1, затем каждый начинает свой компонент. Кирилл строит K2/K3 на согласованных примерах до готовности S1-S3; Семён тестирует серверные команды на отдельной PostgreSQL до готовности K1; Никита использует текущий C3 без ожидания обоих.

Новый подробный порядок: [Кирилл](../team/kirill.md), [Семён](../team/semyon.md), [Никита](../team/nikita.md). Точки сборки I1/I2/I3 в [общем плане](../plan.md). K5a нужен до проверки S5, а не после G2. Примеры запросов и версии - [worked-example.md](../worked-example.md), проверки - [acceptance.md](../acceptance.md).

Следующие решения T0: фактические часы каждого, актуальный кейс/допуски, бот/домен, доступное железо NLI. Ответственного указывает соответствующая задача; отсутствие внешнего доступа не останавливает локальные контракты. Runtime-сессии, рабочие Java REST-команды и workers ещё не реализованы; новые внутренние inference DTO/клиенты готовы.

## Передача исправленного dev - 13.09.2026

Начать с [contracts/README.md](../../contracts/README.md) и подробного [04](../../contracts/04-similar-cases.md). Кирилл: показывать предложения/вопросы только автору; READY_FOR_REVIEW не означает выполненный ремонт. Не открывать рабочие endpoints до K1/S1; будущий серверный Principal передать в SimilarCasesService.

Семён: использовать SimilarCasesService.find(verifiedUserId, caseId, limit). Он проверяет Membership, берёт подтверждённые snapshots из БД, ограничивает запрос 20 кандидатами/512 KiB и повторно проверяет права/версии после HTTP. Не вызывать его внутри транзакции команды. Подключить CaseEventPublisher через durable outbox после подтверждения состава: future ошибки доступен вызывающему коду, само наличие publisher не обеспечивает доставку. Вызовы из CRUD пока отсутствуют. Для хранения intake/similar не придумывать report_id; согласовать новую структуру в S4. Применённые V1/V2 не менять.

Никита: Chroma сохраняет целое обращение в коллекцию с суффиксом `_snapshots_v2`, внутри - векторы отдельных пунктов. Не возвращать поиск только по houseId: вход содержит разрешённые Java candidates, ML не расширяет его. Проверены дверь во втором пункте, слабое/чужое/устаревшее совпадение, повтор и порядок 7→6. Пороги 0.85/0.95 и all-MiniLM-L6-v2 пока не имеют измерения качества на русском; подготовить размеченные пары, оценить ложные объединения и пропуски. Extract/compare остаются STUB, clarify - RULES.

Consumer перечитывает историю даже с прежней группой и подтверждает offset после записи. В dev история Kafka не ограничена: до эксплуатации нужен backfill из Java и политика хранения. Один полный индекс обслуживает одна группа с одним активным consumer; отдельные volumes реплик требуют разных групп. Старый формат Chroma не удаляется автоматически, новая коллекция строится replay. Секреты и продуктовая PostgreSQL Python недоступны.

Проверено локально: 42 Java и 49 Python тестов с реальными PostgreSQL/HTTP/Kafka/Chroma; Java-интеграция использует реальные ONNX-веса, Python регрессии - тестовые векторы. Полные команды и пределы - [testing.md](../testing.md), актуальные факты - [PROJECT_STATE.md](PROJECT_STATE.md). Готовность CRUD, MAX, NLI или точность модели не заявлены.
