## Не потерять при интеграции

receipt, nextAction, displayNumber, отчёты и связи, наблюдения, административные решения и история реализованы и возвращаются; в контракте не осталось ни одной операции со статусом TARGET, TARGET остался только у поля allowedActions.

Сохранение отчёта не создаёт раунд: раунд создаёт только подтверждённая связь, и только у своего пункта. Набор связей применяется целиком или не применяется вовсе. Повтор пары отчёт-пункт закрыт навсегда: новые сведения оформляются новым отчётом, а не новым ключом идемпотентности.

Отзыв и архив - разные исходы, а не синонимы: отзыв попадает в withdrawn, архив остаётся в remaining, и ни один из них не уменьшает total и не даёт allConfirmed. Оба необратимы: возврата из архива и отзыва в контракте нет, новая проблема оформляется новым пунктом. Окончательность проверяется и в SQL, не только в домене.

История отдаёт details по белому списку полей, а не payload аудита как есть; добавляя новое событие, надо добавить и его поля в HISTORY_DETAIL_FIELDS, иначе событие появится в истории с пустыми деталями. Недоступное обращение отвечает 404, а не 403, - иначе 403 выдал бы факт существования чужого обращения.

Уведомление ставится в очередь той же транзакцией, что и изменение состояния, и несёт только идентификаторы. Право получателя проверяется заново перед отправкой: потерявший доступ получает отмену с причиной, а не сообщение, и sent_at у такой строки остаётся пустым - отменённое не считается доставленным. Ответы бота лежат в той же очереди с пустым case_id, и для них проверять права по обращению нечего: получатель сам нам написал.

Разбор update'а MAX терпим к нескольким формам полей и **не догадывается**: без распознанного отправителя событие остаётся во входящем ящике с пустым processed_at. Когда появится живой трафик, первые же застрявшие события покажут настоящий формат - править надо senderId/text в BotDialog и eventKey в WebhookIntake, а не подгонять тесты.

RULES v2 не переносит сказуемое с одного пункта на другой, но и не понимает больше, чем v1: при сомнении воздерживается. Не выдавать development 16/16 за гарантию - эти фразы видели при написании правил; честная проверка - holdout Софии. Подсказка - это совет: READY не значит, что работа сделана, связь всё равно подтверждает диспетчер. Подсказка про прошлый раунд или прошлую версию пункта не отдаётся (STALE). SimilarCasesService и сравнение отчёта не вызывать внутри SQL-транзакции, события CRUD отправлять только через durable outbox.

MockMvc не пересылает сбой на /error и не маскирует CSRF-токен, поэтому ни коды ошибок, ни CSRF-рукопожатие им не проверить: такие тесты идут через настоящий порт, как ErrorResponsesHttpTest. Непойманное исключение логирует только RequestIdFilter и без сообщения; не добавлять логирование e.getMessage() и не ловить Exception в @ExceptionHandler - это вернёт текст в лог или перехватит CaseException.

Состояния уведомления: sent_at - доставлено; failed_at - отправка прекращена (отказ MAX или последняя попытка); отмена по правам - available_at через 100 лет и причина в last_error. Ограничения «не sent_at и failed_at вместе» в базе нет, потому что тесты паркуют чужие строки через sent_at; правило держит код. Настоящий отправитель MAX должен бросать MaxDeliveryException.fromHttp(...) на ответ API: любое другое исключение считается временной недоступностью и повторяется.

## Как заканчивать

ID/ветка/SHA, пользовательский результат, изменённый DTO/миграция, команда проверки/результат, предел, следующий ID. Общий статус после интеграции обновляет Кирилл. [AI-инструкция](../ai-workflow.md) содержит готовые промпты. Доступность сервера и реальный deployment не выводятся из наличия дизайна; [release](../release.md) описывает необходимые доказательства.

Полная проверка ml та же, что в CI: `uv sync --frozen && uv run pytest -q && uv run ruff check . && uv run ruff format --check app scripts tests && uv run pylint app`; pylint падает на любом сообщении. Java-тесты без DB_TEST_URL пропускаются молча: 177 с 125 skip - не зелёный прогон. Перед миграцией на стенде - `scripts/db_backup.py backup` и `verify`. CI-интеграция включает Kafka сама (COMPOSE_PROFILES=similar, KAFKA_ENABLED=true); локально для тех же тестов - те же две переменные, иначе Kafka не стартует.
