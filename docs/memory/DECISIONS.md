# Архитектурные решения

Дата: 19.09.2026. Обновлять существующее решение при изменении причины; не превращать файл в полный лог разговоров.

## D14. Детали интеграции 19.09.2026

Статус: принято при реализации K1/N1. В data-check-string MAX входят URL-декодированные значения: шаг 4 официальной страницы валидации (dev.max.ru) и её TS-пример требуют decode до подписи; «сырым» сохраняется только JSON пользователя (не пересериализуется). Тестовые векторы HMAC генерируются независимым инструментом (python3), а не проверяемым Java-кодом.

RULES baseline (N1) подключается только явным env `KOREN_COMPARE_ANALYZER=rules`; поведение сервиса по умолчанию остаётся STUB, поэтому общие контрактные примеры, Java contract tests и smoke не менялись. Смена режима по умолчанию - отдельное решение после held-out оценки N4.

Локальная проверка Java выполнялась на PostgreSQL 16 (Homebrew) вместо 17: DDL V1/V2 и новые тесты совместимы; подтверждение на 17 даёт CI (postgres:17-alpine) после push. Это ограничение локального доказательства, не смена целевой версии.

## D1. Один Java-владелец состояния

Статус: принято. Java 21 / Spring Boot 4.1.1 с PostgreSQL. Один монолит по предметным пакетам проще для двух backend-разработчиков, чем набор сервисов со своими транзакциями. Python отделён по границе inference; в dev добавлен производный Chroma-индекс без полномочий менять PostgreSQL или выдавать доступ (D13). Цена: Java-процесс также обслуживает workers; масштабировать его независимо по функциям пока не требуется.

Рассмотрены два варианта: монолит + stateless inference и микросервисы/внешний workflow engine. Выбран первый: текущие инварианты легче проверить в одной транзакции. BPMN не требуется. Позднее в dev появился Kafka только для доставки снимков в производный индекс (D13); он не заменяет транзакционные правила монолита.

## D2. Четыре факта вместо единого статуса

Содержание, отчёт, наблюдение и административное решение хранятся раздельно по каждому пункту. «Работы закрыты» не превращается в «автор подтвердил результат». Обоснование - сценарий лампы и двери, а также явное различение источника отметки в FixMyStreet. Цена: UI показывает несколько коротких полей; нет одной удобной, но неточной зелёной галочки.

## D3. Явные SQL и версии

Spring JDBC + Flyway. Составные FK защищают принадлежность, optimistic lock защищает актуальную запись, таблицы редакций сохраняют исходный контекст. JPA не добавлен: для небольшого числа операций явный SQL с ожидаемой версией понятнее команде. Цена: ручное отображение DTO и SQL-запросов. После применения миграции не менять её текст, продолжать следующей версией.

## D4. Сначала ручной процесс, затем измеренная NLI

Модель не владеет состоянием. STUB запускается без весов и честно возвращает `INSUFFICIENT_INFORMATION`. Кандидат NLI исследуется отдельно, сравнивается с формой и правилами. Генеративный LLM не требуется для базового пути. Цена: стартовая заготовка не демонстрирует качество ML; оно будет результатом N2-N5, а не обещанием.

## D5. Надёжность на границе сети

Состояние + аудит + outbox в одной транзакции; webhook сначала сохраняется в inbox и лишь затем подтверждается. Внешние вызовы идут вне транзакции, с ограниченными повторами и проверкой актуальности. Причина inbox - окно между ранним ACK и обработкой, наблюдаемое в прочитанном standalone handler MAX SDK. Цена: worker и повторы нужно реализовать в S4/S5/K5. Таблица сама не является готовым worker.

## D6. Понятный frontend и воспроизводимые зависимости

React/TypeScript/Vite без SSR и лишнего UI-фреймворка. MAX Bridge ограничен отдельным адаптером. MAX UI 0.4.0 требует точные React peers 19.2.8; стартовый React 19.3.0 не форсируется через несовместимую установку. Подключать UI kit только при реальной пользе и совместном закреплении версий. Цена: базовые стили поддерживает Кирилл.

## D7. Командная память в Git, личная в Obsidian

По явному поручению пользователя планы и память для нейронок находятся в `docs/`. В Git сохраняются общие факты разработки, решения и передача работы. Личная карточка КОРНЯ в Obsidian остаётся долговременной личной памятью; её содержимое и исходные разговоры не экспортируются в репозиторий.

## D8. Безопасный старт

Рабочие endpoints закрыты до K1/S1. Demo - синтетический, только по явному профилю, с отдельными путями и без сохранения. Compose публикует порты только на loopback, Python не получает доступ к PostgreSQL. Производный индекс dev описан в D13. Цена: демо не заменяет публичный deployment; внешний запуск требует отдельной проверки настоящего входа и конфигурации.

## D9. Параллельная работа по контрактам

Статус: принято для плана 12.09.2026 по прямому уточнению пользователя. C1-C4 выпускаются до готовности полного компонента; UI, Java и ML используют согласованные фикстуры. Совместный результат интегрируется последовательно в main. Миграции координирует Семён, общий статус/память - Кирилл. Причина: очередь из трёх разработчиков не помещается в тот же бюджет, что параллельные независимые задачи. Цена: короткая ранняя сверка DTO и обязательная проверка настоящего соединения после mock.

K5a выделен из K5 для раннего webhook/транспорта; K5b оставлен для упаковки. S4 проверяется на STUB до NLI. Это устраняет циклическое ожидание этапов, не ослабляя авторизацию для тестирования.

## D10. Граница редактирования и версии MVP

Статус: принято как целевое поведение, реализация S1-S3 впереди. Source/items редактируются в DRAFT, confirm фиксирует текущий список. После подтверждения обычная замена запрещена; отзыв пункта сохраняет знаменатель. Сложный согласованный пересмотр принятого обращения отложен. Причина: избежать неявного переноса старых отчётов/наблюдений на другое содержание. Цена: исправление принятого состава требует отдельного будущего сценария, а не скрытого PATCH.

Общая caseVersion меняется каждой бизнес-командой обращения; itemVersion - изменением/подтверждением пункта. JSON именует их явно. Цена: одновременные изменения разных пунктов одного обращения могут конфликтовать; для MVP такой явный конфликт проще распределённых частичных слияний. Сохранение report не создаёт workRound: это делает только подтверждённый link.

## D11. Сессия и владение очередью

Статус: целевой план, не работающая инфраструктура. В K1 начинаем со штатной HttpSession одной Java-инстанции, CSRF и проверки совместимости cookies в MAX на раннем этапе. Рестарт требует нового входа; данные остаются в PostgreSQL. Цена: это не схема горизонтального масштабирования, совместимость конкретных клиентов ещё нужно подтвердить.

Для S4/S5 выборка SKIP LOCKED дополняется persisted lease/token: после commit строковая блокировка уже не защищает сетевой вызов. Завершить задачу может только актуальный владелец. Цена: дополнительные поля и тест падения процесса; Kafka dev обслуживает индекс; jobs и доставку MAX он автоматически не реализует. Внешняя доставка остаётся с возможным повтором, предметные команды идемпотентны.

## D12. Пять контрактов и подтверждённый вход - 13.09.2026

Статус: принято и реализовано в пределах заготовки по уточнениям пользователя. Уровни относятся к предложению проблем и авторскому подтверждению, а не к готовности ремонта. Каталог 01-05: extract, уточнение только у автора, review/confirm Java, similar, compare. NEEDS_DETAILS/READY_FOR_REVIEW отражают заполненность формы; CONFIRMED создаётся только командой Java. Рабочий review REST пока SCHEMA_ONLY.

Рассмотрены пять независимых ML-операций с дублированием решения о готовности и общие границы по реальным действиям. Выбран второй вариант: четыре Python POST и отдельный контракт команд автора. Проверка недостающих полей реализована простыми правилами, потому что для неё не нужна модель. В первоначальной основе извлечение и сходство были STUB без провайдера/векторов. Извлечение остаётся STUB; дальнейшая реализация сходства в dev и её исправления описаны в D13.

Неизменная граница - Python сравнивает только переданных Java кандидатов того же дома с проверенными правами. В первоначальном контракте не было индекса и scope был PROVIDED_CANDIDATES. Текущий dev использует CHROMA, сохраняя ограниченную Java выборку и честный отказ; несовместимое изменение Java/Python и примеров выпускается вместе (D13). Сходство не является разрешением объединить обращения или потерять отдельный пункт.

Экспорт inference остаётся из Python; будущий author-review OpenAPI поддерживается Семёном/Кириллом отдельно. Dev-зависимость jsonschema проверяет примеры и реальные HTTP-ошибки, включая исправленную форму 422. Старый `/compare` совместим; новые маршруты только внутренние, миграций нет. Откат изменения возвращает прежний клиент/образ без преобразования данных БД.

## D13. Исправление Kafka/Chroma в dev - 13.09.2026

Статус: реализовано в dev по поручению исправить пять проблем review коммита коллеги 9dbed68. Существующие Kafka и Chroma сохранены; Java остаётся единственным владельцем продуктовой БД. Chroma - производный снимок и векторы, не источник прав или факта ремонта.

Возвращена передача полного набора разрешённых candidates из Java. SimilarCasesService читает Membership/CONFIRMED/current revisions в короткой REPEATABLE_READ транзакции, ограничивает выборку двадцатью обращениями и 512 KiB UTF-8, делает HTTP вне транзакции и повторно читает все снимки/права. Для полного контекста житель/исполнитель видит свои обращения, диспетчер - дом своего Membership. Цена: это ограниченная выборка, возможны пропуски старых похожих обращений; Chroma не выполняет самостоятельный поиск по одному houseId.

Индекс хранит одну атомарно заменяемую запись на caseId с отдельными векторами пунктов. До записи вычисляются все векторы, писатели одного volume сериализованы; меньшая caseVersion игнорируется, конфликт одинаковой версии отклоняется. Коллекция `_snapshots_v2` отделена от прежнего формата. Replay с начала работает и с прежней Kafka-группой; подтверждается только успешно записанный offset. Для MVP сохраняется вся история: compact оставил бы поздний offset версии 6 после версии 7 и испортил бы rebuild. Цена: растущий журнал и повторное чтение на старте; до production нужны backfill из PostgreSQL и политика хранения. Независимые индексы требуют разных consumer groups.

Сопоставляются отдельные пункты, с одинаковой категорией и нормализованным местом, с явными парами itemId. RELATED начинается с cosine 0.85; POSSIBLE_DUPLICATE требует полного взаимно однозначного покрытия и минимального score 0.95. Это консервативные неизмеренные пороги dev: качество на русском и полноту проверяет Никита. Java дополнительно отвергает неполное «дублирование» и повторное использование пункта. Отключённый, неполный или устаревший индекс даёт MANUAL/NOT_ANALYZED, а не ложное отсутствие похожих.

Исправлены Boot Kafka starter/Jackson 3 serializer, writable cache непривилегированного ML-пользователя и HTTP/1.1 для совместимости с Uvicorn. Publisher возвращает подтверждаемый future; связь с CRUD/outbox ещё не реализована и не заявляется готовой. Проверки и границы доказательства - [testing.md](../testing.md).
