## Подтверждённые факты

GitHub-репозиторий был приватным и пустым. Создана самостоятельная заготовка на Java 21 / Spring Boot 4.1.1, React 19.3.0 / TypeScript / Vite 8.3.0, Python 3.12 / FastAPI 0.141.1 и PostgreSQL 17. Версии закреплены POM/Maven Wrapper и lock-файлами. MAX 2025 не переносился.

Каркас включает Java-приложение и чистые правила `ItemState`/`CaseProgress`, Flyway V1 и V2, клиент inference с проверкой evidence/версий и fallback, изолированный demo API, React-экран, Python STUB с OpenAPI и JSON-примерами, Docker Compose, CI и сквозной smoke script.

Пример действительно вызывает Python через Java и frontend proxy. У обоих пунктов сохраняется отдельное состояние. STUB возвращает отказ от интерпретации; MANUAL означает недоступность/некорректность анализа. Пользователь видит, что данные вымышленные, а модель не подключена.

В `docs/team/` подробные пошаговые планы Кирилла, Семёна и Никиты: существующие файлы, начало без ожидания соседнего компонента, порядок реализации, негативные проверки и передача. Общий план использует T0-T15; календарные даты из PDF являются предварительным предположением. Реестр задач в `docs/plan.md` остаётся TODO: подробная спецификация не означает выполненный продукт.

По уточнению пользователя план переработан под параллельную разработку. C1-C4 фиксируют границы до реализации; Кирилл делает UI на фикстурах, Семён - сервисы с тестовым серверным актором, Никита - анализ на JSONL. Интеграция в main последовательная, общие миграции координирует Семён. K5 разделён на ранний транспорт K5a и упаковку K5b; устранено ожидание webhook до завершения этапа, которому он нужен.

Добавлены `parallel-development.md`, `implementation.md`, `worked-example.md`, `acceptance.md`: владение файлами/окружениями, транзакции и lease, целевые REST DTO, пример десяти команд с версиями, 15 подробных сценариев приёмки. Это проектная спецификация следующей работы, а не новые работающие endpoints.

Таблицы и границы пакетов не означают готовность этих функций.

Новые внутренние операции не означают готовность пользовательского процесса: ещё нет настоящего извлечения пунктов/семантического поиска, сохранения их результатов, frontend формы уточнения и отправки вопроса автору в MAX. Схема 03 - SCHEMA_ONLY. Роли RESIDENT/DISPATCHER/EXECUTOR и миграции V1/V2 не менялись; выдача Membership/вход остаются K1/S1.

## Решения

Java единолично меняет рабочую БД; Python возвращает только подсказку. Четыре факта пункта независимы. Отчёт/отзыв/архив не равны подтверждению результата. Сохраняются sourceRevision, contentVersion, workRound и optimistic version. Полнота списка и точность Unicode evidence проверяются до показа предложения.

Причины и цена решений: [DECISIONS.md](DECISIONS.md). Исследованы FixMyStreet, Open311, официальный MAX SDK/UI и doccano; закреплённые источники - [research.md](../research.md). Не заявлено мировое первенство или измеренное превосходство над аналогами.

## Правило обновления

Заменять устаревшее состояние. Записывать только проверенный факт, команду/результат и ближайший незавершённый шаг. Не хранить в Git личные данные, токены, закрытое ТЗ или полные разговоры. Личная карточка проекта ведётся в Obsidian отдельно от этой командной памяти.

При параллельной работе автор задачи передаёт факты интегратору, а Кирилл обновляет общий статус после проверки объединённого кода. Перед записью перечитать актуальный файл и сохранить чужие изменения. В факте указывать ID задачи, commit/дату проверки, команду, результат и предел доказательства. Не добавлять отдельную память на каждого помощника.

Если проверка не запускалась, писать NOT_RUN с причиной. Если команда упала, писать FAIL и следующий шаг, не заменять результат планом исправления. Устаревший факт заменить, существенную причину решения хранить в DECISIONS, историю изменений оставлять Git.
