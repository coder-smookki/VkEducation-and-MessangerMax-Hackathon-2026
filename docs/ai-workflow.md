# Как поручать работу Claude/Codex

## Один агент - конкретная проверяемая задача

Передать репозиторий целиком с `AGENTS.md`, `CLAUDE.md`, `docs/`, `contracts/`, `design/` и lock-файлами. Не прикладывать `.env`, токен или реальные обращения. Отсутствие локального исходного PDF не мешает работе: активная спецификация продублирована в предметных документах, планах и матрице экранов.

1. Прочитать текущий [QA-протокол](qa/profile-visual-2026-09-27.md), `docs/memory/PROJECT_STATE.md` и выбранный персональный план. S-01..S-09 уже интегрированы; старый TODO или истёкшая дата не повод повторять реализацию. Выбрать незавершённый ID и владельца в `docs/plan.md`. ID S/K/Q с дефисом относятся к текущему плану; прежние S1/K1/N1 - только исторический вклад.
2. Проверить Git и актуальные файлы. Составить короткую трассу «действие → DTO → права → application → SQL → ответ → экран». Найти существующего владельца инварианта.
3. Назначить одного владельца каждого изменяемого файла; независимые задачи можно выполнять параллельно. Не выполнять задачи соседнего участника молча. На согласованных fixtures разрешено разрабатывать UI параллельно, но статус остаётся «проверено на fixtures».
4. При несовпадении контракта сообщить конкретное поле, producer/consumer и совместимый вариант. Нельзя добавлять доверенную роль, скрытый auto-confirm, фиктивный success или bypass auth.
5. Реализовать минимально полный сценарий со всеми отказами, перечисленными в задаче. Не переименовывать весь проект и не обновлять зависимости без причины.
6. Выполнить проверки затронутого слоя. Для SQL нужны PostgreSQL/миграции; для UI - реальная сеть или явно отмеченные fixtures; для MAX - реальный клиент отдельно.
7. В передаче указать файлы/контракт/миграцию/команду/результат/предел. Командные `docs/memory/PROJECT_STATE.md`, `DECISIONS.md`, `HANDOFF.md` обновляет интегратор после включения работы; личная долговременная память остаётся только в Obsidian по AGENTS.md.
8. Рабочие обращения сохранять: пользователь подтвердил «убрать заглушки, записи сохранить». `scripts/check_miniapp.py` создаёт отдельный временный Compose-проект для real API QA. Не выполнять seed/очистку/опасные сбои в рабочей БД ради теста и не коммитить реальные профили, PNG, дампы или credentials.

## Промпт Семёна

```text
Ты работаешь над КОРНЕМ в роли backend-разработчика Семёна. Прочитай AGENTS.md,
docs/README.md, docs/memory/PROJECT_STATE.md, docs/team/semyon.md,
docs/domain.md, docs/api.md и contracts/README.md. Выполни задачу S-XX из
актуального плана, предварительно проверив её зависимости и существующий код.
Используй Java как владельца состояния и PostgreSQL; Python только подсказывает.
Проследи авторизацию, версии, идемпотентность и сбои. Изменения контрактов
согласуй с потребителями и обнови примеры/тесты. Не открывай небезопасные endpoints.
Заверши доказательством на реальных компонентах; явно перечисли пропуски и
передай Кириллу/Софии конкретные входы для интеграции. Не заявляй готовность MAX
по mock-тесту. Не публикуй секреты и не делай внешних действий без поручения.
```

Заменить S-XX реальным ID. Если задача уже выполнена, проверить доказательство и не писать вторую реализацию.

## Промпт Кирилла

```text
Ты работаешь над КОРНЕМ в роли frontend-разработчика Кирилла. Прочитай AGENTS.md,
docs/team/kirill.md, docs/design.md, docs/screens.md, docs/api.md и состояние проекта.
Выполни K-XX. Следуй текущему docs/design.md и runtime-компонентам: PNG 22.09
исторические; актуальный ДомПульс по assets/boards пользователя и runtime-компонентам
выше старых макетов. Не имитируй функции макетов без согласованного API.
Каждую кнопку свяжи с согласованной командой, каждый статус - с серверным полем.
Реализуй loading/empty/denied/conflict/unknown-outcome/manual, обе темы и доступность.
Не импортируй демонстрационный app.js как продуктовую бизнес-логику; не используй
localStorage для прав или реальных текстов. Не показывай успешное сохранение до
ответа сервера. Если API отсутствует, явно отдели fixtures и передай блокер Семёну.
Проверь сборку и сценарии, приложи реальные результаты. Отдели fixture UI от
настоящего Java/PostgreSQL API и от живого MAX. Не выдавай макет за продукт.
```

## Промпт Софии

```text
Ты работаешь над КОРНЕМ в роли тестировщика Софии. Прочитай AGENTS.md,
docs/team/sofia.md, docs/acceptance.md, docs/testing.md, docs/screens.md и состояние.
Выполни Q-XX на точном SHA. Проверь основной путь, чужие права, старые версии,
повторы, частичный отчёт, отказ ML/сети и доступность MAX mobile/web.
Записывай шаги/ожидание/факт/среду; NOT_RUN и BLOCKED не считать PASS.
Дефект содержит воспроизводящий пример без секретов, ожидаемый инвариант,
владельца и серьёзность. Не исправляй реализацию так, чтобы тест повторял ошибку.
Передай независимое заключение готовности и список обязательных блокеров.
```

## Формат завершения задачи

```text
ID / владелец / ветка / проверенный SHA:
Пользовательский результат:
Изменённые контракты и миграции:
Команды проверки и фактический результат:
Что не проверено и почему:
Оставшийся риск / следующий ID:
```

Не писать «всё работает», когда запускалась только сборка. Совпадение верстки с PNG не проверяет доступ и данные. Наличие старого зелёного CI не подтверждает новый commit.
