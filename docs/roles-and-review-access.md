# Самостоятельная проверка организаторами: роли и доступ

## Реализованное ограниченное решение - 30.09

По прямому разрешению пользователя реализованы отдельные одноразовые приглашения роли DISPATCHER для новых учебных домов. Оно заменяет необходимость присутствия команды при проверке, если у организаторов есть **три разных MAX-аккаунта**. Подробный прежний проект переключения трёх режимов одним аккаунтом ниже остаётся НЕ реализованным.

Оператор создаёт `seed_stand.py house "Учебный дом проверки N-А (тестовые данные)" --review`, отдельный Б и три приглашения: `invite HOUSE_A --role RESIDENT`, `invite HOUSE_A --role DISPATCHER`, `invite HOUSE_B --role RESIDENT` (до 30 дней). Для выдачи DISPATCHER на стенде требуется `REVIEW_INVITATIONS_ENABLED=true`; обычный дом не допускает такую выдачу даже при включённом флаге. Приглашение одноразовое, хранится только SHA-256. Выданное членство не истекает вместе с кодом, отзыв - операторская команда. Приватный комплект содержит несколько независимых наборов; коды нельзя расходовать техническими тестами.

Каждый участник открывает https://max.ru/t109_hakaton_max_bot?startapp, входит своим аккаунтом, в «Доступ к дому» вводит только свой код набора. После claim `/me` определяет интерфейс. Житель А создаёт свет + дверь; диспетчер принимает, сохраняет отчёт и явно связывает его только со светом; автор подтверждает свет, итог 1 из 2; житель Б не видит чужое обращение. EXECUTOR-кабинет отсутствует, для третьей роли используется настоящий RESIDENT другого дома. Не выдавать это за проверку физического MAX, пока организаторы/команда не прошли её сами.

Обновлено: 29.09.2026. Организаторы получают проект и презентацию через Яндекс Диск, проверяют без команды. Поэтому ручное назначение каждого организатора после начала проверки не подходит. Ниже - выбранный план доработки. Автономный вход/переключение ролей пока НЕ реализованы; текущие назначения команды проверены отдельно.

## Выбранное решение

В комплект сдачи добавить приватные коды проверки. Каждый код открывает отдельный учебный полигон с двумя домами и позволяет проверяющим переключать три режима через настоящий Java API. MAX-аутентификация обязательна; аккаунты не подменяются. Данные создаются обычными продуктовыми формами и хранятся в PostgreSQL.

Кирилл/Семён заранее выпускают набор кодов и комплект сдачи. Во время проверки роли выдаёт Java по проверенному коду и серверной записи полигона. Никаких SSH-команд, согласования MAX userId в переписке или передачи чужого аккаунта организаторам не требуется.

Код проверки - отдельная ограниченная capability. Обычное приглашение жильца сохраняет прежнее правило: только RESIDENT. Обычные /memberships/claim и ID домов не становятся способом получить DISPATCHER. Один код проверки относится только к своей паре учебных домов; он не даёт доступа к домам команды и реальным домам.

## Действия организатора

1. Открыть из комплекта «Начать проверку.pdf». Внутри: прямой бот `https://max.ru/t109_hakaton_max_bot`, запуск Mini App `https://max.ru/t109_hakaton_max_bot?startapp`, HTTPS `https://hackathon.lumnex.ru/`, код полигона, поддерживаемые роли, порядок проверки и зафиксированные SHA.
2. Войти своим MAX-аккаунтом, открыть приложение, выбрать «Проверить проект», вставить код из PDF. Голая ссылка на HTTPS в обычном браузере не заменяет подписанный MAX-вход.
3. Java проверяет код/срок/предел участников, присоединяет аккаунт к нужному учебному полигону и открывает режим «Автор». На экране постоянно написано «Учебный полигон, данные тестовые».
4. Создать обращение «свет + дверь», подтвердить два пункта, сохранить его номер/ссылку. Не нужны готовые обращения или фиктивные MAX-пользователи.
5. Выбрать «Диспетчер». Сервер реально меняет роль только в учебном доме А; открываются очередь, приём, следующий шаг, отчёт и явная связь отчёта с пунктом. Сам выбор текста/кнопки на клиенте ничего не разрешает.
6. Добавить отчёт только о свете и подтвердить связь только со светом. Вернуться в «Автор», подтвердить восстановление света. Ожидание: 1 из 2, дверь остаётся.
7. Выбрать «Посторонний»: доступ этого аккаунта к дому А отзывается, он становится жителем учебного дома Б. Перейти по сохранённой ссылке на А. Ожидание: закрытая карточка/404, никакого текста или истории А из старого cache.
8. Вернуться в «Автор» и продолжить то же обращение. Переключение не удаляет обращения/историю и не создаёт новый раунд работы.
9. Новый MAX-запуск должен восстановить тот же полигон/режим. Код допускает повторный вход того же участника, не расходуется как одноразовое приглашение жильца.

Для независимого одновременного сценария два-три организатора используют один код полигона, каждый со своим MAX-аккаунтом. Первый выбирает «Автор», второй «Диспетчер», третий «Посторонний». Коды разных полигонов разделяют группы: первая группа не меняет роли/обращения второй. Каждый участник меняет только свой режим.

Один аккаунт позволяет пройти основной продуктовый цикл и отзыв доступа к дому. Он НЕ доказывает изоляцию между двумя авторами в одном доме, межаккаунтную доставку уведомлений и полный трёхаккаунтный G2. Это прямо указать в PDF; такие пункты проверять несколькими настоящими аккаунтами. Смена роли не меняет case.authorId.

## Режимы и фактические права

| Режим проверки | Membership дома А | Membership дома Б | Что проверять |
|---|---|---|---|
| Автор | RESIDENT | Отозван/отсутствует | Своё обращение, список проблем, история, собственное наблюдение и отзыв |
| Диспетчер | DISPATCHER | Отозван/отсутствует | Подтверждённые обращения А, приём, следующий шаг, отчёт, явная связь, архив пункта |
| Посторонний | Отозван/отсутствует | RESIDENT | Отсутствие доступа к А; свои обычные обращения в Б |

«Автор» - отношение к обращению, «посторонний» - проверочная ситуация; отдельных enum AUTHOR/STRANGER нет. Технический оператор - обязанность Кирилла/Семёна, а не публичная роль ADMIN.

EXECUTOR есть в SQL, но назначенные ему пункты/кабинет/отчёт от исполнителя в действующем API отсутствуют. Выдавать эту роль с обещанием готового кабинета нельзя. Обязательный MVP проверяется через автора и диспетчера. Если в презентации обещан самостоятельный исполнитель, убрать обещание либо отдельно полностью реализовать его доступ/команды/приёмку; переключатель ролей этого не исправит.

## Семёну: минимальная реализация в существующем Java backend

Не делать отдельный сервис/вторую БД или универсальную систему ролей. Использовать проверенную сессию MAX, CSRF, JdbcTemplate/транзакции, существующую таблицу Membership и продуктовые CaseService-команды.

1. Новая неизменяемая миграция (после актуального V11 - согласовать следующий номер) хранит: полигон с двумя houseId; коды доступа SHA-256, срок, предел участников и блокировку; участников с userId из серверной сессии, режимом и версией. House UUID полигона берётся только из серверной записи, не из тела запроса. Два дома создаёт оператор при выпуске комплекта, без фиктивных пользователей/обращений.
2. Ограничить feature отдельным серверным флагом по умолчанию false. Включается только для согласованного учебного стенда. Перед выпуском проверить, что дома принадлежат именно полигону, А/Б различны и ни один дом не используется обычной командной/реальной Membership. Не считать TRAINING_MODE фронтенда серверной защитой.
3. Коды с достаточной случайностью, raw только в приватном комплекте. Не писать код в URL, Git, логи, аналитику или браузерный storage. Сделать пачку независимых полигонов на случай параллельных групп. Для одного полигона код повторно используется его участниками; предел новых участников проверяется атомарно, повтор существующего не увеличивает счётчик. Ограничить попытки ввода кода.
4. Предлагаемые, ещё не существующие операции: POST /api/v1/review/access/claim (код, без userId/role/houseId); GET /api/v1/review/session; POST /api/v1/review/mode (режим и expectedVersion). Описать в общем контракте и обновить типы потребителя. Все операции требуют настоящую сессию; POST также CSRF. Без feature/кода/участия права не выдаются.
5. Claim повторяемый для того же пользователя/кода. В одной транзакции проверить действующий код, добавить участника и Membership начального режима. Не переинициализировать его режим/данные при повторном входе. Недоступный код отвечает общей безопасной ошибкой без раскрытия полигона.
6. Mode меняет только Membership текущего пользователя в двух домах его полигона по фиксированной таблице выше. Сначала права/актуальность/версия, затем атомарно обе Membership и режим. Не менять другие дома/пользователей, authorId, workRound, содержание, состояния ремонта или историю обращений. Повтор команды безопасен; конфликт версии - 409, неизвестный сетевой исход восстанавливается GET session. Смена режима журналируется с прежним/новым режимом, actor, workspace и временем, без raw кода.
7. Срок доступа должен быть серверным ограничением действующих прав, а не только истечением кода для новых участников. Минимальный вариант - nullable expires_at у Membership, проверяемый во ВСЕХ запросах активного членства (CaseRepository, списки, /me, справочник диспетчеров, повторные проверки ML, sender перед доставкой и идемпотентные команды). Обычные Membership без срока сохраняют поведение. После истечения нельзя продлить доступ простым новым входом или mode. Одного фонового отзыва недостаточно для точного срока; SQL/серверное время остаётся источником истины. Прежде выбрать общий срок с запасом на фактическую проверку организаторов; не назначать 5 минут или срок до ближайшего коммита.
8. Подготовить операторскую команду выпуска/проверки/отзыва полигона, не публичный endpoint раздачи любых ролей. Секретные параметры вводятся безопасно, код показывается один раз. Данные участников/обращений не удаляются при переключении/отзыве. Последующие обновления контейнеров сохраняют полигон и права.

При реализации срока Membership найти все SQL-обращения к membership, а не исправить только /me. Новую функцию review нельзя включать до полной реализации авторизации, контрактов и проверки настоящего PostgreSQL. Номера миграций/общий контракт согласовать с владельцем backend.

## Кириллу: UI и комплект, без ручной помощи во время проверки

1. На экране входа/доступа понятная ссылка «Проверить проект». Форма кода отличает его от обычного одноразового приглашения. Ошибки: неверный/истёкший код, исчерпанный доступ, потеря сети, необходимость нового MAX-входа. Никаких общих логинов/паролей.
2. Панель трёх режимов показывается только когда сервер вернул проверенное review-участие. Названия простые, роль/дом выводятся из API. После mode перечитать /me и review/session; очищать cache прежних карточек/отчётов/истории/списков и несохранённое состояние с предупреждением. Не показывать старые данные автора в режиме постороннего. Навигацию/кнопки переключать только после подтверждённого ответа, при ошибке не оставлять блокировку навсегда.
3. Сохранять номер тестируемого обращения для возврата/проверки 404, а не копию его приватного содержимого. При переключении сначала сохранить или явно отказаться от черновика. Дом режима берётся из API полигона; пользователь не подставляет UUID для повышения роли.
4. PDF «Начать проверку»: MAX-ссылка/QR, HTTPS, код, три режима, точные кнопки и ожидаемый результат каждого шага. Отдельно один аккаунт/несколько аккаунтов/ограничения телефонов и уведомлений. Не требовать команды SSH, Docker, чтение SQL или обращение к команде для выдачи роли.
5. Яндекс Диск: исходники зафиксированной версии, презентация, PDF проверки с кодами, DATA-API.yaml, пример конфигурации без секретов, инструкция локального запуска. В проектном ZIP не должно быть .env, паролей сервера, токенов MAX/Cloudflare, дампов/реальных данных. Коды проверки отдельно от публичного Git. Доступ к коду ограничен полигоном даже если ссылка на комплект переслана.
6. Сервер оставить доступным на весь согласованный срок проверки, зафиксировать web/backend SHA и проверить ссылки с нового аккаунта. Наличие ZIP/презентации не заменяет работающий Mini App: подписанный вход требует MAX и доступного серверного API. Новый локальный запуск требует собственного токена/настройки MAX; секрет команды не раздаётся.

## Софье/автотестам: критерии завершения

- Новый настоящий MAX-аккаунт получает полигон без команды/ручного изменения БД; существующие дома команды недоступны.
- Три режима реально меняют серверные права; role/houseId/userId из поддельного JSON не расширяют доступ. Чужой workspace/mode, выключенная feature, истёкший доступ и исчерпанный код отклоняются.
- Настоящий Java/PostgreSQL: параллельный первый вход/переключение/повтор после потерянного ответа/409; никаких дублированных участников или частично применённых Membership.
- Один аккаунт: создание/подтверждение, приём/отчёт/связь, наблюдение 1 из 2, переход в постороннего с настоящим 404, восстановление авторского режима без потери карточки.
- Два-три аккаунта одного полигона: разные авторы в А, диспетчер, посторонний Б, настоящие уведомления. Разные полигоны не смешиваются.
- Полигон сохраняется после релиза/перезапуска и нового входа >30 минут; доступ не продлевается после своего срока. Cache не показывает прежнее содержимое после потери прав.
- Запустить локальный check_miniapp.py и Java/Python/UI checks на изолированном стенде; физический MAX/G2 проверить отдельно. Отказы зависимостей не устраивать на публичном домене.
- Дать PDF человеку, не участвовавшему в разработке: пройти без пояснений команды. Если нужна помощь для получения роли, самостоятельный доступ не принят.
