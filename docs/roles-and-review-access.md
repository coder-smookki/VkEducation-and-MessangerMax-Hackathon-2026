# Роли и доступ организаторов к ДомПульсу

Дата: 29.09.2026. Это схема проведения проверки с существующим API и операторскими командами. Новая панель администратора, автоматическое повышение роли и кабинет исполнителя этим документом не объявляются реализованными.

## Кто выдаёт доступ

На стенде основной ответственный оператор - Кирилл, резервный - Семён. Оператор работает через SSH с серверными инструментами. Это эксплуатационная обязанность команды, а не роль ADMIN внутри Mini App. Организаторам SSH, пароль сервера, токен бота, MAX-аккаунты команды и cookies других пользователей не передаются.

Оператор назначает сотрудника конкретному дому после согласования личности и полномочий. Для реального использования основание - подтверждение ответственного представителя УК; для конкурса - согласованный список проверяющих и учебные дома. Сам факт входа из MAX подтверждает аккаунт, но не право быть диспетчером.

Житель получает отдельное одноразовое приглашение. Оператор выдаёт его через `seed_stand.py invite` и передаёт нужному человеку приватно. Java после погашения создаёт Membership только RESIDENT. UUID дома, username, имя, выбранная в интерфейсе роль и JSON с ролью не являются основанием доступа. У приглашения срок годности и одна успешная активация; Membership после активации не наследует срок приглашения.

## Какие роли существуют сейчас

| Назначение | Выдача | Что действительно разрешено |
|---|---|---|
| Житель, RESIDENT | Подписанный MAX-вход + отдельное приглашение | Создавать свои обращения в подключённом доме, подтверждать свой список проблем, читать свои карточки, наблюдать свой результат, отзывать свой пункт с причиной |
| Диспетчер, DISPATCHER | Только явное серверное назначение оператором существующему MAX-аккаунту в конкретном доме | Читать подтверждённые обращения своего дома, принимать их, задавать следующий шаг, создавать отчёты, подтверждать связи с пунктами, архивировать пункт с причиной |
| Исполнитель, EXECUTOR | Значение предусмотрено схемой, но отдельный рабочий кабинет/назначенные пункты и ввод отчётов исполнителем сейчас не реализованы | В действующем API только действия автора своего обращения. Для конкурсного MVP эту роль не выдавать как готовое рабочее место |
| Автор | Отдельно не выдаётся | Отношение к конкретному обращению: case.authorId совпадает с проверенным пользователем. Диспетчер тоже может быть автором своего обращения |
| Посторонний | Отдельной роли нет | Житель другого дома или человек без Membership в нужном доме. Он не должен получать чужое обращение; API возвращает 404 |

У Membership одна основная роль в одном доме. Один аккаунт может быть жителем дома Б и диспетчером дома А. Повышение в А не даёт полномочий в Б. Диспетчер не подтверждает физическое восстановление за другого автора; Python не выдаёт роли и не меняет права.

## Как подготовить организаторам проверку

1. Кирилл заранее согласует время проверки, участников и то, кому нужны действия диспетчера. Достаточно двух MAX-аккаунтов для автора/диспетчера; для отдельной проверки изоляции нужен третий. Один человек может проверить большую часть функций, но это не доказательство взаимодействия разных аккаунтов.
2. Создать отдельную пару домов «Учебный дом комиссии А» и «Учебный дом комиссии Б». Имеющиеся дома команды и её обращения сохранять. Лучше отдельная пара на каждую независимую группу, чтобы проверки не мешали друг другу.
3. Организаторы открывают `https://max.ru/t109_hakaton_max_bot?startapp` со своих настоящих MAX-аккаунтов. HTTPS Mini App - `https://hackathon.lumnex.ru/`. Первый вход создаёт серверного пользователя, но ещё не Membership.
4. Оператор сопоставляет конкретные проверенные MAX userId с согласованными участниками. Источник - серверная учётная запись/проверенный MAX update, а не присланное имя или роль. Если сопоставление неясно, не повышать первый или последний вошедший аккаунт. Нужен явный контакт с проверяющим.
5. Автору выдать новый одноразовый код дома комиссии А, постороннему - отдельный код дома комиссии Б. Они вводят коды в «Доступ к дому». Одно приглашение на каждый аккаунт; ID дома в поле не вводится.
6. Назначить согласованный аккаунт диспетчера только дому комиссии А. Роль диспетчера не выдаётся обычным приглашением. Готовая операторская команда - `seed_stand.py dispatcher <houseId> <maxUserId>`; человек должен ранее войти через MAX.
7. Все нажимают «Обновить доступ» в разделе доступа и проверяют «Профиль» → «Мои дома и роли». Сам новый MAX-вход не обязателен для смены роли: Membership проверяется сервером на каждом запросе, профиль нужно обновить.
8. Оператор сверяет точные назначения и отсутствие лишних прав, фиксирует дату, SHA web/backend и результаты без секретов. Кирилл/Софья подтверждают собственные экраны, затем можно запускать продуктовый сценарий.

Текущий `seed_stand.py check` проверяет фиксированные дома А/Б из seed.json. Его нельзя выдавать за проверку новых домов комиссии. Для них использовать отдельный приватный seed.json/account mapping с тем же проверенным скриптом в отдельном рабочем каталоге либо точное чтение Membership по их идентификаторам. Не переписывать канонический seed в Git и не считать дополнительные согласованные дома ошибкой проверяющего скрипта.

## Операторские команды, которые уже существуют

В защищённой SSH-сессии выбрать именно release project. Рабочий каталог должен содержать проверенные scripts/seed_stand.py и scripts/seed/seed.json; на текущем сервере для подготовки использован `/home/smokkkkiiii/koren-seed`.

```sh
export COMPOSE_FILE=/srv/koren/current/compose.release.yaml
export COMPOSE_PROJECT_NAME=koren-release
export COMPOSE_ENV_FILES=/etc/koren/release.env
cd /home/smokkkkiiii/koren-seed
sudo -E python3 scripts/seed_stand.py house "Учебный дом комиссии А (тестовые данные)"
sudo -E python3 scripts/seed_stand.py house "Учебный дом комиссии Б (тестовые данные)"
```

Каждая команда выводит новый houseId. Затем использовать фактически выданные ID и согласованные MAX userId, а не копировать шаблоны как реальные данные:

```sh
sudo -E python3 scripts/seed_stand.py invite <houseId_A> --count 1 --days 7
sudo -E python3 scripts/seed_stand.py invite <houseId_B> --count 1 --days 7
sudo -E python3 scripts/seed_stand.py dispatcher <houseId_A> <maxUserId_dispatcher>
```

`apply` тоже умеет назначать диспетчера, но создаёт недостающие приглашения; для одного повышения предпочтительнее адресная команда dispatcher. При повторном аудите accounts.private.json нужно подготовить заново из согласованного списка: после успешной командной проверки он удалён. `check` сам роли не назначает.

## Что организаторы должны проверить

1. Автор в А создаёт «не горит свет + не закрывается дверь», исправляет/подтверждает два пункта. Сохраняются исходный текст, номер, история и версии.
2. Диспетчер в А видит подтверждённое обращение, принимает, задаёт следующий шаг. Автор видит фактическое обновление. Чужой черновик диспетчеру не раскрывается.
3. Диспетчер добавляет отчёт только про свет и отдельно связывает его именно с пунктом света. Сохранение отчёта само не создаёт связь и не закрывает пункты.
4. Автор подтверждает восстановление только света. Итог - 1 из 2, дверь остаётся. Отчёт и подсказка RULES не являются подтверждением ремонта.
5. Другой автор в А не читает чужую карточку; житель Б не читает и не меняет обращение А. Само наличие роли жителя не открывает все обращения дома.
6. Проверить настоящие MAX-уведомления/кнопку и сохранение доступа после нового входа. Автотест Chromium не заменяет эту проверку.
7. Повторы команд, устаревшие версии, недоступность анализа и остальные условия проверяются по актуальной QA-инструкции. Не имитировать сбои на публичном домене; такие проверки проходят в изолированном полигоне.

## Завершение и отзыв прав

До выдачи прав согласовать срок проверки и ответственного за отзыв. Сейчас у Membership нет expires_at; автоматически истекает код приглашения, а не роль. Временный срок роли пока обеспечивается оператором, не таймером приложения.

После подтверждения окончания проверки оператор отзывает только Membership участников комиссии в её домах через revoked_at, сохраняя пользователей, обращения, историю и данные команды. Выполнять адресно, с явным согласованием; не очищать всю БД. Перед отзывом сохранить проверяемый список назначений без токенов. После отзыва проверить отсутствие домов в /me и закрытый доступ к карточкам. Новое приглашение жильца восстанавливает только RESIDENT, прежний диспетчер автоматически не возвращается.

Публичного API управления ролями и команды revoke у seed_stand.py нет. Для текущего MVP отзыв - контролируемая серверная операция с точным userId/houseId и записью в эксплуатационный журнал. Самовыдача повышенных ролей и выбор «я диспетчер» без проверки не нужны.

## Небольшое улучшение перед самостоятельной проверкой

Кириллу полезно добавить в «Профиль» копируемый «Код пользователя для оператора» из уже проверенного /me.userId. Это идентификатор обращения к оператору, не приглашение и не секрет авторизации. Семёну - адресную операторскую команду назначения/отзыва по этому UUID с проверкой существования аккаунта и журналом изменения. Тогда проверяющим не нужно искать MAX userId или пользоваться инструментами разработчика. Эти два улучшения пока не реализованы; действующий путь выше использует проверенные MAX userId и существующую команду.

Полноценную панель управления сотрудниками, автоматический срок повышенной роли, приглашения сотрудника с подтверждением УК и кабинет исполнителя добавлять после конкурса с отдельными контрактами/объектной авторизацией/аудитом, а не как обход действующих проверок.
