# Правила предметной области

Источник концепции: PDF v2, стр. 11-12 и 18. Это правила КОРНЯ, не спецификация MAX API.

## Четыре независимых факта пункта

| Факт | Значения | Кто имеет право менять |
|---|---|---|
| Содержание | category, location, symptom, contentVersion | Автор в DRAFT; после CONFIRMED в обязательном MVP состав зафиксирован |
| Работы | `NOT_ASSIGNED`, `PLANNED`, `REPORTED_DONE` | Уполномоченный сотрудник, после проверки назначения и подтверждения связи |
| Наблюдение | `NOT_RECEIVED`, `RESTORED`, `PERSISTS`, `CANNOT_CHECK` | Только автор этого обращения |
| Административное решение | `ACTIVE`, `ARCHIVED`, `WITHDRAWN` | Диспетчер для архива; автор для отзыва; требуется причина |

`REPORTED_DONE` означает содержание отчёта о работах, а не доказанный физический эффект. `RESTORED` - наблюдение автора, а не техническая экспертиза. `ARCHIVED` не меняет наблюдение. `WITHDRAWN` не считается выполнением.

В существующем enum `NOT_ASSIGNED` означает исходное состояние без принятого сообщения о работах. Будущее назначение executor хранится отдельно и само не создаёт report/раунд. В UI показывать «Нет сведений о работах» и отдельного назначенного исполнителя, а не выводить отсутствие назначения из этого WorkStatus.

## Версии

Перед подтверждением предложения проходят уровни NEEDS_DETAILS и READY_FOR_REVIEW: это заполненность category/location/symptom, а не состояние ремонта. Только авторская команда Java переводит весь текущий список из DRAFT в CONFIRMED. Пункты, предложенные моделью, имеют временный proposalId; сохранённый itemId назначает Java. [Пять контрактов](../contracts/README.md).

- `sourceRevision`: версия исходного текста обращения; нужна для актуальности предложения модели.
- `contentVersion`: версия category/location/symptom конкретного пункта; исправление требует нового подтверждения.
- `workRound`: раунд сведений о работах по конкретному пункту; до работ 0, далее положительное число.
- `version`: optimistic lock текущей строки/агрегата в БД; правила увеличения для обращения и пункта указаны ниже.

В целевом HTTP это `caseVersion` для обращения и `itemVersion` для пункта. Каждая успешная команда обращения увеличивает caseVersion; изменение/подтверждение конкретного пункта также увеличивает его itemVersion. У запроса явные expectedCaseVersion/expectedItemVersion. Подробная транзакционная политика - [implementation.md](implementation.md).

Сохранение текста отчёта не меняет пункт. Только подтверждённая диспетчером новая связь отчёта с пунктом создаёт workRound и сбрасывает актуальную проекцию наблюдения в `NOT_RECEIVED`; прежнее наблюдение остаётся в истории. Контракт callback связывает actor + item + contentVersion + workRound и ожидаемую itemVersion. Ранее не применённый callback старого контекста не подходит к новому.

Повтор той же команды с тем же Idempotency-Key возвращает прежний результат только после повторной проверки прав. Новая корректировка автора - другая команда с актуальной version, даже если contentVersion/workRound прежние. Так повтор доставки не смешивается с поздним изменением наблюдения.

## Расчёт прогресса

`confirmed` - число неотозванных пунктов с актуальным положительным наблюдением автора.
`withdrawn` - число отозванных пунктов. `remaining = total - confirmed - withdrawn`.
`allConfirmed = total > 0 && confirmed == total`. Поле `remaining` не означает «доказанно не отремонтировано»; это активный/архивный остаток без положительного наблюдения.

Пример: один подтверждён и один отозван → `total=2, confirmed=1, withdrawn=1, remaining=0, allConfirmed=false`. Нельзя исключить отзыв из знаменателя и сообщить полное выполнение.

Архивированный пункт с уже положительным наблюдением сохраняет этот факт. Сам архив никогда не создаёт положительное наблюдение. Отказ выполнять работу или перенаправление требуют объяснения, но не являются `REPORTED_DONE`.

## Действия и отказы

| Событие | Требования | Эффект |
|---|---|---|
| Подтверждение списка | Автор, текущая редакция, непустые пункты | Зафиксировать подтверждённое содержание |
| Сохранение отчёта | Сотрудник, полномочия/назначение, допустимые targetItemIds | Неизменяемый текст и область разбора, без изменения раундов |
| Подтверждение связи отчёта | Диспетчер дома, текущий контекст, только перечисленные допустимые itemId | Новый раунд затронутых пунктов, сброс актуального наблюдения |
| AFTER_REPORT observation | Автор, точные версия/раунд, workStatus=REPORTED_DONE | Запись события, новая проекция наблюдения |
| INDEPENDENT observation | Автор, точные версия/раунд | Наблюдение без изменения статуса работ |
| Устаревший callback | Версия или раунд не совпадает | 409, показать актуальную карточку |
| Повтор идентичной команды | Авторизованный тот же актор и совпадающий hash | Прежний результат без второго события |
| ML-предложение | Полный набор актуальных IDs, evidence, модель и sourceRevision | Только предложение; рабочие поля неизменны |
| Архив/отзыв | Соответствующие права, причина | Административное решение без фиктивного успеха |

`ItemState` реализует лишь базовую проекцию и защиту наблюдения/смены раунда. Он не является системой аутентификации, persisted event store или готовым API. Остальные правила реализуются в S1-S6 и проверяются через реальные транзакции.

## Матрица доступа целевого API

| Действие | RESIDENT | DISPATCHER | EXECUTOR | Python |
|---|---|---|---|---|
| Читать обращение | Своё | Подтверждённое своего дома или своё | Назначенные ему пункты или своё как автору | Только переданный контекст |
| Создать/подтвердить пункты | Для себя в разрешённом доме | Только как автор своего обращения | Только как автор своего обращения | Только предложение через 01; сохранять/подтверждать нельзя, извлечение пока STUB |
| Ввести отчёт | Нет | Своего дома | По назначению | Нет |
| Подтвердить связь отчёта | Нет | Своего дома | Нет в MVP | Нет |
| Наблюдать результат | Только своё | Только если сам автор | Только если сам автор | Нет |
| Архивировать | Нет | Своего дома, с причиной | Нет | Нет |
| Отозвать | Своё, с причиной | Только своё как автор, с причиной | Только своё как автор, с причиной | Нет |

Авторство и роль проверяются отдельно. В MVP один основной role на Membership; авторство не выводится из role. Повышение роли выполняется контролируемым серверным назначением, не self-service.

DRAFT видит только автор. Исполнитель получает урезанную проекцию назначенных пунктов без исходного общего текста, полной истории и progress всего обращения. После CONFIRMED обычная правка текста/состава отклоняется; ошибочный пункт можно отозвать с причиной. Сложный согласованный пересмотр принятого обращения относится к расширению и не считается готовой функцией. [Контракт доступа](api.md).
