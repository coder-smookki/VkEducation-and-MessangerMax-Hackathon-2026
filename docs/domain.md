# Правила предметной области

Источник концепции: PDF v2, стр. 11-12 и 18; действующие правила сверены с Java 27.09.2026. Это правила КОРНЯ, не спецификация MAX API. Проектные расширения явно отделены от работающего MVP.

## Четыре независимых факта пункта

| Факт | Значения | Кто имеет право менять |
|---|---|---|
| Содержание | category, location, symptom, contentVersion | Автор в DRAFT; после CONFIRMED в обязательном MVP состав зафиксирован |
| Работы | `NOT_ASSIGNED`, `PLANNED`, `REPORTED_DONE` | Диспетчер дома при явном подтверждении связи отчёта с пунктом |
| Наблюдение | `NOT_RECEIVED`, `RESTORED`, `PERSISTS`, `CANNOT_CHECK` | Только автор этого обращения |
| Административное решение | `ACTIVE`, `ARCHIVED`, `WITHDRAWN` | Диспетчер для архива; автор для отзыва; требуется причина |

`REPORTED_DONE` означает содержание отчёта о работах, а не доказанный физический эффект. `RESTORED` - наблюдение автора, а не техническая экспертиза. `ARCHIVED` не меняет наблюдение. `WITHDRAWN` не считается выполнением.

В существующем enum `NOT_ASSIGNED` означает исходное состояние без принятого сообщения о работах. Будущее назначение executor хранится отдельно и само не создаёт report/раунд. В действующем UI показывать «Нет сведений о работах». Если появится назначение исполнителя, отображать его отдельным фактом, а не выводить отсутствие назначения из этого WorkStatus.

## Версии

В контракте предложений перед подтверждением используются уровни NEEDS_DETAILS и READY_FOR_REVIEW (автоматические extract/clarify ещё не подключены к UI): это заполненность category/location/symptom, а не состояние ремонта. Только авторская команда Java переводит весь текущий список из DRAFT в CONFIRMED. Пункты, предложенные моделью, имеют временный proposalId; сохранённый itemId назначает Java. [Пять контрактов](../contracts/README.md).

- `sourceRevision`: версия исходного текста обращения; нужна для актуальности предложения модели.
- `contentVersion`: версия category/location/symptom конкретного пункта; исправление требует нового подтверждения.
- `workRound`: раунд сведений о работах по конкретному пункту; до работ 0, далее положительное число.
- `version`: optimistic lock текущей строки/агрегата в БД; правила увеличения для обращения и пункта указаны ниже.

В действующем HTTP это `caseVersion` для обращения и `itemVersion` для пункта. Каждая успешная команда обращения увеличивает caseVersion; изменение/подтверждение конкретного пункта также увеличивает его itemVersion. У запроса явные expectedCaseVersion/expectedItemVersion. Подробная транзакционная политика - [implementation.md](implementation.md).

Сохранение текста отчёта не меняет пункт. Только подтверждённая диспетчером новая связь отчёта с пунктом создаёт workRound и сбрасывает актуальную проекцию наблюдения в `NOT_RECEIVED`; прежнее наблюдение остаётся в истории. Контракт callback связывает actor + item + contentVersion + workRound и ожидаемую itemVersion. Ранее не применённый callback старого контекста не подходит к новому.

Повтор той же команды с тем же Idempotency-Key возвращает прежний результат только после повторной проверки прав. Новая корректировка автора - другая команда с актуальной version, даже если contentVersion/workRound прежние. Так повтор доставки не смешивается с поздним изменением наблюдения.

## Расчёт прогресса

`confirmed` - число неотозванных пунктов с актуальным положительным наблюдением автора.
`withdrawn` - число отозванных пунктов. `remaining = total - confirmed - withdrawn`.
`allConfirmed = total > 0 && confirmed == total`. Поле `remaining` не означает «доказанно не отремонтировано»; это активный/архивный остаток без положительного наблюдения.

Пример: один подтверждён и один отозван → `total=2, confirmed=1, withdrawn=1, remaining=0, allConfirmed=false`. Нельзя исключить отзыв из знаменателя и сообщить полное выполнение.

Архивированный пункт с уже положительным наблюдением сохраняет этот факт. Сам архив никогда не создаёт положительное наблюдение. Отказ выполнять работу или перенаправление требуют объяснения, но не являются `REPORTED_DONE`.

## Действия и отказы

| Событие | Требования | Эффект |
|---|---|---|
| Подтверждение списка | Автор, текущая редакция, непустые пункты | Зафиксировать подтверждённое содержание |
| Сохранение отчёта | Диспетчер дома, допустимые targetItemIds | Неизменяемый текст и область разбора, без изменения раундов |
| Подтверждение связи отчёта | Диспетчер дома, текущий контекст, только перечисленные допустимые itemId | Новый раунд затронутых пунктов, сброс актуального наблюдения |
| AFTER_REPORT observation | Автор, точные версия/раунд, workStatus=REPORTED_DONE | Запись события, новая проекция наблюдения |
| INDEPENDENT observation | Автор, точные версия/раунд | Наблюдение без изменения статуса работ |
| Устаревший callback | Версия или раунд не совпадает | 409, показать актуальную карточку |
| Повтор идентичной команды | Авторизованный тот же актор и совпадающий hash | Прежний результат без второго события |
| ML-предложение | Полный набор актуальных IDs, evidence, модель и sourceRevision | Только предложение; рабочие поля неизменны |
| Архив/отзыв | Соответствующие права, причина | Административное решение без фиктивного успеха |

`ItemState` реализует лишь базовую проекцию и защиту наблюдения/смены раунда. Он не является системой аутентификации, persisted event store или готовым API. Остальные правила реализованы в CaseService, репозиториях и адаптерах S-02..S-07 и проверяются через реальные транзакции.

## Матрица доступа действующего MVP

| Действие | RESIDENT | DISPATCHER | EXECUTOR | Python |
|---|---|---|---|---|
| Читать обращение | Своё в доме с активным членством | Подтверждённое своего дома или своё | Только своё как автору; доступ к назначенным пунктам не реализован | Только переданный контекст |
| Создать/подтвердить пункты | Для себя в разрешённом доме | Только как автор своего обращения | Только как автор своего обращения | Только предложение через 01; сохранять/подтверждать нельзя, извлечение пока STUB |
| Ввести отчёт | Нет | Своего дома | Нет в действующем API | Нет |
| Подтвердить связь отчёта | Нет | Своего дома | Нет в MVP | Нет |
| Наблюдать результат | Только своё | Только если сам автор | Только если сам автор | Нет |
| Архивировать | Нет | Своего дома, с причиной | Нет | Нет |
| Отозвать | Своё, с причиной | Только своё как автор, с причиной | Только своё как автор, с причиной | Нет |

Авторство и роль проверяются отдельно. В MVP один основной role на Membership; авторство не выводится из role. Повышение роли выполняется контролируемым серверным назначением, не self-service.

DRAFT видит только автор с действующим членством. Урезанная проекция назначенных исполнителю пунктов пока не реализована: `assignedExecutorId=null`, `visibility=FULL`. Если она будет добавлена, чужой исходный текст, полная история и progress всего обращения не должны попасть в неё. После CONFIRMED обычная правка текста/состава отклоняется; ошибочный пункт можно отозвать с причиной. Сложный согласованный пересмотр принятого обращения относится к расширению и не считается готовой функцией. [Контракт доступа](api.md).

## Приём и ответственность по пункту

Авторское CONFIRMED означает утверждённое содержание. Приём диспетчером - отдельные acceptedAt/acceptedBy, а квитанция автору - confirmedAt и номер. Эти события не являются работой или наблюдением.

Следующий шаг относится к одному пункту: действие, активный ответственный диспетчер дома и nullable дата следующего обновления. API допускает действующего диспетчера дома; текущий UI указывает себя, так как справочника сотрудников нет. Дата не означает гарантированного ремонта. Изменение шага проверяет caseVersion/itemVersion и фиксирует историю. Архив сохраняет последний план, но не показывает его действующим обещанием. Просроченный updateDueAt означает только истечение даты этого шага; он не доказывает отсутствие более позднего отчёта или наблюдения.

## Административная гранулярность

В обязательном MVP архивируется отдельный пункт с причиной. Полного массового архива обращения нет. Карточка сохраняет все исходные пункты; список без queueState возвращает все доступные обращения с пагинацией. Диспетчер выбирает NEEDS_ACCEPTANCE/NEEDS_ACTION/AWAITING_AUTHOR/ARCHIVED; фильтры пересекаются, так как относятся к фактам разных пунктов. Фильтр архива возвращает доступные карточки с архивными пунктами, не маскируя остальные состояния.

Отзыв разрешён автору своего пункта. Отозванный пункт остаётся в total и истории, не засчитывается в confirmed. Молчание и CANNOT_CHECK не закрывают пункт. После административного решения нельзя создать видимость ремонта заменой текста заголовка или зелёным цветом.

## Роли команды и роли продукта

Семён/Кирилл/София - роли разработки, не значения Membership. Значения схемы: RESIDENT, DISPATCHER, EXECUTOR. «Автор» - отношение `case.authorId == actorId`, не новый enum AUTHOR. EXECUTOR-сценарий расширение; основной пользовательский путь обслуживают автор и диспетчер. Публичный выбор роли и доверие полю role из JSON запрещены.

Членство имеет серверный признак отзыва `membership.revoked_at` (V3). Удаление Membership не является безопасным обходом, поскольку на него могут ссылаться исторические записи. Самостоятельного API выдачи повышенной роли или отзыва членства пока нет; серверное администрирование сохраняет историю. Перед каждым чтением/командой/повтором проверяется актуальное право, а не только membership из старого initData.

Повторное приглашение не является выдачей повышенной роли. Для активного Membership роль сохраняется; при восстановлении отозванного Membership код жильца даёт только RESIDENT, прежний DISPATCHER не восстанавливается автоматически. Погашение кода и запись членства атомарны; при сбое сохраняется возможность корректно использовать код позднее.
