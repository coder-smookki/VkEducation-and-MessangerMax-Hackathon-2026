## Первый час

Запустить `ItemStateTest`, `SuggestionValidatorTest`, `PostgresSchemaTest`. Последний требует `DB_TEST_URL`; без неё он явно пропускается. Прочитать `V1__initial_schema.sql`: схема есть, репозиториев и рабочих HTTP-команд пока нет.

Начать S1 в `cases/application` и `cases/persistence`; использовать Spring JDBC и явные SQL с условием `version`. Не добавлять универсальный Repository/Service для всех таблиц. Транзакцию держит application service. Контроллер не выполняет SQL и не определяет бизнес-переходы.

## Обязательные правила реализации

Авторизовать актора и конкретный ресурс до чтения результата идемпотентного повтора. Ключ привязать к actor + operation + key; различный hash тела с тем же ключом даёт 409. Конкурентный `UPDATE ... WHERE version = :expected` с нулём строк даёт конфликт. Историю, изменение проекции и outbox записывать в одной транзакции.

Вызов Python и MAX нельзя держать внутри транзакции БД. После завершения inference повторно проверить sourceRevision/contentVersion/workRound. Отсутствие evidence, выход за границы Unicode и неизвестный item дают ручной разбор.

Membership проверять не только на списке обращений, но и на отчёте, наблюдении, истории, экспорте и повторе команды. Роль EXECUTOR разрешает отчёт только по назначенным ему пунктам; назначение и соответствующий столбец/таблицу добавить новой миграцией в S2.
