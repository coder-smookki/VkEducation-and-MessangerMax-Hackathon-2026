# Семён - Java Backend и PostgreSQL

План под параллельную работу. Основная оценка 35-44 часа + 8 часов резерва. Все задачи продукта TODO; единый реестр - [plan.md](../plan.md). Критический путь внутри твоей работы: S1 → S2 → S3. UI и ML разрабатываются независимо по контрактам и фикстурам.

## Зона ответственности

`backend/src/main/java/ru/koren/cases/`, `reports/`, `observations/`, `notifications/`, `inference/`, рабочие REST DTO и `backend/src/main/resources/db/migration/`. Кирилл владеет identity/MAX/Frontend; Никита - Python. Ты координируешь номера миграций, включая потребности identity.

До кода прочитать [domain.md](../domain.md), [api.md](../api.md), [implementation.md](../implementation.md) и [сквозной пример](../worked-example.md). V1/V2 и чистые правила уже существуют. Репозитории, use cases, HTTP-команды и workers ещё отсутствуют.

## S0. Контракты, которые разблокируют команду - 2 часа

1. Запустить Java-тесты и `PostgresSchemaTest` на тестовой PostgreSQL. Без `DB_TEST_URL` тесты БД пропускаются, это не успешная проверка DDL.
2. За первый час согласовать с Кириллом C1: серверный actor, Membership, версии, draft DTO, ошибки. Передать пример success и 409 раньше полного CRUD.
3. На основе [api.md](../api.md) передать C2: report/links/observation/progress. Подтвердить с Никитой C3; его текущие JSON-примеры уже работают.
4. С Кириллом описать C4: граница MAX adapter → inbox → domain command → outbox. Он делает транспорт, ты - надёжную обработку и эффект.
5. Использовать готовые `contracts/author-review.openapi.json` и review/confirm-примеры из `contracts/examples/`; это ещё не реализованные endpoints. Дополнять остальные HTTP-фикстуры вместе с тестом/потребителем без второй копии уже согласованных ответов.

Основа 13.09.2026: [пять контрактов](../../contracts/README.md), Java `IntakeContract`/`IntakeValidator` и новые методы `InferenceClient` уже реализованы. Для extract/clarify сверять DRAFT/автора и версии; для similar готовить ConfirmedCaseContext и только доступных кандидатов того же дома. Наличие слова CONFIRMED в присланном JSON не заменяет чтение БД. Вопрос получает только автор, а не все участники Membership.

Приёмка: Кирилл способен строить экран на согласованных данных; Никита понимает snapshot и evidence; ни один участник не ждёт реализации всех твоих задач для старта.

## S1. Реальные черновики и права - 8-10 часов

Можно начать сразу после C1. До готовности K1 тестировать application services с актором из тестовой фикстуры и PostgreSQL. Рабочие HTTP routes открывать только вместе с настоящей авторизацией.

1. В `cases/persistence/` сделать конкретные SQL-операции на Spring JDBC. Контроллер не пишет SQL; application service держит транзакцию. Переиспользовать существующие domain-типы.
2. В одной транзакции создать `service_case` и первую `case_revision`. Составные/отложенные FK должны пройти commit. История и `processed_command` пишутся атомарно.
3. Реализовать чтение своей карточки/списка и фильтрацию Membership. DRAFT видит только автор; диспетчер получает CONFIRMED своего дома; исполнитель - только назначенный контекст. Не фильтровать чужие данные уже после выдачи в DTO.
4. Реализовать изменение sourceText только в DRAFT: новая sourceRevision и expectedCaseVersion. Предыдущая редакция сохраняется.
5. Реализовать замену draft-списка 0-20 пунктов. Новый ID выдаёт сервер; существующий ID обязан принадлежать этому draft. Изменение содержания создаёт item_revision и увеличивает contentVersion; неизменённый пункт не получает фиктивную новую редакцию.
6. До первого confirm можно убрать draft-пункт без рабочих зависимостей; проверять отсутствие report/observation и делать операцию транзакционно. После CONFIRMED физическое удаление/подмена состава запрещены.
7. Confirm проверяет текущий sourceRevision, expectedCaseVersion и непустой валидный список. Установить подтверждение именно текущих item_revision; в той же транзакции изменить submission_status.
8. Реализовать optimistic lock агрегата/пунктов и идемпотентность по [implementation.md](../implementation.md). Одновременный повтор не оставляет лишних строк и не превращается в случайный 500.
9. Совместно с Кириллом подключить нужные HTTP routes и ProblemDetail. GET после login использует тот же внутренний ID; дом/роль из тела не дают прав.

Приёмка: A01/A02/A03/A07/A08 из [acceptance.md](../acceptance.md). Особые случаи: пустой confirm, чужой itemId, 21 пункт, конфликт двух вкладок, дубль create, другой hash при том же key, недоступный дом, отзыв Membership перед replay, rollback между проекцией и историей.

Передача Кириллу: рабочие create/read/source/items/confirm, формы ответа, все версии и один запрос на каждый существенный отказ. Передача Никите: стабильные itemId и смысл contentVersion, без доступа к БД.

## S2. Отчёты, назначения и ручные связи - 6-8 часов

Начало: S1 + C2. Не ждать NLI: диспетчер умеет выбрать связи вручную.

1. Добавить новой миграцией назначение executor на пункт. Назначать может диспетчер того же дома; назначенный пользователь должен иметь роль EXECUTOR в нём. Назначение само по себе не является сообщением о выполнении.
2. Сохранять неизменяемый `work_report` и его разрешённые `targetItemIds`. Автор отчёта - серверный actor. EXECUTOR может перечислить только назначенные ему пункты; DISPATCHER - допустимые пункты своего обращения.
3. POST reports создаёт отчёт и историю, но не workRound/observation. Возможный analysis job добавляется в S4. Отказ Python не откатывает отчёт.
4. POST links принимает только явный набор itemId/contentVersion/expectedWorkRound/workStatus, от диспетчера своего дома. Проверить принадлежность report и каждого item, актуальность, targetItemIds, отсутствие отзыва.
5. Для каждой новой подтверждённой связи вызвать правило нового раунда, записать `report_item_link`, увеличить item version и сбросить актуальное наблюдение. Старые события остаются в истории. Пункты вне links не изменяются.
6. Новый key для уже связанного report/item не создаёт новый раунд - 409 `LINK_ALREADY_EXISTS`. Изменить ошибочный отчёт/связь можно новой подтверждаемой информацией, не переписыванием истории.
7. Добавить ручную историю и DTO для K3. Значения relation модели не копируются автоматически в WorkStatus.

Приёмка: A04/A05/A07. Ответ только про лампу не меняет дверь; PLANNED не даёт AFTER_REPORT-подтверждение; чужой report/item/исполнитель отклоняется; два диспетчера с одной caseVersion не записывают две конкурирующие связи.
Передача Кириллу: назначение, сохранение отчёта отдельно от links, полный пример частичного ответа. Никите: реальные snapshot после сохранения, точный reportText без нормализации.

## S3. Наблюдения и административные решения - 5-6 часов

1. В `observations/` реализовать команду с expectedCaseVersion, expectedItemVersion, contentVersion, workRound. Авторство проверить независимо от текущей роли в Membership.
2. AFTER_REPORT допустим при REPORTED_DONE; INDEPENDENT позволяет сообщить собственное наблюдение без фиктивного отчёта. Значение NOT_RECEIVED не принимается как ответ пользователя.
3. Сохранять каждое новое добровольное наблюдение как событие; текущую проекцию менять вместе с аудитом. Последующее PERSISTS снимает актуальное положительное наблюдение, не удаляя историю RESTORED.
4. ARCHIVE доступен диспетчеру своего дома, WITHDRAW - автору. Непустая причина обязательна; ни одно действие не устанавливает RESTORED/REPORTED_DONE.
5. WITHDRAWN блокирует новые links/observations. Архив допускает поздний факт автора и не создаёт напоминаний. Содержание подтверждённого пункта через эти команды не меняется.
6. Карточка/история возвращают отдельно факты и версии; progress вычислять только `CaseProgress.from`, включая отозванные пункты в total.

Приёмка: A05/A06/A07. Чужой автор, старый callback, устаревшая item version, новый раунд после RESTORED, отрицательная корректировка, архив без причины, один подтверждённый + один отозванный → allConfirmed=false.
Передача Кириллу: допустимые действия и ошибки. Для S5 подготовить тот же application use case, чтобы callback не получил отдельную упрощённую бизнес-логику.

## S4. Надёжный анализ вне транзакции - 5-6 часов

Можно начать на STUB после S2/C3. N2/N3 нужны только для подключения настоящего анализа.

1. Добавить persisted job со snapshot входа и hash, состоянием, попытками и lease. Создание отчёта и job атомарно; UI сразу получает сохранённый reportId.
2. Worker забирает задачу короткой транзакцией, фиксирует token/lease, вызывает существующий `InferenceClient` вне неё и завершает только своё владение.
3. Добавить предел тела ответа до десериализации, ограничение активных вызовов и конечную retry-политику. Не накапливать задачи только в памяти Java.
4. Сохранить `SuggestionValidator` как проверку внешнего контракта: полнота IDs, версии, mode, точное Unicode evidence. Отдельно перечитать БД и проверить snapshot перед сохранением/выдачей READY.
5. Версия/раунд изменились - STALE; временный отказ после попыток - MANUAL_REQUIRED. Неверная схема/evidence не повторяется бесконечно. Принятие человеком всегда идёт через обычный POST links с актуальными версиями.
6. GET suggestions не запускает новые jobs и не меняет состояние обращения. Polling UI читает статус; остановленная модель не делает Java health красным, если обязательная БД доступна.

Приёмка: A09/A10. Реальный HTTP-имитатор даёт timeout, 429/503, повреждённый JSON, огромный/chunked ответ, чужой item и emoji spans. Между отправкой и завершением меняется раунд; старый результат не попадает в актуальные предложения. Рестарт возвращает просроченную lease-задачу к обработке.
Передача Никите: согласованные timeout/concurrency, modelVersion и причина отказа. Кириллу: job status, polling и ручной путь.

## S5. Inbox/outbox и уведомления - 5-7 часов

Начало: S3 и C4. Сеть имитируется локально до K5a; к G2 подключить реальный адаптер Кирилла.

1. В `notifications/` реализовать обработку сохранённого inbox через существующие application services. Проверенный callback повторно авторизует sender/resource, не доверяет payload-кнопке.
2. Добавить непрозрачную ссылку callback с автором, item, contentVersion, workRound, ожидаемой версией пункта и сроком. Повторное действие использует стабильный idempotency key; изменённое тело прежнего ключа не подменяет первый результат.
3. После подтверждённого REPORTED_DONE поставить одно логическое приглашение для автора/пункта/версии/раунда. Состояние, аудит и outbox пишутся вместе; нет сети внутри транзакции.
4. Добавить настройки уведомлений с собственной version. Opt-out, уже полученное наблюдение, архив/отзыв отменяют ожидающее приглашение; перед отправкой проверить актуальность снова.
5. Lease/token, ограниченные повторы, видимый terminal failure и восстановление после падения - по [implementation.md](../implementation.md). Из-за неопределённого результата внешнего HTTP допустима повторная доставка, но не повторный предметный эффект.
6. Не считать взятую из таблицы запись доставленной. sent_at ставится после подтверждённого результата; timeout не превращается в успех.

Приёмка: A11/A12. Падение после inbox ACK, до/после domain commit; падение до фиксации sent_at; два worker; opt-out; просроченный/чужой callback; новый раунд до отправки. Повтор не создаёт второе наблюдение и новый запрос проверки.
Передача Кириллу: статусы доставки и минимальные данные для сообщения. Неподдержанные MAX Update не превращать в команды.

## S6. Интеграционные проверки - 4-5 часов

Это общий резерв на системные проверки, а не повод откладывать тесты S1-S5 до конца.

1. Пройти [acceptance.md](../acceptance.md) через HTTP и настоящую PostgreSQL. Фикстура содержит двух жителей, два дома, диспетчера и исполнителя.
2. Конкурентные запросы выполнять действительно одновременно на отдельных соединениях. Проверять результат обеих команд, версии и число записей audit/outbox, а не только HTTP status.
3. Внести сбой между отдельными стадиями транзакции/worker, перезапустить процесс и проверить конечное состояние. Не заявлять restart safety по unit-тесту одного метода.
4. Проверить чистую миграцию и обновление текущей схемы, затем восстановление тестовой копии в отдельную БД. Не направлять destructive tests в демонстрационный стенд.
5. Подготовить независимые тексты/разметку для N4 до просмотра предсказаний и проверить выводы Никиты. При нехватке времени согласовать меньший фактический набор.
