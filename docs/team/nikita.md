# Никита - ML/AI и доказательство полезности

План под параллельную работу. Основная оценка 29-37 часов + 6 часов резерва. Все задачи продукта TODO; реестр - [plan.md](../plan.md). Для старта не нужны CRUD, MAX и база Java: есть работающие inference-контракт, STUB и синтетический JSONL.

## Зона ответственности

`ml/app/features/inference/`, `ml/app/main.py`, `ml/scripts/evaluate.py`, `ml/data/`, `ml/tests/`, `ml/pyproject.toml`, `ml/uv.lock` и экспорт `contracts/inference.openapi.json`. Java records/общие примеры меняются с Семёном, подписи UI - с Кириллом.

Python не меняет продуктовую БД и не выполняет команды. Техническая ML-БД/векторное хранилище могут хранить аудит и embeddings, но не состояние обращения. Выход модели - интерпретация текста, а не подтверждение ремонта. Базовый путь обходится без генеративного LLM, fine-tuning, RAG и внешнего закрытого датасета.

## Первый запуск

Из `ml/`: `uv sync --frozen`, `uv run pytest -q`, `uv run ruff check .`, `uv run python -m scripts.evaluate`. Команды и окружение - [development.md](../development.md).

Сейчас 7 учебных диалогов и 14 пунктов; analyzer всегда возвращает INSUFFICIENT_INFORMATION. Coverage=0, precision=null. Это проверка связи и инструмента оценки, не результат NLI. Health сейчас жёстко сообщает STUB: при подключении модели нужно изменить реальное состояние, а не только подпись.

## N0. Разметка - 4-5 часов

1. Прочитать [domain.md](../domain.md), [api.md](../api.md) и текущие examples. Разделять содержание отчёта, физический результат и авторское наблюдение.
2. В `ml/data/README.md` при реализации N0 описать единицу разметки: один подтверждённый item + полный ответ исполнителя. У диалога есть id, origin, author, templateGroup и split; у item - label и допустимые точные evidence spans. Не менять существующий JSONL несовместимо без обновления evaluator.
3. Совместно с Кириллом или Семёном разметить первые 10 диалогов, обсудить расхождения и уточнить правила. Затем довести development-набор до целевых 40, если позволяет бюджет; вымышленные данные помечать synthetic.
4. Спорные случаи помечать явно. Не удалять трудные примеры ради роста показателя; отдельно фиксировать disagreement и решение после обсуждения.
5. Не использовать одну перефразированную заготовку как независимые train/dev/test. Вся templateGroup относится к одному split. Исправления опечаток одной истории тоже не новый независимый шаблон.

### Смысл меток

| Relation | Что утверждает текст | Что проверять человеку |
|---|---|---|
| REPORTED_DONE | Сообщается о выполненной работе по этому объекту/месту | Это отчёт, а не физическое подтверждение |
| PLANNED | Намерение/запланированное действие, а не уже выполненное | Будущее время и условия |
| SYMPTOM_PERSISTS | Прямо сказано, что симптом сохраняется | Нельзя потерять «но света нет» после слов о замене |
| INSUFFICIENT_INFORMATION | Достоверной интерпретации для пункта нет | Данных мало или анализ отказался; пункт остаётся видимым |
| UNRELATED | Есть фрагмент о другом объекте/месте | Отсутствие упоминания само по себе не даёт эту метку |
| CONFLICT | В тексте несовместимые утверждения по одному контексту | Это не автоматическое преобразование класса contradiction у NLI |

При сочетании «работу сделали, но симптом остался» использовать SYMPTOM_PERSISTS по согласованной политике. CONFLICT требует именно неразрешимого противоречия, а не двух независимых фактов. Если одного Relation недостаточно, сначала обсудить конкретный пример с Семёном, затем менять контракт обоих потребителей.

Приёмка: версия правил разметки, фактический размер, перечень групп и трудных случаев, проверка вторым человеком. Передача Кириллу - нейтральные русские подписи, Семёну - смысл каждой relation.

## N1. Простой baseline - 3-4 часа

1. Зафиксировать A/B/C: A - ручное сопоставление без подсказок; B - простые правила; C - NLI с той же формой и теми же правами. Ручная форма не получает фиктивный model score.
2. Реализовать B как детерминированные проверяемые правила category/place + явное время/отрицание. Работать с копией текста для поиска; evidence возвращать в координатах исходного текста.
3. Без надёжного совпадения возвращать отказ. Не угадывать этаж/подъезд по первому числу. Каждому входному item соответствует один ответ.
4. Вернуть mode=RULES и конкретный modelVersion правил. Подключение B не должно требовать изменений рабочих статусов в Java.
5. Расширить evaluator так, чтобы разные анализаторы сравнивались по одному протоколу. Результаты сохранять отдельным машинным файлом вместе с версиями, а не только печатать общий процент.

Приёмка: повторяемый B, пример правильного предложения и отказа, те же Java contract tests; метрики отделены от A. Модель не считается полезной только потому, что у STUB coverage=0.

## N2. Одна настоящая NLI-модель - 6-8 часов

Кандидат: [MoritzLaurer/mDeBERTa-v3-base-mnli-xnli](https://huggingface.co/MoritzLaurer/mDeBERTa-v3-base-mnli-xnli). В каркасе веса и Transformers/PyTorch ещё не установлены. Карточка модели не доказывает качество на нашем процессе.

1. Проверить актуальную карточку/лицензию, совместимость Python 3.12, объём весов и доступное железо. Закрепить конкретный revision весов и tokenizer; зависимости записать через uv с обновлением lock. Не добавлять несколько движков до первого замера.
2. Загрузить модель один раз на startup, выполнить прогрев, записать modelVersion и фактический device. Не скачивать веса при каждом запросе и не запускать загрузку после первого действия пользователя.
3. Использовать sequence classification; читать `config.id2label`, не предполагать порядок entailment/neutral/contradiction. Модель в режиме evaluation, расчёт без градиентов. Применимые API сверить с установленной версией. [Transformers: sequence classification](https://huggingface.co/docs/transformers/tasks/sequence_classification).
4. Сначала проверить короткую пару premise/hypothesis, затем небольшой batch. Гипотезы выражают смысл отчёта по данному item, а не доказывают существование ремонта в доме.
5. Контролировать token length до inference. Длинный текст сегментировать с сохранением исходных offsets; если значимый контекст не помещается, отказаться. Тихое обрезание отрицания в конце недопустимо.
6. `/healthz` показывает живой процесс и фактический mode; отдельная готовность к NLI становится успешной только после загрузки/прогрева. При недоступных весах явно STUB/MANUAL либо неготовый NLI, без ложной надписи model ready. Java сохраняет ручной путь.

Приёмка: веса реально запущены, modelVersion воспроизводим, есть положительный и отказной пример на CPU/выбранном device. Запись `mode=NLI` без вызова модели не проходит.
Передача Семёну: request/response C3, startup/readiness, ресурсы и предварительное время одного вызова.

## N3. Evidence и отказ от ненадёжного вывода - 5-6 часов

1. Разбить ответ на кандидаты-фрагменты, сохраняя точные индексы `[start,end)` в Unicode code points. Не вычислять spans после нормализации/перевода/перефразирования.
2. Для каждого item отдельно проверить объект, место и смысл высказывания. Одинаковые слова о другой двери/этаже не подтверждают нужный пункт.
3. Entailment-score использовать как сигнал для нашей политики, не как итоговую Relation без правил. Contradiction у NLI не означает CONFLICT в предметном смысле.
4. В development подобрать порог, минимальный отрыв подходящего кандидата и условия отказа. Все параметры/шаблоны гипотез версионировать вместе с analyzer. Не подбирать по held-out.
5. Для содержательной relation вернуть точный фрагмент. Текущий контракт допускает один непрерывный span: если смысл основан на двух фразах, взять охватывающий их исходный фрагмент либо отказаться. Не склеивать цитату из несмежных частей.
6. Проверить полноту, уникальность, echo версий и STUB/MANUAL без содержательных утверждений. Неверный ответ должен отклоняться Java; такая проверка не заменяет корректный Python-выход.
7. Подключить в S4 и дать Кириллу примеры READY, отказа, UNRELATED, конфликта и emoji evidence. Предложение не вызывает POST links самостоятельно.

Приёмка: отрицание, будущее время, другое место, частичный ответ, сохраняющийся симптом, противоречие, цитата, опечатки, emoji, длинный текст и инструкция модели внутри отчёта. Пользовательский текст рассматривается как данные, не как команды изменить статусы.

## N4. Независимая оценка - 8-10 часов

1. Заморозить analyzer, модель/revision, tokenizer, правила и пороги. Зафиксировать commit, hash dev-набора и процедуру измерения.
2. Кирилл и Семён готовят новые диалоги, не глядя на предсказания. Цель - 60 новых диалогов с отдельными templateGroup. Проверить пересечения/почти-дубликаты с development до анализа результатов.
3. Разметить по зафиксированным правилам; спорные примеры пометить и разрешить независимо от ответа модели. После раскрытия held-out не считать его снова независимым для изменённой настройки.
4. Выполнить B/C на одном наборе. Сохранить по каждому item gold/prediction/evidence/mode/reason и ошибку, агрегаты считать из этого файла.
5. Для A/B/C измерить всё время правильного человеческого разбора: чтение, выбор, проверку и исправления. Уравновесить порядок условий и распределить сопоставимые группы текстов, чтобы повторное чтение не давало ложный выигрыш NLI.
6. Опубликовать примеры ошибок и фактический объём. Если нет пользы относительно B, так и написать; решение о включении принимает команда с учётом требований кейса.

### Что считать

| Показатель | Определение |
|---|---|
| Coverage | Число содержательных ответов, кроме INSUFFICIENT_INFORMATION, / все item |
| Label precision | Верные метки среди содержательных ответов; при нуле ответов null |
| Actionable precision | Верные предложения REPORTED_DONE/PLANNED среди всех таких предложений; отдельно от UNRELATED/CONFLICT |
| Evidence validity | Доля spans, точно соответствующих исходнику; дополнительно человек проверяет смысловую достаточность |
| Ошибки по классам | Confusion counts, отдельно опасное превращение плана/другого места в REPORTED_DONE |
| Время | Человеческое время до правильного результата и доля исправлений; latency модели измеряется отдельно |

Текущий evaluator считает совпадение меток среди всех non-abstention как поле `precision`; он пока не проверяет смысл evidence, раздельную actionable precision или человеческое время. В N4 эти ограничения должны быть устранены, а старое число не переименовано в точность ремонта.

Ориентир из PDF около 0.95 для точности предлагаемых связей - исследовательская цель, не полученный результат. Публиковать числитель/знаменатель и coverage рядом. Несколько десятков диалогов, тем более synthetic, не доказывают production-качество; неопределённость и источник данных указывать.

Планируемые артефакты создаются в N0/N4: `ml/data/README.md`, development/test JSONL, manifest с hashes и `ml/results/` с конфигурацией/агрегатами без личных данных. Сейчас этих результатов нет. Веса не помещаются в Git; текущий ignore для `ml/models/` сохраняется.

## N5. Производительность и перегрузка - 3-4 часа

1. На целевом железе указать CPU/GPU, RAM, число потоков, model/tokenizer revision, batch и token limits.
2. Отдельно измерить cold startup и прогретые запросы; короткий текст, максимальные допустимые items/text и 5 одновременно пришедших задач.
3. Для каждой серии записать число запросов, p50/p95, ошибки/отказы и peak memory. Не смешивать ожидание Java-очереди с Python inference без раздельного отчёта.
4. Python ограничивает одновременно активный inference; лишняя нагрузка получает согласованный 429/503, а не бесконечный threadpool/очередь в RAM. С Семёном подобрать timeout и concurrency по замеру.
5. Если CPU не укладывается в полезное ожидание, сохранить ручной путь и B; оптимизировать batching/размер контекста после профиля. Квантизацию/другую модель проверять как отдельный вариант с повторной оценкой качества.

Приёмка: повторяемая команда/набор нагрузки, фактические числа, отказ при перегрузке, стабильная память и отсутствие влияния на сохранение обращения Java.

## Передача и завершение

Семёну: C3, версии, лимиты, readiness, реальные задержки и ошибки. Кириллу: смысл каждой метки и пример корректного выделения. Команде: manifest, результаты, ошибки, фактическая польза B/C относительно A.

Перед merge выполнить pytest/ruff, экспорт OpenAPI и проверку общих примеров; после изменения C3 - Java и smoke с Семёном. Нельзя менять только Python, оставляя Java на прежней схеме. Коммит - короткий русский заголовок без тела и соавторства; общую память обновляет интегратор после проверки.
