# Кирилл - безопасный RULES и интеграция анализа

Дата: 28.09.2026. Задача K-ML-01 по прямому поручению Кирилла. На время этой задачи Кирилл владеет изменениями RULES, проверками и их согласованной интеграцией в Java/UI. Семён параллельно выполняет [DATA-API](semyon-data-api.md). Не менять одни и те же файлы без передачи работы. Основной backend остаётся Java.

Этот документ содержит порядок реализации и дальнейшего сопровождения. Факт выполнения, метрики и ограничения фиксируются отдельно в [протоколе](../qa/rules-v3-2026-09-28.md); один текст плана не доказывает готовность. Проверки работают на синтетических данных в отдельном локальном полигоне. Они не заменяют G2 на настоящих клиентах MAX.

Последний выполненный повтор и дополнительные исправления - [QA 28.09](../qa/local-playground-2026-09-28.md). Первые FAIL сохранены, frozen challenge не менялся, новые 36 регрессий закрывают четыре найденных класса ошибок. Дальнейшую работу начинать с этого актуального среза, не с исторических 159 Python tests первоначального протокола.

## 1. Что именно исправляем

RULES сопоставляет текст сохранённого отчёта с конкретными пунктами обращения. Это детерминированный анализатор текста, а не обученная модель и не доказательство физического ремонта.

Ошибки прежней v2:

- Условие «Если лампу заменили, сообщите диспетчеру» становилось `REPORTED_DONE`.
- Вопрос «Лампу заменили?» и условное наклонение «заменили бы» считались выполненной работой.
- Процитированный или опровергнутый старый отчёт превращался в текущий факт.
- «Замечаний не поступало» ошибочно отрицало соседнее «освещение восстановлено».
- Этаж `2-м` не распознавался как другой этаж; отрицательный адрес и контекст между предложениями терялись.
- Неуточнённое «лампу заменили» привязывалось сразу к двум пунктам об освещении на разных этажах.
- Сохранённый ответ старой модели мог оставаться видимым после выключения анализа. Кэш UI мог показывать прежнюю подсказку после неудачного обновления.

Нельзя исправить только строку с «если» и считать задачу законченной. Нужно проверить утверждение, объект, место, область отрицания и контекст; затем сохранить безопасное поведение на всех границах Python → Java → UI.

## 2. Инварианты, которые нельзя нарушать

1. Python получает только снимок Java: `caseId`, `reportId`, `sourceRevision`, полный `reportText`, целевые пункты с `itemId`, `category`, `location`, `symptom`, `contentVersion`, `workRound`.
2. Ответ содержит каждый переданный пункт ровно один раз. ID, версии и раунды возвращаются без подмены.
3. `REPORTED_DONE` означает только «в тексте явно сообщается о выполнении». Не «ремонт проверен», не `RESTORED` и не закрытие обращения.
4. `PLANNED` означает явно запланированную работу. Условие, вопрос, просьба и предположение сами по себе не становятся планом.
5. `SYMPTOM_PERSISTS` требует утверждения об оставшемся симптоме. Отрицание относится к своему сказуемому.
6. `UNRELATED` требует явного другого объекта/места. Отсутствие сведений - `INSUFFICIENT_INFORMATION`.
7. `CONFLICT` - неустранённое противоречие, а не любое соседство «сделали» и «не». «Раньше не работало, теперь работает» требует учёта времени или воздержания.
8. При недостатке уверенности возвращать `INSUFFICIENT_INFORMATION`, `evidence=null`. Не выдумывать процент уверенности.
9. Цитата - непрерывный точный фрагмент исходного текста. `start` включительно, `end` исключительно, единицы - Unicode code points. Emoji не должны сдвигать границы. Нормализованный текст нельзя использовать как источник offsets.
10. Текст пользователя никогда не является инструкцией для программы. Нет выполнения команд, SQL, HTTP-запросов или изменения статусов из отчёта.
11. Сохранение отчёта, подтверждение связи человеком и наблюдение автора - три отдельные команды. Свет не закрывает дверь. Все права проверяет Java по сессии и Membership.
12. `ANALYSIS_ENABLED=false` должен скрывать также старые сохранённые READY и ожидающие задачи на чтении. Запрос чтения не пересоздаёт анализ и не меняет историю.

## 3. Варианты и порядок выбора

| Вариант | Что даёт | Что теряем / риск | Решение |
|---|---|---|---|
| Отключить анализ и оставить ручную связь | Рабочий безопасный сценарий сразу | Нет автоматических подсказок | Обязательный аварийный fallback |
| Добавить к v2 несколько стоп-слов | Маленькое изменение, сохраняет покрытие | Сохраняет ошибки привязки места, отрицания и одинаковых категорий; список исключений разрастается | Измерить как контрольный вариант, не выбирать по размеру diff |
| Консервативный scoped RULES v3 | Явные предикаты, область утверждения/места, проверка всего набора пунктов, отказ при неоднозначности | Больше воздержаний, ограниченная языковая грамматика | Основной кандидат для текущего MVP |
| Добавить dependency parser / NLI | Потенциально лучше покрытие языка | Нужны реальные размеченные данные, новые зависимости, latency/качество/отказоустойчивость и отдельная оценка | Не подключать без измеримого выигрыша |
| Генеративный LLM | Может понимать сложный контекст | Непредсказуемость, стоимость/доступность, новая поверхность ошибок; не нужен для основной цепочки | Не использовать как быстрый ремонт RULES |
| Структурированный отчёт по каждому пункту | Убирает часть языковой неоднозначности | Меняет UX/контракт; человеческая связь уже существует | Использовать существующий ручной выбор, не строить второй механизм |

Сравнивать три реализуемых кандидата на одинаковых входах: зафиксированная v2, v2 с минимальными guard-проверками, scoped v3. Основной приоритет - не выдавать ложный `REPORTED_DONE`. Затем точность остальных подсказок, доля полезных ответов и время. Не объявлять тривиальный анализатор «всегда недостаточно сведений» победителем только за ноль ложных DONE: нужны положительные контрольные примеры.

## 4. Последовательность K-ML-01

### Шаг 1. Зафиксировать исходную точку

Прочитать [архитектуру](../architecture.md), [домен](../domain.md), [контракт 05](../../contracts/05-report-comparison.md), [contracts/README](../../contracts/README.md) и текущие `ml/app/features/inference/rules_analyzer.py`, `ml/app/features/inference/schemas.py`, `ml/scripts/evaluate.py`. Проверить `git status`, ветку и SHA. Не затирать чужие изменения.

Сохранить v2 только в инструменте сравнения `ml/scripts/evaluation/`. Production endpoint должен иметь один выбранный алгоритм. Не добавлять пользователю переключатель «старый/новый».

### Шаг 2. Исправить анализ в ответственном слое

Работать в `ml/app/features/inference/rules_analyzer.py` и существующих тестах. Использовать стандартную библиотеку и существующие схемы. Сначала выделить допустимые утверждения и область их действия, затем сопоставлять пункту.

- Распознавать точные утвердительные конструкции и категорию объекта. Слишком свободный substring-match не должен создавать факт.
- Не извлекать факт из вопроса, условия, модальности, команды, цитаты без установленного актуального контекста или опровержения. Не поддержанное безопасно отбрасывать.
- Не переносить отрицание через соседнее сказуемое: «заменили лампу, жалоб нет» отличается от «лампу не заменили».
- Проверять этаж, подъезд и другие поддержанные признаки места. Не поддержанный или неоднозначный адрес не считать совпадением.
- Учитывать весь набор пунктов. Если одной фразе подходят два одинаковых объекта в разных местах, без явного уточнения воздержаться; нельзя независимо выдать DONE обоим.
- Не терять контекст между предложениями. Если грамматика не умеет достоверно разрешить ссылку «там/её/на этом этаже», воздержаться.
- Выбирать evidence из оригинального текста вместе с существенными отрицанием/условием/противоречием. Никогда не обрезать опровергающую часть ради уверенного результата.

Версия ответа - `rules-baseline-v3`. Новая смысловая версия должна согласованно пройти Java policy, UI и примеры контрактов. Новый enum/API не нужен.

### Шаг 3. Измерить независимо

Разделить:

- существующий синтетический regression-набор;
- новые адресные unit/regression-тесты разработчика;
- замороженный синтетический challenge другого автора, не виденный до первой версии;
- будущий размеченный людьми набор реальных обезличенных фраз - его сейчас нет.

Challenge: [данные](../../ml/data/challenge-v3.jsonl), [протокол разметки](../../ml/data/challenge-v3.md). Нельзя менять gold после просмотра результата, чтобы повысить метрику. Спорные строки учитывать отдельно: строгий результат и sensitivity с заранее заданными alternatives. После исправлений по challenge он становится regression-набором; не называть повторный прогон слепой оценкой.

Для каждого кандидата записать: число отчётов и наблюдений, confusion matrix/метрики по классам, ложные DONE, пропущенные положительные случаи, долю воздержаний, ошибки цитат/версий, время на тех же условиях. Оценивать весь набор, включая отказ, а не только ответы, которые алгоритм захотел выдать. Сохранить SHA256 данных и исходников, команды и пределы воспроизводимости.

### Шаг 4. Закрыть Java-границу и старые ответы

Файлы: `backend/.../inference/AnalysisPolicy.java`, `inference/application/AnalysisWorker.java`, `cases/application/CaseService.java`, `inference/application/AnalysisHttpTest.java`.

- Структурную валидацию `SuggestionValidator` сохранить. Не смешивать её со списком версий, допущенных в текущий выпуск.
- Worker может пометить ответ READY только для проверенной пары `RULES + rules-baseline-v3`. Неизвестная версия/NLI/STUB не превращается в доверенную подсказку.
- При чтении сначала проверить доступ к отчёту. Затем выключенный feature flag возвращает `MANUAL_REQUIRED` без результата даже при сохранённом READY.
- Старый v2 или несовпадающие sourceRevision/contentVersion/workRound возвращают `STALE` без payload. Сохранённая история остаётся неизменной.
- GET не запускает Python и не пересоздаёт очередь. Не нужен массовый SQL UPDATE старых подсказок.
- Отказ Python не блокирует сохранение отчёта или ручную связь. HTTP-вызов Python остаётся вне SQL-транзакции.

### Шаг 5. Закрыть UI-кэш

Файлы: `frontend/src/features/reports.tsx`, `frontend/tests/ui.spec.ts`, согласованный fixture в `contracts/examples/report-suggestions-ready.json`.

- До свежего успешного чтения подсказок не показывать сохранённый кэш.
- Ошибка повторного чтения убирает цитату; ручной выбор остаётся доступным.
- При возвращении на экран/вкладку проверять актуальность; открытый READY проверяется периодически. Это не мгновенный push: учитывать интервал и наличие сети.
- Проверить mode/version, caseId/reportId, sourceRevision/contentVersion/workRound и точную цитату.
- Checkbox не выбирается автоматически. Подсказка не отправляет команду и не задаёт итог ремонта.
- Уход с экрана/загрузка/ошибка не должны стирать уже введённый человеком выбор без объяснения.

### Шаг 6. Полный локальный путь

Использовать [полигон](../qa/playground.md). Реальный Java + PostgreSQL + Python + reverse proxy + браузер; синтетические только учётные записи и обращения. Отдельные браузерные контексты автора, диспетчера и постороннего. Проверить:

1. «Свет + дверь», автор подтверждает список, прогресс 0/2.
2. Диспетчер сохраняет условный отчёт; DONE не предлагается, прогресс остаётся 0/2.
3. Явный отчёт про свет получает точную подсказку только свету; ничего автоматически не связано.
4. Диспетчер вручную связывает свет; автор ещё не подтвердил - 0/2.
5. Автор сообщает RESTORED по текущему раунду света - 1/2. Дверь и её следующий шаг остаются.
6. Старый ответ после новой связи/раунда скрывается. При выключении анализа ручная цепочка продолжает работать.
7. Посторонний получает отказ и не читает ни текст, ни отчёт, ни подсказки.

Не запускать эти мутации на публичном домене. Удалять только созданный полигоном уникальный Compose-проект и его тома.

## 5. Критерии локального принятия

- Все известные критические фразы воспроизводимо покрыты; нет ложного DONE в зафиксированном challenge. Если это не достигнуто, публикация анализа остаётся выключенной.
- Положительные ясные фразы всё ещё распознаются; цена консервативности и пропуски явно указаны.
- Pytest, форматирование, статический анализ, Java/PostgreSQL HTTP tests, frontend build и UI tests проходят.
- Реальный локальный API-сценарий с включённым анализом проходит; UI tests с mock API отдельно обозначены как mock.
- Версии/цитаты/старые результаты/выключенный flag/ошибка кэша проверены.
- Семён может продолжать DATA-API без новой несовместимой схемы. Общие документы ссылаются на проверенный результат.
- Выпуск на сервер - отдельный этап: согласованная сборка Java + Python + frontend, SHA, public smoke, ручной MAX G2. Старые production-записи сохраняются.
