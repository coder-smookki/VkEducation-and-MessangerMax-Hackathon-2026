## K0. Запуск и границы - 2 часа

Результат: у троих воспроизводится каркас, известны ограничения кейса и маршрут получения MAX-доступов.

1. Сверить закрытый кейс, допуск заранее подготовленного кода/AI, календарь и обязательные материалы. Исторический PDF не заменяет новые условия.
2. Каждый запускает Compose и smoke из [development.md](../development.md). Записать точный блокер, если не работает Docker/порт/диск.
3. Проверить наличие тестового бота, HTTPS-домена и тестовых аккаунтов; секреты передаются отдельно от Git. Отсутствующие доступы не блокируют локальные UI/Java/ML.
4. За первый час принять C1 с Семёном; затем C2/C4 и подписи C3 с Никитой. Не тратить день на согласование несуществующих расширений.

Приёмка: команда знает, что запускается сегодня; доступы имеют фактический статус; у каждого есть первая независимая задача.
Передача: Семёну - требования входа и экранов; Никите - обязательность ML по кейсу и доступное время проверки людьми.

## K1. Настоящий вход MAX - 7-9 часов

Начало: C1; завершение: Membership S1 и проверка доступного реального клиента. Пока ждёшь MAX, работай с криптографическими тестовыми векторами и UI-фикстурами, сохраняя закрытый рабочий API.

1. Из `frontend/src/platform/max.ts` получить исходный `window.WebApp.initData`. Не восстанавливать подписанные данные из `initDataUnsafe`, не отправлять роль из UI.
2. В `identity/` реализовать разбор и проверку по [официальному алгоритму MAX](https://dev.max.ru/docs/webapps/validation), повторно сверив страницу при реализации. Отдельно тестировать криптографию и HTTP-сессию.
3. Для raw initData проверить единственность параметров/hash; пары разбирать по первому `=`. Декодировать значения ровно в нужном слое, сохранить исходное представление JSON пользователя для подписи. Отсортировать ключи, соединить пары переводом строки. HMAC-SHA256 с ключом `WebAppData` от bot token даёт secret; HMAC-SHA256 от строки параметров с этим secret даёт сравниваемую подпись. Сравнивать байты constant-time. Не подставлять алгоритм другого мессенджера.
4. Только после подписи разобрать user/auth_date. Стартовая серверная политика: не старше 5 минут, будущее не более 60 секунд; тесты используют управляемые часы. Эти интервалы - наше решение, не требование MAX. Повторный ключ в строке и повторное открытие приложения - разные случаи.
5. Связать проверенный MAX ID с внутренним `app_user.id`. Уникальность MAX ID должна выдержать два одновременных входа. Кирилл и Семён согласуют один Principal, без двух сущностей пользователя.
6. Подключить штатную session strategy, сохранение SecurityContext, logout и CSRF. Политика сессии и ограничения встраивания - [implementation.md](../implementation.md). MAX token не попадает в Frontend, логи, URL или response.
7. Реализовать C1 endpoints `/csrf`, `/auth/max`, `/auth/logout`, `/me`. Открывать только нужные route/method; Membership проверяется на каждом доступе, а не единожды в login.

Приёмка: валидный вход и следующий GET `/me`; подмена подписи, дубль ключа, неверный hash, старое/будущее время, неправильное кодирование; роль из тела игнорируется/отклоняется; logout закрывает доступ; команды без CSRF отклоняются; смена session ID; отзыв Membership действует без нового login.

Проверить `+`, `%`, Unicode, emoji и значение с `=` по официальным векторам/реальному запуску. Не использовать один собственный ошибочный encoder и для генерации ожидаемого hash, и для проверяющего кода.
Передача Семёну: внутренний Principal и способ подключения тестового security context. Передача UI: точный цикл входа/выхода, CSRF, истечение сессии, отсутствие доступа к дому.

## K2. Сохранённый черновик автора - 8-10 часов

Начало: C1 и примеры ответов. Можно делать одновременно с S1. Интеграция: K1 + S1.

1. Разделить UI по сценариям: список обращений, редактор черновика, подтверждение, карточка. Создавать компоненты по мере поведения; не проектировать большой общий UI-kit.
2. В `src/api/client.ts` добавить рабочие запросы, тип ошибки и версии. В компонентах не собирать свои fetch с другим протоколом ошибок.
3. Создать черновик с houseId из `/me`, исходным текстом и одним Idempotency-Key на попытку пользователя. Повтор после сетевого сбоя сохраняет тот же ключ/тело; новое действие получает новый ключ.
4. Показывать исходный текст рядом с category/location/symptom. До подтверждения можно добавить/исправить/удалить пункт. OTHER доступен без попытки угадать категорию.
5. Различать «несохранённые изменения», «сохраняется», «сохранено сервером», ошибку и конфликт. Не рисовать сохранение до успешного ответа.
6. Сохранять незавершённый ввод в ограниченный черновик текущей вкладки, привязанный к текущему внутреннему пользователю/дому. Не хранить там initData/токены; очищать после завершения и logout. После перезапуска перечитать сервер и предложить восстановление текста без тихой перезаписи новой версии.
7. Перед confirm показать весь список и получить явное действие автора. Отправить sourceRevision и expectedCaseVersion. После CONFIRMED убрать редактирование состава и показать допустимый отзыв с причиной.

Приёмка: создание при выключенном Python; повтор не создаёт второе обращение; ошибка сохраняет ввод; 409 показывает серверную версию и оставляет локальный текст; 401 требует вход; 404 не раскрывает чужую карточку; пустые/слишком длинные поля и 21-й пункт не отправляются; сервер проверяет то же независимо.

Передача: Семёну - обнаруженные расхождения C1 с UI и минимальный пример; в общий smoke добавить реальный авторский путь только после его появления. Старый synthetic smoke не переименовывать в тест CRUD.

## K3. Диспетчер, подсказки и результат - 7-9 часов

Начало: C2/C3 и фикстуры; сначала ручной экран, после S4 подключение анализа. S2/S3 не должны ждать NLI.

1. Список диспетчера показывает только разрешённые дома и доступные подтверждённые обращения. Назначение исполнителя и ввод отчёта используют отдельные серверные команды.
2. Сохранить отчёт; отобразить его исходный текст. Не менять работу пункта из факта сохранения отчёта.
3. Для каждого пункта показать ручной выбор связи: сведения о планах/выполнении или оставить без связи. Полнота списка сохраняется даже без подсказок.
4. Подсказки отображать как предложение с точным evidence; `Array.from(reportText)` переводит code-point offsets в корректное выделение. Не применять HTML из текста и не использовать `dangerouslySetInnerHTML`.
5. Разделять job status QUEUED/RUNNING/READY/STALE/MANUAL_REQUIRED и mode STUB/RULES/NLI/MANUAL. При STALE предложить актуальный разбор; при MANUAL оставить все ручные действия доступными. Не показывать процент физического ремонта.
6. Принятие связи - обычная команда с expectedCaseVersion, contentVersion и expectedWorkRound. Отказ от ML не меняет рабочее состояние. Сохранение связи и новое наблюдение требуют подтверждённого серверного результата.
7. На экране автора показывать работы, наблюдение, административное решение и содержание раздельно. AFTER_REPORT доступно только для REPORTED_DONE; самостоятельное наблюдение - отдельное действие. «Не могу проверить» и отсутствие ответа не являются успехом.
8. История показывает актора, время, действие и контекст раунда. Доля подтверждения приходит с Java; отозванный пункт не исчезает из общего числа.

Приёмка: сценарий [worked-example.md](../worked-example.md); только свет подтверждён, дверь остаётся; план не выдаётся за выполненную работу; архив не зеленеет; новое сообщение снимает актуальность прежнего наблюдения только после связи; ошибки 409 не запускают автоматическую повторную мутацию.
Передача: Никите - неоднозначные подписи/evidence; Семёну - точные запросы конфликтов. Проверки A01-A08 в [acceptance.md](../acceptance.md).

## K4. Проверка UX и помощь оценке - 4-5 часов

1. Проверить вход в доступных реальных MAX-клиентах уже в K1, затем весь путь после G1. Записать OS, версию клиента, дату и пройденный сценарий. Непроверенные устройства не отмечать успешными.
2. Узкая ширина 390 px, увеличение текста, длинные русские строки, экранная клавиатура, возврат из приложения, потеря сети, двойное нажатие.
3. Все элементы доступны клавиатурой; видим фокус; label связан с полем; статусы различаются текстом, а не только цветом; ошибка объявляется доступным способом и не уводит фокус без причины.
4. Подготовить свою независимую часть отложенных диалогов до просмотра предсказаний и помочь N4 измерять время правильного разбора. Не исправлять test-набор под текущую модель.
5. Зафиксировать фактические неудобства и исправить блокирующие. Красивый экран без работающей команды не проходит приёмку.

## K5a. MAX-транспорт до общей доставки - 3-4 часа

Начало: C4 и доступы. Это задача T5-T7, не последнего дня.

1. В `max/` реализовать только необходимые HTTP-операции, актуальные адреса и авторизацию проверить в официальных docs. Один ограниченный клиент; не выводить URL с токеном в ошибки.
2. Приём webhook: предел тела, секрет, поддержанный тип Update, устойчивый event key, hash тела, сохранение inbox, затем ACK. БД недоступна - не выдавать успешный ACK за несохранённое событие.
3. С Семёном договориться об адаптере callback: проверенный sender, непрозрачная server-side ссылка, идентификатор события. Доменный эффект реализует S5 через S3, не второй handler со своими правилами.
4. Передать результат отправки: успех/временная ошибка/неповторяемая ошибка, допустимый Retry-After. Retry и persisted lease принадлежат S5.

Приёмка: неверный секрет не создаёт inbox; дубль не создаёт второй эффект; несовпавший hash не затирает оригинал; остановка после commit до обработки сохраняет событие. До MAX-доступов можно проверить локальный HTTP-транспорт, но это не подтверждает реальную доставку.

## K5b. Сборка, инструкция и сдача - 3-4 часа

1. Подготовить воспроизводимую сборку и единый HTTPS origin web/API для разрешённого внешнего запуска; выключить demo/no-db. Vite dev server не использовать для публичного размещения.
2. Проверить конфигурацию секретов, внутренний доступ Python/БД, body/rate limits, health и восстановление БД вместе с Семёном. Не обещать готовый deployment из локального Compose.
3. Попросить второго участника запустить чистый checkout по README. Исправить реальные пропуски инструкций.
4. Записать демонстрацию ручного пути, подсказок и отказа ML. Указать commit, режим и ограничения; финальные материалы сверить с кейсом. Внешняя публикация/отправка выполняется в пределах актуального поручения.
