# Кирилл - Frontend + Backend интеграции

Роль: владелец пользовательского пути и MAX. Backend остаётся Java; бот не выносится в самостоятельный Node/Python-сервис.
Основные файлы: `frontend/src/`, `backend/src/main/java/ru/koren/identity/`, `backend/src/main/java/ru/koren/max/`, `compose.yaml`, `.github/workflows/ci.yml`.

## Задачи по порядку

| ID | Часы | Зависимость | Действие | Приёмка |
|---|---:|---|---|---|
| K0 | 2 | Нет | Сверить кейс, заранее подготовленный код, доступы MAX и календарь; запустить каркас у всех | У каждого есть запуск; ограничения записаны в состоянии проекта |
| K1 | 7-9 | S0 | MAX Bridge → исходный `initData` → Java-проверка подписи и срока → серверная сессия; вместе с Семёном согласовать Principal | Подделка, повтор параметров, истёкшая дата и будущая дата отклоняются; `initDataUnsafe` не даёт доступа |
| K2 | 8-10 | S1, после K1 для рабочего режима | Экран автора: сохранённый черновик, редактирование пунктов, подтверждение списка, состояния загрузки/ошибки/409 | После сбоя сети текст можно восстановить; видны все пункты; исходный текст рядом; повторы отправки не дублируют обращение |
| K3 | 8-10 | S2-S3, контракт S4 | Панель диспетчера и экран результата автора; принять/отклонить связь; выделить evidence, показать версии | «Лампа» не закрывает «дверь»; план не предлагает подтверждение ремонта; 409 требует обновления данных |
| K4 | 4-5 | G1 | Проверить Mini App на реальных доступных клиентах, узком экране и клавиатурой; согласовать аварийный маршрут | Статусы понятны без цвета; кнопки доступны; возврат из MAX не теряет черновик; невыполненные проверки устройств перечислены |
| K5 | 5-6 | G2 | Java-webhook и доставка с Семёном; единый HTTPS origin для web/API, инструкция запуска, демо/видео | Секрет webhook проверяется; 2xx только после надёжной записи события; сборка воспроизводима; внешняя публикация выполняется только по актуальному поручению |

Ориентир: 34-42 часа + общий резерв. Для снижения нагрузки Семён берёт всю бизнес-логику, DTO рабочих обращений и SQL; Никита готовит подписи и смысл ML-состояний для UI.

## Первый час

Прочитать [контракты](../api.md), запустить [каркас](../development.md), открыть `frontend/src/App.tsx` и `frontend/src/api/client.ts`. Это учебный экран, а не реализация K2-K3. Начать K1 в `identity/`; не добавлять приём `userId` или роли из query/body для удобства теста.

## Java-часть K1/K5

Проверять подпись по [текущему алгоритму MAX](https://dev.max.ru/docs/webapps/validation); криптографию брать из Java standard library. Срок и допустимый сдвиг часов - политика сервера. После валидации получить внутренний `app_user.id`; дом и роль определяет Membership, не MAX.

Сессия Mini App и браузерной панели должна работать через один согласованный вход. В MVP диспетчер также входит аккаунтом MAX и получает роль серверным назначением. Обычная браузерная вкладка без валидного входа не получает прав. Произвольный выбор роли из UI запрещён.

Webhook: лимит тела до разбора JSON, проверка `X-Max-Bot-Api-Secret`, durable inbox, защита от дублей, ограниченные повторы. Схему идентификатора события сверить с реально полученными типами MAX; универсальный `update_id` не предполагать.

## Передача

Семёну: форма Principal, правила сессии, требуемые DTO UI и обработка 409. Никите: понятные пользователю обозначения всех `Relation`, контекст выделения фрагмента. Обоим: короткое видео реального пути и перечень заглушек.
