# Параллельная работа трёх участников

## Разделение без скрытого четвёртого разработчика

Семён владеет Java/Python/SQL/ботом. Кирилл - React/стилями/сборкой и интеграцией. София - независимыми сценариями, fixtures и проверкой. София не считается резервным backend-разработчиком; Кириллу не назначается скрытая реализация аутентификации.

| Общий участок | Автор | Кто проверяет до интеграции |
|---|---|---|
| Java REST DTO/ошибки | Семён | Кирилл: потребление; София: негативные случаи |
| Python DTO/экспорт/Java валидатор | Семён | София: независимые примеры; Кирилл: смысл отображения |
| Поля для экрана/макеты | Кирилл | Семён: существование/права/команда; София: состояние ошибки |
| SQL V3+ | Семён | София: clean DB и upgrade с V2 |
| Compose/proxy/CI | Кирилл | Семён: env/сеть; София: чистый запуск |
| Общий статус/план | Кирилл после интеграции | Каждый передаёт фактический итог |

## Контракты до параллельного кода

Базовый набор S-01/K-01 уже используется; при каждом изменении сохранить согласованность: `/me`/Membership, CaseView/ItemView, receipt/nextAction, report/link, observation/history, ошибки. Для каждого есть успешный JSON, пустой ответ, запрет, конфликт и неизвестный исход. В примерах только синтетические UUID и текст. OpenAPI/JSON Schema и фактические DTO обязаны совпасть до переключения UI с fixtures на API.

Не путать пять файлов `contracts/01..05` с организационными пакетами работы. Для конкретного изменения указывается имя schema/DTO и оба потребителя. При несовместимости не менять один consumer «на потом»: согласованный атомарный PR/commit либо временная совместимая версия.

Кирилл может реализовать весь экран на fixture, София - тесты/план, пока Семён пишет сервер. Такой экран не получает VERIFIED для интеграции. Test-only adapter должен подключаться явно, не автоматически при ошибке сети и не в production.

## Git и совместные файлы

Интеграционная ветка сейчас `dev`. От актуального dev - короткая ветка на один task ID; обычное слияние после проверки. Не менять main, не force-push и не удалять чужую рабочую ветку по старому поручению из истории. Следить за текущим указанием капитана. Текущие согласованные изменения и документация отправляются в dev; релиз в main требует отдельного актуального поручения.

Один владелец файла в каждый момент. Особенно `SecurityConfig`, миграции, `contracts/*.json`, `frontend/package-lock.json`, Compose/CI. Нельзя одновременно генерировать OpenAPI и вручную править тот же output. Перед получением общего файла перечитать `git diff`; не применять `reset --hard`/`checkout --` к чужим правкам.

## Ритм дня

- Начало: 10 минут - ближайший gate, блокеры, свободный номер миграции, изменяемый контракт.
- Первая половина: вертикальные небольшие задачи; публиковать DTO/fixtures сразу, не ждать готовности всего слоя.
- Середина: 15 минут - живой запрос producer → consumer; сообщить несовместимости до вечера.
- Конец: 20-30 минут - интеграция проверенных изменений, один совместный smoke; София фиксирует факт. Общую память обновить после включения.

При блокере сообщать «нужно поле X с семантикой Y для экрана Z», а не «backend не готов». Приложить минимальный запрос/ожидание. Пока зависимость исправляется, делать независимые сценарии, accessibility или проверки, не обходить права.

## Передача

ID, ветка/SHA, доступная функция, изменённый DTO/миграция, команды и результаты, ограничения, следующий ID. Скриншот служит доказательством отображения, но не транзакции. CI относится только к конкретному SHA; пропущенный внешний тест не PASS.
