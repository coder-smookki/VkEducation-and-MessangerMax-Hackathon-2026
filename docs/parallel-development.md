# Параллельная разработка

Рабочие правила для трёх участников и нейронок, которые помогают каждому. Владение файлами не разрешает незаметно менять общий контракт. Текущее поручение - доставить каркас и документацию в `main`; дальнейшие задачи удобно вести короткими отдельными ветками с последовательной интеграцией.

## Первые два часа

| Время | Кирилл | Семён | Никита |
|---|---|---|---|
| 0-30 минут | Запуск Frontend, проверка способа получения MAX-доступов | Запуск Java/PostgreSQL, чтение V1/V2 | Запуск Python, тестов и evaluator |
| 30-60 минут | Проверка C1 и состояний экранов | Минимальный C1: Principal, draft, версии, ошибки | Проверка C3, схема разметки |
| 60-90 минут | K1 и UI на примерах C1 | S1 с серверным актором в тестах | N0, без CRUD и MAX |
| 90-120 минут | Короткая сверка форм C2/C4 | Примеры C2/C4, затем продолжение S1 | Evidence с emoji и случаи отказа |

Это окна для короткой синхронизации, не обязательное двухчасовое совещание. Решения внутри компонента принимает владелец.

C3 включает extract/clarify/similar/compare. В dev similarity использует Kafka/Chroma только на разрешённой Java выборке; clarify работает на RULES, extract/compare остаются STUB. Контракт 04 и его оба потребителя изменяются вместе.

## Независимая работа

- Кирилл строит компоненты с данными и обработчиками, проверяет загрузку, пустое состояние, 409, отказ ML и клавиатуру. Временный mock включается только в тестах/явной локальной среде. При I1/I2 подключает настоящий HTTP. Mock не должен давать права в рабочем API.
- Семён проверяет application services на PostgreSQL с серверным актором из тестовой фикстуры. В HTTP-тестах используется тестовый security context. Никаких production-заголовков `X-User-Id` и отключения `SecurityConfig` ради независимости от K1.
- Никита работает на JSONL и общих inference-примерах. Python не получает БД. Семён проверяет timeout, неверный ответ и очередь на STUB/локальном HTTP-имитаторе до готовности модели.

Фикстура доказывает контракт, общая интеграция - соединение настоящих компонентов. Не создавать постоянную вторую реализацию продукта ради mock.

## Владение файлами

| Область | Основной автор | Как меняем вместе |
|---|---|---|
| `frontend/**`, `backend/.../identity/**`, `backend/.../max/**` | Кирилл | Семён передаёт требования контракта |
| `backend/.../cases/**`, `reports/**`, `observations/**`, `notifications/**`, `inference/**` | Семён | Никита меняет протокол через C3 |
| `ml/**`, экспортированный inference OpenAPI | Никита | Java records/примеры проверяет Семён |
| `backend/.../config/SecurityConfig.java` | Кирилл | Семён сообщает route/method и тесты прав до открытия |
| `backend/pom.xml`, `application*.yml` | Владелец функции | Сообщить зависимость/ключ до правки; не обновлять версии заодно |
| `backend/src/main/resources/db/migration/**` | Семён - координатор | Кирилл передаёт потребности identity; номер согласуется до merge |
| Compose, Dockerfiles, CI, README | Кирилл | Никита передаёт ресурсы ML, Семён - настройки БД |
| `docs/team/<участник>.md` | Свой участник | Уточнять свой план без изменения соседних ID |
| `docs/plan.md`, `docs/memory/*.md` | Кирилл при интеграции | Авторы передают итог в PR; не ведут три конкурирующих журнала |

В Java `...` означает `src/main/java/ru/koren`, а не буквальную папку. Карта существующего и планируемого кода - [implementation.md](implementation.md).

## Миграции

V1/V2 уже применялись. Следующий свободный номер сейчас V3, но перед работой смотреть актуальную `main`. Две разные миграции с одним номером недопустимы.

1. Автор описывает изменение; Семён закрепляет свободный номер в передаче задачи.
2. SQL приходит вместе с потребителем либо совместимой подготовительной схемой. Проверяются чистая БД и обновление текущей цепочки.
3. Если номер занят в `main`, невыпущенную миграцию переименовать до применения в общей среде и повторить проверку на отдельной тестовой БД.
4. Если она уже применена к сохраняемой общей БД, не переписывать и не переименовывать - добавить новую исправляющую миграцию.
5. Не использовать `flyway repair`, удаление history или `down -v` для разрешения конфликтов веток.

Для трёх человек достаточно одного согласованного порядка; дополнительные схемы версионирования не нужны.

## Ветки и интеграция

Каждый начинает от свежей `main` в своём clone/worktree. Примеры будущих веток: `codex/k2-author-screen`, `codex/s1-drafts`, `codex/n1-baseline`. Первоначальная `codex/hackathon-starter` удаляется после доставки в `main` по текущему поручению.

Одна ветка - один проверяемый результат. Кирилл интегрирует по очереди: совместимый контракт/схема, затем потребители. Проверять объединение с актуальной `main`: старый зелёный CI отдельной ветки не доказывает совместимость. Не переписывать опубликованную чужую историю и не делать force-push в `main`.

Коммит - один короткий **русский заголовок**, без тела и coauthor trailers. Например: `Добавлено сохранение черновика обращения`. Описание поведения и проверок хранится в PR и не добавляется в тело коммита.

Контракт блокирует соседа - передать маленький совместимый PR первым. Несовместимое изменение требует связанных PR с согласованным порядком либо единой интеграции обеих сторон. Отключать validation/права для прохождения проверки нельзя.

## Окружения

На разных компьютерах стандартные порты Compose не конфликтуют. На одном компьютере `-p` разделяет контейнеры/volumes, но **не опубликованные порты**. Текущий Compose фиксирует 5173/8080/5432: перед вторым стеком развести порты локальным проверенным override или остановить свой первый стек. Один `-p` проблему не решит.

Каждый использует свою тестовую БД. Изменяющие тесты не направлять в общую демонстрационную БД. Общий стенд запускает согласованную сборку. Один интегратор управляет тестовым MAX-ботом; webhook не переключается одновременно между тремя ноутбуками. Локально воспроизводятся синтетические Update.

## Передача готовой части

```text
Задача: S1
Автор: Семён
База main и commit изменения: реальные SHA
Работает: конкретная команда и наблюдаемое поведение
Контракт: C1, изменённые поля/ошибки
Миграции: фактический файл или «нет»
Проверка: команда, результат, тестовая среда
Нужно Кириллу: endpoint + пример + сценарий ошибки
Осталось: конкретное ограничение
```

DONE означает реализацию, негативные проверки, совместимость потребителя и сохранённое доказательство. Готовность кода в своей ветке ещё не означает прохождение G1-G3. Не менять статус чужой задачи без её проверки.
