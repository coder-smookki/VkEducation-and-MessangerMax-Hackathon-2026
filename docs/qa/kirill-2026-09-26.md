## Что реализовано

- K-01/K-06: оболочка, реальные роли из /me, темы system/light/dark, крупный текст, focus/dialog/dirty guards, адаптивность. Палитра из design.md; токены и системный шрифт, без несовместимого UI toolkit.
- K-02: создать исходник, вручную добавить/править/удалить пункты, уточнить только своё обращение, отдельный review/confirm, квитанция. 0 пунктов допустимы в черновике, подтверждение 1..20; Unicode code points соответствуют Java.
- K-03: очередь диспетчера и серверные фильтры, приём, следующий шаг от текущего диспетчера, сохранение отчёта отдельно от явных связей. Подсказки только с актуальными версиями и точной цитатой, выбор всегда пустой. На desktop таблица очереди и двухколоночный отчёт.
- K-04: три наблюдения автора, серверный прогресс, незавершённые пункты сначала без перенумерации исходного списка, история, архив и отзыв с причиной. Архив не становится ремонтом, total не уменьшается.
- K-05 локально: официальный Bridge, raw initData, native back/closing confirmation, UUID start_param только для перехода, восстановление сессии. Внешний браузер получает кнопку открытия проверенного @t109_hakaton_max_bot, без фиктивного входа.
- K-07: static release Dockerfile/nginx, private DB/Python, optional Caddy HTTPS, no-demo, JSON API failures, cache policy, воспроизводимый одноразовый стенд. Токен не в JS.

Типы генерируются из Java OpenAPI, проверяются api:check. Query cache и hash router используют стандартные библиотеки; нет второй продуктовой state machine. Формы сохраняют snapshot, ожидаемые версии и ключ команды. Неизвестный исход повторяется тем же телом/ключом; 409 требует явного согласования нового контекста. При повторном входе тем же аккаунтом ввод сохраняется, при смене аккаунта кэш очищается.

Чистый **по данным** одноразовый Compose: build/start/браузерные сценарии 27.3 с, Docker layers и скачанные зависимости уже были в кэше. Это не замер холодной source-build и не обещание ≤5 минут на сервере. Итоговый bundle около 126 КБ gzip JS; серверная производительность этим не измеряется.

Реальные сценарии: автор создал/подтвердил свет+дверь; диспетчер принял/дал шаг; сохранение отчёта не изменило пункты; связь только со светом; RESTORED автора дал 1 из 2; диспетчер за автора получил 403, чужой дом 404; архив с оборванным ответом повторился без второго audit event. Также одноразовое приглашение/повтор403, PERSISTS/CANNOT_CHECK, отзыв с прежним total, demo/аноним401, nginx413JSON и static fallback. При остановленном Java API возвращает JSON503, static остаётся доступным, после старта Java восстановлен ответ /csrf. Runner проверен с посторонним COMPOSE_PROFILES=https и подставным MAX_BOT_TOKEN: они не переопределили изолированный тестовый стенд.

Найдены и исправлены в ходе работы: форма брала старую версию из cache при первом открытии; nginx не наследовал error_page413 в API location; read-only nginx требовал temp directories в /tmp; loopback port недоступен при одной internal network. Исправления подтверждены соответствующим повтором тестов.
