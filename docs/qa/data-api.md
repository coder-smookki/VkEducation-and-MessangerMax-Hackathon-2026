### Что означает успешный официальный валидатор

Валидатор проверяет JSON Schema, некоторые зависимости/переменные и наличие пути/метода в OpenAPI. **Он не выполняет HTTP**, не входит в MAX и не доказывает бизнес-результат. Вложенные `bodySchema` дополнительно проверяются локальным `Draft202012Validator.check_schema`; один официальный exit 0 не означает, что эти ожидания уже исполнились на сервере.

На 28.09 наш файл и официальный заполненный пример дают **exit 0**. Для нашего файла остаются предупреждения о внешних переменных - это ожидаемая необходимость подготовить доступы/дом/параметры, а не автоматически предоставленные платформой значения. Не удалять предупреждения фиктивными `extract` и не вставлять секреты в Git.

Команда из корня проекта (официальные файлы остаются вне репозитория):

`--schema` указан явно: в проверенной версии схема лежит в `Example/`, а default валидатора ищет её рядом со скриптом. `api.openapi` разрешается относительно нашего YAML. Коды: 0 - формат подтверждён, возможны предупреждения; 1 - ошибки проверки; 2 - файл/окружение не удалось прочитать. Сверять вывод целиком, не только код.

### Входные значения для исполнения HTTP

| Внешняя переменная | Подготовка |
|---|---|
| `residentCookie` | Полный актуальный набор cookies автора дома А после настоящего MAX-входа |
| `dispatcherCookie` | Отдельный cookie jar диспетчера того же дома А |
| `strangerCookie` | Отдельный cookie jar жильца дома Б, без Membership дома А |
| `houseId` | Явно выбранный UUID учебного дома А; подтвердить автору и диспетчеру через `/me`, не брать первый элемент массива |
| `runId` | Новый UUID на каждый полный сценарий; не секрет |
| `nextActionDueAt` | Будущий момент RFC3339, например текущее UTC + 1 день; не фиксированная устаревающая дата |

Три `userId` должны различаться. ID диспетчера, ID обращения/пунктов/отчёта и версии извлекаются из ответов. Для CSRF после входа используются `/csrf` и JSON `token`, не сырое значение cookie `XSRF-TOKEN`. Исполнитель обязан сохранять `Set-Cookie` в jar соответствующей роли и обновлять внешний `…Cookie` перед следующим запросом, включая cookie из `/csrf`. Заголовок из старого значения не должен подавлять новые cookies. Роль `public` всегда использует отдельный анонимный контекст.

Подстановка целого JSON-поля `${linkedCaseVersion}` должна сохранять integer из ответа. Подстановка внутри `Idempotency-Key` создаёт строку. Опубликованный валидатор не реализует эти операции: это условие исполнения, которое нужно согласовать с проверяющими. Не полагаться на неявное преобразование строк Jackson.

`repeatable: true` у команды означает повтор **исходных** роли, тела и ключа. Нельзя заново вычислять тело из более свежей версии при том же ключе. Новый полный прогон получает новый `runId`. GET с ожиданием промежуточного состояния (например, пустые `report.links`) повторяется только на соответствующей стадии, до последующих команд. После FAIL зависимые команды не выполнять.

### Вход организатора заново

1. Подготовить три разрешённых тестовых MAX-аккаунта и дома по [release](../release.md), сохранив прежние записи. Автоматическая локальная проверка не создаёт эти роли в публичной базе.
2. Каждый аккаунт открывает Mini App из бота. Для внешнего HTTP-клиента: отдельный jar → `GET /api/v1/csrf` → `POST /api/v1/auth/max` со свежим **настоящим** `initData` и CSRF → сохранить сменившийся `JSESSIONID` → снова `GET /csrf` → `GET /me`.
3. Проверить матрицу доступа и передать процедуру/временные доступы через согласованный закрытый канал. Не передавать bot token, не подписывать production `initData` самостоятельно.
4. После 30 минут бездействия повторить настоящий запуск MAX. Наш backend принимает новый `initData` не старше 5 минут; это ограничение входа, а не срок уже работающей сессии. Заранее выданная cookie не гарантирует доступ на следующий день.

**Остаток для капитана:** согласовать способ нового MAX-входа, отдельные cookie jars, типизированные подстановки/внешние значения и защищённый канал с техническими проверяющими. Репозиторий организаторов описывает формат и валидатор, но не предоставляет HTTP-runner или доступ к аккаунтам. Сообщение организаторам автоматически не отправлялось.

### Чем дополняется YAML и что приложить

Сдать `DATA-API.yaml` в корне вместе с `contracts/author-review.openapi.json`; в README оставить эту инструкцию и команду существующего `scripts/check_data_api.py`. Наш изолированный runner глубже схемы: сравнивает динамические ID, весь снимок двери и nextAction, owner/срок, точный scope, пагинацию очереди, replay, отказы и details истории. Не приписывать эти сравнения официальному валидатору или только статическому `bodySchema`.

В YAML нет `cleanup`: реального DELETE API нет, а архив не удаляет запись и историю. Для автоматических прогонов используется одноразовый локальный проект Compose с удалением **только своих** томов. Публичные проверки выполняются только в согласованной учебной среде; очистку рабочих данных не добавлять ради валидатора. Секреты и сырые протоколы в комплект Git не включать.

## Как запустить

```sh
python3 scripts/check_data_api.py            # два свежих прогона
python3 scripts/check_data_api.py --runs 3   # больше прогонов
```

Нужны Docker Compose и Python 3.11+. Скрипт сам поднимает **одноразовый** стенд из `compose.release.yaml` (проект `koren-dapi-check-<случайно>`, порт на 127.0.0.1, случайный тестовый ключ подписи), создаёт синтетические данные, проходит сценарий и в `finally` пытается удалить проект вместе с томами. Успешное удаление - отдельная обязательная проверка `cleanup`: ненулевой код Compose или исключение делает весь результат FAIL. К публичному стенду и к рабочей базе не подключается. Ключ, initData, cookies, CSRF и коды приглашений не печатаются и не пишутся в протокол.

Итог: построчно `PASS/FAIL, прогон, check, фактическое значение (ожидание при FAIL)`, затем `RESULT PASS|FAIL: n/m checks` и код выхода 0/1. JSON-протокол с SHA исходников, флагом незакоммиченных изменений и всеми expected/actual пишется в `output/qa/data-api-<время с микросекундами>.json`; другой путь задаётся `--report`. Каталог `output/` в `.gitignore`. Для независимых запусков используйте разные пути, чтобы не перезаписать предыдущий результат.

`sourceBefore` и `sourceAfter` содержат манифесты с хешами файлов, включая незакоммиченные и неигнорируемые новые файлы. Используется общий `source_snapshot` из `check_miniapp.py`. Изменение байтов исходников или HEAD во время сборки/проверки даёт FAIL `source-unchanged`; один SHA с пометкой dirty не считается фиксацией исходников. Во время прогона не редактируйте проект и не переключайте ветку.

Сбой подготовки, входа, HTTP-запроса, SQL, чтения логов или очистки сохраняется в JSON как FAIL и приводит к коду 1, даже если предыдущие публичные проверки прошли. Исключения сохраняются только по имени типа, без текста, URL или SQL. При недоступном пути самого JSON скрипт возвращает 1 и печатает `report-write` с типом ошибки; создать файл в недоступной папке невозможно.

## Роли и подготовка (внутри одноразового стенда)

| Аккаунт | Роль | Как получена |
|---|---|---|
| author | RESIDENT дома А | одноразовое приглашение → `POST /memberships/claim`, как у настоящего жильца |
| dispatcher | DISPATCHER дома А | запись оператора в SQL, как `seed_stand.py dispatcher` |
| stranger | RESIDENT дома Б | приглашение дома Б → claim |

У каждой роли свой cookie jar и свой CSRF, полученный заново после входа (сессия меняется при логине). Вход — `POST /api/v1/auth/max` с initData, подписанным тестовым ключом этого стенда. Внутренние UUID берутся из `/me`. Проверяется точная матрица ролей: у каждого ровно одно ожидаемое членство, три `userId` различны. Дом выбирается по известному ID, не `memberships[0]`.

## Сценарий одного прогона

У каждого прогона новый `runId`, а ключи идемпотентности имеют вид `data-api-<runId>-<операция>`. Тела собираются словарями и сериализуются штатным JSON, поэтому версии и раунды уходят числами. Каждая следующая команда строится из последнего ответа сервера, версии «на глаз» не увеличиваются.

| Check | Роль и запрос | Что сравнивается |
|---|---|---|
| create-case | author: POST /cases | 201, DRAFT, дом А, authorId автора, тот же текст |
| patch-items | author: PATCH /cases/{id}/items | ровно два пункта: LIGHTING «Подъезд 1, этаж 3» «Не горит свет», затем ENTRANCE_DOOR «Подъезд 1, вход» «Дверь не закрывается» |
| confirm-case | author: POST /confirm (caseVersion, sourceRevision) | CONFIRMED, `receipt.confirmedAt`, progress = 2/0/0/2/false, JSON-типы |
| read-case | author: GET /cases/{id} | те же itemId, 0/2 |
| dispatcher-queue | dispatcher: GET /cases?houseId=A&queueState=NEEDS_ACCEPTANCE, с пагинацией | обращение в очереди; пустой список — FAIL |
| accept-case | dispatcher: POST /acceptance | `acceptedAt`, `acceptedBy` = UUID диспетчера, 0/2 |
| queue-after-accept | dispatcher: та же очередь | обращения там больше нет |
| set-door-next-action | dispatcher: **PUT** /items/{door}/next-action | шаг только у двери, owner — диспетчер, срок совпал, оба пункта NOT_ASSIGNED/NOT_RECEIVED, 0/2 |
| save-light-report | dispatcher: POST /cases/{id}/reports, targetItemIds = свет **и** дверь | 201, `report.links = []`, scope из двух пунктов, **все пункты байт-в-байт прежние**, 0/2, анализ QUEUED или MANUAL_REQUIRED |
| read-saved-report | author: GET /reports/{id} | тот же отчёт, текст, scope, связей нет |
| link-report-to-light | dispatcher: POST /reports/{id}/links, **только свет** | свет REPORTED_DONE, раунд +1, NOT_RECEIVED; дверь идентична снимку после next-action; 0/2 |
| observe-light-restored | author: POST /items/{light}/observations, RESTORED, AFTER_REPORT | свет RESTORED в том же раунде; дверь идентична; **2/1/0/1/false** |
| read-partial-result-author/-dispatcher | GET /cases/{id} обеими ролями | ответ полностью совпадает с ответом наблюдения |

Снимок двери берётся **после** next-action, потому что сам шаг законно меняет её `itemVersion`. Любое отличие двери после отчёта, связи или наблюдения — FAIL.

У каждого отказа проверяются статус, `application/problem+json`, стабильный `code`, заголовок `X-Request-Id` и отсутствие посторонних полей (допустимы `type, title, status, code, requestId, instance`).

Общие проверки: публичные `/csrf`, 401 `AUTH_REQUIRED` для `/me` и `/cases` без сессии, SHA стенда из `/actuator/info` совпадает с исходниками; все прогоны завершились и создали разные обращения; в логах стенда нет известных тестовых секретов и текста обращения или отчёта. В памяти для проверки логов сохраняются все отправленные initData, поколения cookies и CSRF, включая анонимные и прежние значения до входа, коды приглашений и случайные серверные секреты. В результат выводятся только количество совпадений и признак найденного текста. Недоступные логи не считаются чистыми. Этот поиск известных значений не заменяет отдельный аудит логирования.

## Проверка самого runner

```sh
python3 -m unittest discover -s scripts -p 'test_check_data_api.py' -v
```

Контрольные тесты выполняются без сети и Docker, в CI идут сразу после checkout в job `backend`. Они воспроизводят прежний ложный PASS после четырёх публичных проверок и ошибки входа, непредвиденные исключения HTTP/SQL, сбои сборки, логов, очистки, смену исходников и ротацию секретов. ## Найденный и исправленный дефект: requestId в теле доменных отказов

[api.md](../api.md) обещает `requestId` в теле любой ошибки. Отказы из фильтров (401/403 CSRF/404/411/413) и `/error` его несли. Исправление в этой же ветке, бизнес-логика, контракт и DTO не менялись:
- `RequestIdFilter.addTo(problem, request)` кладёт id текущего запроса в тело, то же значение, что и в заголовке;
- `CaseExceptionHandler` и оба обработчика `AuthExceptionHandler` вызывают его;
- `ErrorResponsesHttpTest.domainRefusalsNameTheirRequestInTheBodyToo`: 404 `RESOURCE_NOT_FOUND`, 403 `INVITATION_REJECTED`, 401 `INVALID_MAX_INIT_DATA` несут в теле тот же `requestId`, что в заголовке.

## Что остаётся OPEN

- **Доступ оценщика (часть DAPI-04, затем DAPI-06/07).** Самостоятельный новый вход, выдача ролей и исполнение подстановок в среде технической оценки не подтверждены. Требуемые условия перечислены выше; статические cookies не обеспечивают доступ на весь период.
- **Реальный MAX/G2.** Локальный runner подписывает запуск тестовым ключом только своего одноразового стенда. Приёмка трёх настоящих аккаунтов и физических клиентов остаётся за командой.
- **Публичные тестовые роли и независимый повтор.** Новый YAML не запускает seed и не меняет публичную базу. Подготовка и отдельный повтор Софьей остаются по плану.
