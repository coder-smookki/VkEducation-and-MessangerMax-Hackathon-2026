## RULES: причина и граница гарантии

`ml/app/features/inference/rules_analyzer.py` ищет подстроки категорий и маркеры выполненных/планируемых работ. `_positive_hits` проверяет короткое окружение перед словом, `_classify` выбирает REPORTED_DONE при найденном положительном маркере. `_item_clauses` может потерять условие/опровержение или адрес в соседнем предложении. `analyze_item` не знает о конкурирующем пункте той же категории.

Повторный разбор подтвердил системные ошибки:

- Условие, вопрос и опровергнутая цитата могут стать REPORTED_DONE.
- Два пункта LIGHTING на разных этажах получают REPORTED_DONE из одного отчёта «Лампу заменили» без места.
- Для пункта на третьем этаже фраза «На 2-м этаже лампу заменили» ошибочно подходит: форма `2-м` не распознаётся текущим извлечением места.
- В «Освещение восстановлено, замечаний не поступало» отрицание относится к замечаниям, но получается CONFLICT.

Абсолютную правильность интерпретации произвольного русского текста обещать нельзя. Можно обеспечить: ограниченную область распознавания, воздержание при неоднозначности, проверяемую цитату и отсутствие автоматических предметных действий. REPORTED_DONE означает утверждение в отчёте, а не доказанный физический ремонт. Связь диспетчера и наблюдение автора остаются отдельными командами Java.

## Варианты и рекомендуемое решение

| Вариант | Что даёт | Ограничение |
| --- | --- | --- |
| Существующий ручной выбор пункта и типа сведений | Определённое поведение без ошибочных автоматических выводов | Диспетчер читает текст сам; нужна полная блокировка показа старых подсказок при выключении |
| Консервативный RULES v3 с воздержанием | Объяснимые подсказки на ограниченном наборе конструкций, без новой инфраструктуры | Меньше покрытие; требуется независимая языковая проверка |
| Морфология/синтаксический разбор плюс правила | Помогает связывать действие, объект и отрицание, учитывать формы слов | Не решает автоматически смысл цитаты/времени; добавляет модель и проверку ресурсов/сборки |
| NLI/классификатор/LLM | Кандидат для расширения покрытия после измерения на данных проекта | Нельзя считать качество доказанным по названию модели; нужны размеченный набор, измерение ошибок, latency и fallback |

Рекомендация для текущего кандидата: сохранить ручной путь, реализовать ограниченный v3 в существующем Python-модуле и включать его только после приёмки. Новый сервис, брокер, генеративная модель и БД Python для этого не нужны.

### Поведение v3

1. Один раз разобрать исходный отчёт в утверждения с исходными offsets. Сохранить существующую карту Unicode code points; не вычислять evidence по изменённой строке.
2. Для каждого утверждения определить объект/место, действие, отрицание именно этого действия, план/время, вопрос/условность, цитирование и возможное опровержение в контексте. Не применять общий запрет на любое слово «не» или «если» во всём отчёте.
3. Сопоставить утверждение со всем переданным набором target items. При двух подходящих пунктах и недостаточном месте не размножать выполнение на оба. Не выдумывать неизвестный адрес и не переносить адрес между предложениями без однозначной связи.
4. Разрешить REPORTED_DONE только для распознанного утвердительного сообщения о выполнении/результате по конкретному пункту. План -> PLANNED; прямое сообщение о сохраняющемся симптоме -> SYMPTOM_PERSISTS. «Не заменили лампу» само по себе не доказывает, что свет сейчас не работает.
5. Вопрос, условие, гипотеза, старая/опровергнутая цитата, неясный объект -> INSUFFICIENT_INFORMATION с evidence=null. Однозначно другое место -> UNRELATED. Явное неразрешённое противоречие по одному объекту -> CONFLICT, только если его можно показать достоверной цитатой; иначе воздержание.
6. Evidence не должна обрезать условие/отрицание/опровержение. Если один диапазон не позволяет корректно обосновать вывод в текущем контракте, воздержаться. Не расширять DTO до списка цитат ради этого исправления.
7. Возвращать по одному результату для каждого исходного item с теми же ID/версиями. Разбор ничего не сохраняет в продуктовую БД и не вызывает предметные команды.

Это можно сделать внутри существующих `analyze_rules`, разбора контекста и классификации; существующие enum, HTTP-контракт и ручной UI достаточны. Внутренние причины отказа полезны для тестов, но не требуют новой публичной модели данных.

### Выключение и обновление анализатора

В текущем коде одного `ANALYSIS_ENABLED=false` недостаточно. `CaseService.saveReport` прекращает создание jobs, `AnalysisConfig` отключает расписание, но `CaseService.getSuggestions` не проверяет этот флаг. Старый READY продолжает читаться, QUEUED может оставаться в ожидании. `readyOrStale` проверяет sourceRevision/contentVersion/workRound, но не modelVersion. Перезапуск Python с v3 сам по себе не инвалидирует v2 в БД.

Нужно в существующем слое Java:

- Сначала проверить право на отчёт, затем при выключенном анализе возвращать MANUAL_REQUIRED без результата для любой сохранённой job.
- Проверять разрешённые mode/modelVersion при выдаче и при сохранении результата worker. Старый v2 скрывать как STALE без содержимого; новая версия метки сама по себе не является доказательством качества.
- Проверить гонку ответа старого Python во время выпуска, ранее сохранённый READY, QUEUED после выключения и кэш открытого frontend.
- Не менять уже подтверждённые человеком links, workRound, наблюдения и историю задним числом. Повторный анализ старых отчётов не обязателен для безопасного ручного пути и не должен стартовать при GET.

### Проверка результата

- Известные ошибки становятся регрессионными примерами; добавить варианты порядка слов, пунктуации, адресов, одинаковых категорий и отрицаний разных действий.
- София готовит отдельный неизвестный разработчику набор. После просмотра и подгонки он перестаёт быть holdout.
- Считать число пунктов/отчётов, ложные REPORTED_DONE, точность связки item/evidence, качество по каждому классу, покрытие и долю отказов. При нуле предсказаний precision=null. «Всегда недостаточно сведений» не считается полезным анализатором: простые однозначные контрольные примеры должны распознаваться.
- По Q-06 ложноположительный вывод блокирует включение соответствующей подсказки. Нулевые ошибки на конечном наборе не означают 100% точность будущего текста.
- После Python-тестов проверить Java-валидацию, версии/выключение и frontend, затем настоящий основной сценарий: свет 1/2, дверь не подтверждена.

## DATA-API: что уже работает, а чего нет в файле

Backend и Mini App уже имеют отчёт, подтверждение связи, наблюдение и прогресс. В `DATA-API.yaml` отсутствует описание их проверки. Сейчас 11 checks заканчиваются приёмом и чтением истории. Expected проверяет коды/формат/наличие полей, но не значения прогресса. Поэтому даже ошибочный прогресс 2/2 мог бы удовлетворить проверке наличия поля `progress`.

Дополнительные проблемы описания:

- `${houseId}` берётся из `memberships[0]`, без проверки нужного учебного дома и роли.
- Нет начальной проверки dispatcher/stranger и их изоляции.
- После acceptance не извлекается новая caseVersion. Confirm также меняет itemVersion, а saveReport меняет caseVersion, хотя не меняет состояние пунктов.
- Постоянные `data-api-v1-*` ключи возвращают старые результаты команд. Это полезно для проверки replay, но не создаёт новый независимый прогон; данные и очереди могли уже измениться.
- В предоставленных правилах есть требования к содержанию файла, но не подтверждён точный язык `dependsOn`, `extract`, подстановок и проверок значений. Совместимость с реальным runner организаторов требует шаблона/валидатора либо уточнения. Не добавлять выдуманный DSL.

### Дополнить проверку основной цепочкой

| Шаг | Роль и HTTP | Что проверить |
| --- | --- | --- |
| Контекст | GET /api/v1/me отдельно каждой ролью | Общий дом А у автора/диспетчера, дом Б у постороннего, нужные активные роли |
| Черновик/пункты/confirm/acceptance | Существующие операции | Новый caseId, ровно свет+дверь, свежие версии после каждой команды, прогресс 0/2 |
| Следующий шаг двери | Диспетчер: PUT /api/v1/items/{itemId}/next-action | Изменился только план двери; это не выполнение |
| Сохранение отчёта | Диспетчер: POST /api/v1/cases/{caseId}/reports | Отчёт «Лампу заменили» сохранён; у пунктов прежние workRound/observation, прогресс 0/2 |
| Явная связь только света | Диспетчер: POST /api/v1/reports/{reportId}/links | Свет REPORTED_DONE, его раунд увеличен, наблюдение NOT_RECEIVED; дверь не изменилась, прогресс 0/2 |
| Наблюдение света | Автор: POST /api/v1/items/{itemId}/observations | AFTER_REPORT/RESTORED относится к текущим version/contentVersion/workRound; стало 1/2 |
| Чтение двумя ролями | GET /api/v1/cases/{caseId}, отчёт и история | total=2, confirmed=1, withdrawn=0, remaining=1, allConfirmed=false; одинаковое состояние у автора и диспетчера |
| Чужой дом | GET case/report/history посторонним; запрещённая команда | Отказ без текста и изменения данных; не просто отсутствующая кнопка |
| Повтор/конфликт | Отдельные контролируемые проверки | Тот же key/body - один эффект; тот же key/другое body - отказ; старые версии не перезаписывают актуальное состояние |

Создание отчёта возвращает reportId в `report`, актуальные версии в `case`. Для остальных команд извлекать версии из фактического ответа/нового GET, не вычислять `+1` на клиенте. После confirm заново взять itemVersion; после links - текущий workRound. Item IDs связать с содержимым тестовых пунктов, не считать фиксированными и не полагаться на порядок без проверки категорий. Для next-action ownerId - внутренний UUID диспетчера из /me, не MAX ID. Будущую дату обновления вычислить один раз на новую команду; при retry сохранить то же тело и дату.

Для нового прогона нужен runId и отдельное новое учебное обращение. Ключ команды имеет область runId + шаг; сетевой повтор сохраняет key/body, новый прогон получает новые ключи. Прежние три обращения не очищать. Проверку повторов отделить от основной цепочки, чтобы повтор старого ответа не маскировал отсутствие новой работы.

## Повторный вход: уточнение предыдущей формулировки

`server.servlet.session.timeout: 30m` - предел бездействия HttpSession, не абсолютные 30 минут после login. Связанные с сессией запросы обновляют время доступа; печать текста сама по себе этого не делает.

`MAX_AGE=5min` в MaxInitDataValidator - собственная серверная политика свежести initData при POST /auth/max, не заявленное требование MAX и не срок действующей сессии. Уже вошедший пользователь не вылетает через пять минут.

Frontend сначала читает /me. Если сессия жива, reload продолжает работу. При её потере и свежем initData выполняется новый login. При старом initData нужно закрыть Mini App и открыть из бота: reload не делает подпись новой. Интерфейс уже предлагает повторный вход и копирование несохранённого ввода. Роли, дома и сохранённые обращения остаются в PostgreSQL. Перезапуск текущего backend теряет HttpSession, но не эти данные.

### Что нужно организаторам

1. Постоянная ссылка запуска MAX и понятный сценарий ролей. Первое назначение доступа выполняется один раз: реальные разные аккаунты, приглашения жильцам, контролируемая выдача DISPATCHER оператором. При новом входе заново выдавать роли не нужно.
2. Раздельные устройства/браузерные контексты для ролей. Три вкладки одного профиля разделяют cookie и не являются тремя независимыми аккаунтами.
3. Перед API-прогоном проверить /me; при необходимости получить свежую сессию через обычный MAX-вход. CSRF получать отдельно в том же cookie jar каждой роли. Один анонимный GET /csrf не авторизует остальные запросы.
4. Для браузерной автоматизации можно продолжить HTTP-проверки в авторизованном browser context. Передача бот-токена и искусственная подпись запуска проверяющим для этого не требуются.
5. Для внешнего HTTP-only runner выяснить поддержку подготовительного MAX-входа, браузерного контекста или обновления приватных переменных непосредственно перед прогоном. Сейчас автоматического бессрочного получения новой MAX-сессии у такого runner нет.

Подготовленные заранее cookies пригодны только для короткого согласованного запуска. Они не решают доступ через сутки, после простоя или рестарта. Продление срока до бесконечности, снятие HMAC/CSRF или публичный вход по userId не являются исправлением. Если платформа требует иной способ машинной аутентификации, его необходимо отдельно согласовать и спроектировать с ограниченными правами; новый обход входа не добавляется молча.

## Распределение и порядок

- Семён: Python v3, Java-политика выдачи подсказок/версий, тесты выключения и старых READY; полнота DATA-API и подготовка ролей.
- Кирилл: корректные состояния подсказок и их кэш, ручная форма, повторный вход; интеграция инструкции доступа и проверок API.
- София: независимый набор, изоляция домов/ролей, значения прогресса, повторяемость свежего прогона и доступ после бездействия/рестарта.
- Параллельно можно готовить DATA-API и независимые примеры. Включение v3 и финальный G2 идут после интеграции на одном зафиксированном SHA.

Уточнение к прежнему QA-плану: повторный приём уже принятого обращения с новым ключом даёт 422 INVALID_TRANSITION, а не гарантированный 409. Для проверки 409 использовать действительный конфликт версий, например две формы следующего шага. Проверять ровно задокументированный код, а не «любую ошибку».

Источники: текущие rules_analyzer.py, CaseService/AnalysisConfig, DATA-API/OpenAPI, AuthController/MaxInitDataValidator/application.yml, App/client; предоставленный кейс с.10 и FAQ п.12. Для рассмотренного варианта синтаксических правил сверена [официальная документация spaCy](https://spacy.io/usage/rule-based-matching#dependencymatcher); для входа - [MAX validation](https://dev.max.ru/docs/webapps/validation). Предлагаемые изменения ещё не реализованы и не являются новой метрикой качества.
