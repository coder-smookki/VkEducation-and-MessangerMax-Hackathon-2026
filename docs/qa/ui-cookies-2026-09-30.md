## Причина и исправление

1. У Софьи был сохранён пустой черновик: 0 пунктов. Java корректно запрещает его подтверждение. Неправильно было приглашать к подтверждению после сохранения пустого списка. Теперь отдельны «Сохранить список» (допускает пустой черновик) и «Перейти к проверке» (нужен хотя бы один заполненный пункт). Успех отображается только после ответа Java; подтверждение содержания не считается ремонтом.
2. При попытке продолжить пустые/слишком длинные поля получают красную рамку и `aria-invalid`, фокус переходит к первому. По последнему поручению пользователя видимые красные подписи убраны: одно красное всплывающее уведомление объясняет заполнение/лимит. Индивидуальное объяснение остаётся скрытым только визуально и связано с полем для экранного диктора. Незаполненное поле не показывает ошибочную подпись «сократите текст» у нулевого счётчика. Дополнительный FAIL проверки итогового цвета выявил, что общий input-селектор перебивает border-color ошибки; исправлена специфичность правила, фокус и граница теперь одного красного цвета. Прогон до исправления сохранён, повторы не маскируются как flaky retry.
3. Командные ошибки, сохранение черновика и подключение дома используют общий `Toast` через portal. Успех исчезает через 8 секунд, чтение мышью/клавиатурой приостанавливает таймер. Ошибка остаётся до закрытия/исправления; requestId и повтор неизвестного исхода сохранены. Важные ошибки загрузки/409 со сверкой остаются частью страницы. Первоначальный нижний toast перекрывал нижние действия: сохранён FAIL, размещение перенесено наверх с safe-area, ограничением высоты и прокруткой. Без анимации при reduced motion.
4. В профиле соседние ссылки обёрнуты в существующий `.actions`; `.form-actions` переносит кнопки с gap. Уменьшены отступы формы, шага и карточек без уменьшения доступных кнопок. Убрана лишняя верхняя граница/пустота первой строки facts.
5. В HTTPS iframe с запретом сторонних cookies воспроизведён 403 `CSRF_TOKEN_INVALID`: браузер блокировал XSRF-TOKEN/JSESSIONID. При первом исправлении только session cookie получала `Partitioned`; Spring Security 7.1.1 теряет атрибут при преобразовании ResponseCookie в Servlet Cookie. Исправлена ответственная серверная политика через штатный Tomcat RFC6265 cookie processor. Обе cookies на HTTPS получают `Secure; SameSite=None; Partitioned`; JSESSIONID сохраняет HttpOnly. Локальный HTTP с Secure=false остаётся без Partitioned. CSRF-заголовок, подпись/свежесть MAX и серверные Membership обязательны. Новые endpoints, токены в URL/localStorage, миграции и ослабление авторизации не добавлены.
6. Диагностика CSRF пишет только тип отказа и наличие cookie/заголовка с существующим requestId. Значения токенов, cookies, initData и текст обращения в новые логи не попадают. Конкретный requestId со скриншота Семёна в прежних логах не найден: прежний отказ не логировался. Причина доказана воспроизведением класса ошибки, а не найденной телефонной трассой.
