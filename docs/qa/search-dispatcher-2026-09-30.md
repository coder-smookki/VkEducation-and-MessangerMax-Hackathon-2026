# Поиск и рабочее место диспетчера - 30.09.2026

Задачи K-02/K-06, QA-E07/E12. База интеграции `530c36a`, ветка `dev`. Реальные обращения, роли и рабочая БД сохраняются. Снимки и машинные результаты - вне Git.

## Причина и поведение

На скриншоте «Свет» встречается в исходном тексте черновика и во втором пункте другого обращения. Прежний фильтр находил обе карточки правильно, но всегда показывал первый пункт - дверь. Совпадение было скрыто. Теперь карточка показывает найденный пункт, его номер/тему/место; совпадение только в исходном тексте показывает соответствующий фрагмент. Отозванный/архивный пункт остаётся явно подписанным и не считается выполненным. Поиск проверяет номер, исходный текст, описания, места и темы пунктов; регистр, повторные пробелы и е/ё нормализуются. Посторонние карточки скрываются, нулевой результат отличается от ошибки API, очистка возвращает список.

Это поиск по загруженным доступным карточкам выбранного дома. API не предоставляет глобальный текстовый поиск. При наличии nextCursor остаются честная подпись области поиска и «Загрузить ещё»; нельзя объявлять результат поиском по всей базе. Данные берутся из Java, fixtures существуют только в UI tests. Новый публичный endpoint не добавлен.

Диспетчер получает рабочую очередь с компактными карточками на телефоне и таблицей на большом экране. Вместо создания обращения на главной странице - фильтры существующего queueState: все, NEEDS_ACCEPTANCE, NEEDS_ACTION, AWAITING_AUTHOR, ARCHIVED. Эти выборки пересекаются и не выдумывают взаимоисключающие статусы. Приём, следующие шаги, отчёты и наблюдения по-прежнему используют существующие серверные команды. Навигация: «Очередь», «Дома», «Профиль». Прямой переход в /new в этом рабочем контексте возвращает к очереди; при смене дома на RESIDENT возвращается интерфейс жителя. Это разделение интерфейса, не изменение авторизации Java: действующий backend разрешает создание любому активному Membership; собственные прежние обращения и их история не удаляются.
