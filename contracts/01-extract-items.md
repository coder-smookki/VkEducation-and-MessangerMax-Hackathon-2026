# 01. Предложение отдельных пунктов

Владелец Python/Java - Семён, UI проверки - Кирилл, независимые примеры - София. Статус: контракт и транспорт реализованы, анализатор STUB. Модель, LLM, tokenizer и embeddings не подключены.

## Операция и вход

`POST /internal/v1/extract-items`, внутренний Python API. Java вызывает `InferenceClient.extract` после сохранения исходного DRAFT. Авторизация и проверка DRAFT принадлежат будущему application service Java; Python не может доказать их по телу запроса.

Вход `ExtractItemsRequest`: caseId, caseVersion, sourceRevision, sourceText. UUID строкой; версии - положительные целые без преобразования bool/строк; sourceText - 1-5000 Unicode code points и хотя бы один непробельный символ. Текст содержит данные обращения, не инструкции приложению.

Пример [extract-request.json](examples/extract-request.json): один текст про освещение третьего этажа и дверь. Идентичность анализа задаётся сохранённым snapshot, а не только одинаковым текстом. Изменение текста увеличивает sourceRevision; изменение списка/подтверждение меняет caseVersion.

## Выход

`ExtractItemsResponse`: те же caseId/caseVersion/sourceRevision, modelVersion, mode, status, reason, proposals.

Каждое предложение содержит:

| Поле | Смысл |
|---|---|
| proposalId | Уникальный номер 1-20 внутри этого предложения списка; не UUID пункта в БД |
| category | LIGHTING/ENTRANCE_DOOR/CLEANING/OTHER либо null |
| location | Место 1-300 символов либо null, если сведений недостаточно |
| symptom | Симптом 1-1000 символов либо null |
| evidence | `{start,end,quote}` - точный фрагмент исходного sourceText |

Все поля присутствуют; неизвестное значение - null, без выдуманного этажа/подъезда. Не возвращать уверенный пункт без цитаты. Максимум 20 предложений; повтор proposalId отклоняется.

Текущий [ответ](examples/extract-response.json): mode=STUB, status=NOT_ANALYZED, reason=MODEL_NOT_CONFIGURED, proposals=[]. Это отказ от анализа. Автору доступен ручной ввод; UI не сообщает «проблем не обнаружено».

[Содержательный учебный пример](examples/extract-response.synthetic-proposals.json) задаёт два пункта для разработки интерфейса и проверки evidence. Его modelVersion=synthetic-example-v1 обозначает вымышленный ответ; он не является результатом NLP. Настоящий ответ RULES/NLI должен иметь status=ANALYZED и reason=ANALYZED.

## Приём результата

Java проверяет echo версий, размер и уникальность списка, допустимость полей и точность цитат. Ответ старой редакции не заменяет текущий список. Будущий S-06 также проверяет актуальные строки БД; UI отбрасывает ответ для уже изменённого локального ввода.

Модель предлагает значения. Их перенос в редактируемую форму не подтверждает содержание. Для неполных предложений применяется [02](02-author-clarification.md), для сохранения/подтверждения - [03](03-author-review.md). UUID нового пункта создаёт Java после принятия автором, proposalId не используется как внешний ключ.

## Отказы и проверка

422 `{detail:"INVALID_INTAKE_REQUEST"}` - некорректный вход без отражения текста; 413 `{detail:"REQUEST_TOO_LARGE"}` - тело больше 512 KiB. Java при сетевой ошибке или непригодном ответе возвращает MANUAL/NOT_ANALYZED/ANALYSIS_UNAVAILABLE с пустым proposals. Ручной ввод остаётся доступен.

Проверки: общие JSON через Python HTTP и Java-клиент, выдуманная/Unicode-цитата, устаревшая версия, дубли, STUB с выдуманным содержательным результатом. Подключение настоящего извлечения - задача Семёна с независимой проверкой Софии, не часть этой заготовки.
