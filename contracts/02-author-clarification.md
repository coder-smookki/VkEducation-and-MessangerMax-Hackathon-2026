# 02. Уточнение только у автора

Это уточнение содержания обращения: где находится проблема и что именно происходит. Основание - пункт PDF о вопросах только автору. Диагностика причины аварии, опросы соседей и зависимость от чужих ответов не входят в этот контракт.

Владелец правил/типа - Никита, проверка получателя/версий - Семён, форма и доставка MAX - Кирилл. Сейчас детерминированная проверка работает в Python; отправка вопросов пользователю не реализована.

## Операция

`POST /internal/v1/clarify-items`. Java `InferenceClient.clarify` передаёт caseId, caseVersion, sourceRevision и 1-20 draft-items. У item: уникальный proposalId и обязательные поля category/location/symptom, которые могут быть null. Это проверка предложений перед сохранением полного списка, а не изменение БД.

[Вход](examples/clarify-request.json): для света неизвестно место; дверь описана полностью. Пустая строка не заменяет null. Если список пуст, пользователь сначала добавляет пункт вручную либо получает предложения через 01.

## Работающие правила

Правило `required-fields-v1` проверяет только отсутствие значений. Никакого обращения к ML-модели нет; mode=RULES относится именно к проверке полей, а не к семантическому анализу текста.

| Отсутствует | Код field | Вопрос автору |
|---|---|---|
| Категория | category | Выберите тип проблемы: освещение, входная дверь, уборка или другое. |
| Место | location | Где находится проблема? Уточните подъезд, этаж или вход. |
| Симптом | symptom | Что именно не работает или требует исправления в этом месте? |

Ответ повторяет caseId/caseVersion/sourceRevision, сообщает recipient=AUTHOR, modelVersion=required-fields-v1 и возвращает ровно один результат на каждый proposalId. У результата readiness и questions. Вопрос содержит field и text; максимум три вопроса на пункт. Готовому пункту соответствует READY_FOR_REVIEW и пустой questions. Неполному - NEEDS_DETAILS и ровно вопросы по отсутствующим полям.

[Выход](examples/clarify-response.json) задаёт один вопрос про место света и ни одного про дверь. READY_FOR_REVIEW означает «можно показать автору для проверки», а не «пункт подтверждён» и не «ремонт выполнен».

## Получатель и ответ пользователя

1. Java устанавливает автора из service_case.author_id и проверяет текущий доступ. Подставленный userId/chatId в HTTP-теле не даёт права получать вопросы или отвечать.
2. Python получает только текстовые поля и версии; userId, список соседей, chatId и команды отправки в контракте отсутствуют. Дополнительный recipient во входе отклоняется.
3. Для MVP показывать вопросы в форме этого автора. Если подключается MAX, его адрес определяется Java по проверенному аккаунту автора; ставится один адресный outbox с повторной проверкой версий и получателя перед отправкой.
4. Автор исправляет значения в форме. Повторная 02-проверка показывает актуальные недостающие поля. Полностью заполненный список сохраняется через PATCH из 03; затем автор отдельным действием подтверждает его.
5. Не требовать от автора осматривать опасные места, обращаться к соседям или определять техническую причину. Если точности нет, форма допускает честное описание доступного места/симптома и ручной разбор диспетчером.

Уточнение необязательно как отдельный диалог: заполнить те же поля в форме достаточно. Оно не требует согласования с другими жителями. Отсутствие ответа не создаёт подтверждённый пункт, не закрывает проблему и не запускает бесконечные напоминания.

## Отказы и совместимость

Java проверяет единственного получателя AUTHOR, полное соответствие proposalId, версии, набор полей вопросов и readiness. Устаревшее уточнение не затирает ввод. При недоступности Python `clarify` возвращает Optional.empty: сохранить ручную форму и не отправлять вопрос из непроверенного ответа.

Python: 422 INVALID_INTAKE_REQUEST, 413 REQUEST_TOO_LARGE; схемы содержат фактические ошибки. Семён/Кирилл ещё должны реализовать проверенный пользовательский маршрут и адресную доставку. Тест валидатора AUTHOR не считается работающей аутентификацией или успешной отправкой MAX.
