# 04. Поиск одинаковых и похожих обращений

Владельцы: Семён - Java/Python, права, снимки БД, Kafka и производный индекс; Кирилл - отображение. Актуальная основа в `dev`: защищённая выборка Java, Kafka consumer, Chroma, сравнение отдельных пунктов и явный отказ. Пользовательский endpoint и постановка событий индексирования из действующего CRUD ещё не подключены. В опубликованном release Kafka выключена; Mini App не выдаёт эту заготовку за работающий поиск.

## Кто выбирает кандидатов

`SimilarCasesService.find(verifiedUserId, caseId, limit)` - внутренняя Java-операция. `verifiedUserId` должен поступать из проверенной серверной сессии; сервис не принимает клиентскую роль или готовый список разрешений. Он не вызывается внутри транзакции изменения обращения.

1. Java читает `query` и Membership из PostgreSQL. Нужен CONFIRMED; каждый пункт должен иметь подтверждённую текущую редакцию.
2. Житель и исполнитель как автор могут сравнивать только свои обращения. Диспетчер - подтверждённые обращения доступного дома. Назначение исполнителю отдельных пунктов не даёт доступ к полному чужому обращению. DRAFT, чужой дом и само query исключаются.
3. Java берёт до 20 допустимых обращений: `created_at DESC, id` для стабильного порядка. Это ограниченная выборка, а не доказательство проверки всей БД. Она дополнительно уменьшается до фактических 512 KiB JSON в UTF-8.
4. Снимки query и кандидатов читаются в одной короткой read-only транзакции REPEATABLE_READ. HTTP идёт после её завершения.
5. После HTTP Java в новой транзакции повторяет проверку доступа и сравнение полных снимков query и всех переданных кандидатов. Смена версии/пунктов/раунда или потеря доступа к кандидату даёт MANUAL/NOT_ANALYZED. Потеря доступа к самому query отклоняет операцию.

`InferenceClient.similar` имеет пакетный доступ: продуктовый код использует `SimilarCasesService`, чтобы не обходить проверки БД. Новых открытых HTTP-маршрутов нет.

## Внутренний HTTP

`POST /internal/v1/similar-cases`: `{query, candidates, limit}`.

- Query и 0-20 кандидатов имеют полный [ConfirmedCaseContext](03-author-review.md), положительные версии и 1-20 пунктов.
- `limit` - 1-20, по умолчанию 5 на Python. Это максимум возвращаемых совпадений.
- Все кандидаты того же дома; caseId уникальны, query не входит в список, itemId не делятся между обращениями.
- Python ищет только в переданном списке. Он не расширяет разрешения, не читает PostgreSQL и не запрашивает соседние страницы.
- Прежний запрос `query+limit` без candidates отклоняется: выводить права доступа из одного houseId нельзя.

[Пример запроса](examples/similar-request.json) - «свет + дверь» и кандидат только про дверь. [Базовый ответ](examples/similar-response.json) - честный отказ, пока этот кандидат не проиндексирован. Все данные синтетические.

## Kafka и согласованность индекса

`CaseEventPublisher` возвращает future подтверждения Kafka; вызывающий worker обязан обработать успех/ошибку. Вызовы индексирования из команд сохранения и транзакционный outbox именно для Kafka ещё не подключены (обычный outbox доставки MAX уже работает): отправка после commit сама по себе не гарантирует доставку при падении между БД и Kafka.

Топик `koren.case-updates`, ключ - caseId в UTF-8. Событие `{eventId, eventType, schemaVersion, case}`: тип CASE_CREATED/CASE_UPDATED, schemaVersion строго 1, case - полный CONFIRMED snapshot. Consumer сверяет ключ и снимок. Java использует Boot Kafka starter и JacksonJsonSerializer; заголовки Java-типа не отправляются.

Для MVP топик хранит всю историю (`cleanup.policy=delete`, `retention.ms=-1`, `retention.bytes=-1`). Компакция по caseId здесь непригодна: последним доставленным событием может оказаться версия 6 после версии 7. Удаление истории или ограниченная retention потребуют предварительного backfill из Java/PostgreSQL. Хранение всей истории имеет цену по диску; это не готовая production-политика хранения.

При каждом назначении partitions consumer делает seek в начало доступной истории, включая повторный старт с прежней группой и пустым индексом. После успешного сохранения подтверждается только `offset+1` обработанной partition. При ошибке валидации, векторов или записи offset не подтверждается; поток повторяет попытку. При выключенном Chroma consumer не стартует. Poison event остаётся видимой ошибкой и не пропускается молча; административное исправление такого события не автоматизировано.

Chroma хранит **один документ на обращение**, содержащий полный снимок и векторы его отдельных пунктов. Сначала вычисляются все векторы, затем выполняется один upsert; предварительного удаления старой записи нет. Писатели одного volume сериализованы файловой и потоковой блокировками. Меньшая caseVersion игнорируется; идентичная повторная версия безопасна; одинаковая версия с другим содержанием отклоняется. Новый дом или уменьшение sourceRevision также отклоняются.

Формат хранится в коллекции с суффиксом `_snapshots_v2`; прежние записи по отдельным пунктам не интерпретируются как новый формат. Индекс восстанавливается из Kafka. Для одной логической группы используется один полный локальный индекс и один активный consumer; независимые реплики с отдельными volumes требуют разных групп. Целевая среда - Linux/Docker, локально поддерживается macOS.

## Сравнение и результат

Chroma служит кэшем подтверждённых снимков и векторов. Для ограниченной разрешённой выборки Python читает записи по ID и ранжирует попарное сходство пунктов. Векторы каждой проблемы вычисляются отдельно через стандартную Chroma `all-MiniLM-L6-v2` (ONNX); полный текст чужих пунктов не добавляется к вектору двери. Это не NLI и не проверка физического ремонта.

Для пары нужны одинаковая category и одинаковое нормализованное location (Unicode NFKC, регистр, ё/е, пробелы). Косинусное сходство менее 0.85 не создаёт связь. Сохранённая пара содержит именно те queryItemId/candidateItemId, по которым считался score. Соответствие взаимно однозначное; порядок входных пунктов не меняет результат.

- RELATED - есть подходящие пары, но полного совпадения обоих списков с score >= 0.95 нет. Дверь из «свет + дверь» не закрывает свет.
- POSSIBLE_DUPLICATE - оба списка полностью сопоставлены, минимальный score пар >= 0.95. Это предложение человеку проверить повтор, не доказанная общая неисправность.
- Кандидат без подходящих пар не включается в results. DIFFERENT и NOT_EVALUATED сохранены в enum для совместимости, текущий алгоритм их не выдаёт отдельными строками.

0.85/0.95 - консервативные начальные параметры, не измеренная точность; Семёну и Софии нужны отдельная разметка, оценка русскоязычных обращений и калибровка. Разные написания места могут дать пропуск; это ограничение текущего алгоритма, не повод расширять права.

Ответ: echo query IDs/версий, modelVersion, mode, status, reason, `scope=CHROMA`, до limit результатов. Результаты отсортированы по score убыванию и caseId; score 0..1 - оценка алгоритма, не вероятность ремонта. Java проверяет допустимость caseId, обе версии кандидата, все пары itemId и числовые значения. Один пункт не участвует в двух парах одного результата; POSSIBLE_DUPLICATE требует покрытия всех пунктов обоих обращений.

Scope означает только переданную Java выборку и её актуальные записи индекса. Отсутствие результата не доказывает отсутствие дубликатов во всём доме.

## Отказ и проверки

Отключённый индекс, отсутствующий/устаревший снимок хотя бы одного кандидата, ошибка модели/хранилища/HTTP дают MANUAL/NOT_ANALYZED/ANALYSIS_UNAVAILABLE с пустыми results. Это не «похожих нет». Только готовый разрешённый набор может вернуть ANALYZED, включая пустой набор допустимых кандидатов. Сохранение исходного обращения от результата поиска не зависит.

422 INVALID_INTAKE_REQUEST - неправильный вход; 413 REQUEST_TOO_LARGE - тело более 512 KiB. Данные обращения не отражаются в ошибке и не попадают в логи. Java использует HTTP/1.1, поддерживаемый Uvicorn без h2c upgrade.

Регрессии: Java IntakeContractTest/SimilarCasesServiceTest/KafkaConfigurationTest, Python test_similarity_index.py/test_index_consumer.py. Реальные Kafka/Chroma/HTTP и повторное восстановление с прежней группой: KafkaIndexIntegrationTest и test_kafka_replay.py; [команды](../docs/development.md).
