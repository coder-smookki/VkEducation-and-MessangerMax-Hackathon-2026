# 04. Поиск одинаковых и похожих обращений

Владельцы - Семён (Java-событие подтверждённого обращения), Никита (индекс и анализ), Кирилл (представление подсказок). Java публикует snapshot после изменения подтверждённого обращения в Kafka; ML индексирует его в Chroma.

## Принцип работы

Java передаёт в Kafka только авторизованный snapshot подтверждённого обращения. Python хранит производную копию в Chroma и сам ищет кандидатов по векторному индексу. Chroma не является источником истины и не используется для изменения статуса обращения.

Событие `koren.case-updates` имеет форму `{eventId, eventType, schemaVersion, case}`. `eventType` — `CASE_CREATED` или `CASE_UPDATED`; ключ Kafka — `caseId`, поэтому изменения одного обращения сохраняют порядок. Java отправляет событие после успешной транзакции изменения статуса/содержания. ML подтверждает offset только после обновления Chroma.

Сравнение не требует генеративного LLM, fine-tuning, RAG или закрытого датасета. Будущий алгоритм выбирает Никита по отдельному замеру; существующие DTO не содержат vectors/embeddings, имя провайдера или ключ доступа.

## Вход

`POST /internal/v1/similar-cases`, Java `InferenceClient.similar`.

`SimilarCasesRequest`: query - [подтверждённый контекст 03](03-author-review.md), limit - от 1 до 20. Кандидаты в запросе отсутствуют: их выбирает ML из Chroma. [Пример](examples/similar-request.json).

Правила подготовки и проверки:

1. Query и каждый кандидат имеют CONFIRMED, положительные версии и 1-20 полных пунктов. Изменяемые предложения модели сначала проходят автора.
2. ML фильтрует результаты по тому же дому; query исключается, caseId не повторяются.
3. До отправки Java проверяет доступ к каждому кандидату. Для автора доступны его собственные обращения; диспетчер может работать с разрешёнными подтверждёнными обращениями дома. Один houseId не даёт права читать обращения других жителей.
4. Chroma ищет только документы того же `houseId`; query исключается из результатов. Индекс наполняется только событиями от Java.
5. Тело целиком не больше 512 KiB. Максимумы отдельных полей/массивов не гарантируют, что их совместный максимум поместится в этот байтовый предел; Java должна разбивать допустимую выборку до отправки.

Scope результата всегда CHROMA. Результат отражает только доступный на момент индексирования набор; отсутствие результата не доказывает отсутствие дубликатов во всей системе.

## Выход

Ответ повторяет caseId/caseVersion/sourceRevision query; добавляет modelVersion, mode, status, reason, scope и results. Ровно один result на каждого кандидата независимо от наличия сходства; порядок не является ранжированием.

Result содержит caseId/caseVersion/sourceRevision кандидата, relation, score и matchedItems. Пара matchedItems: queryItemId + candidateItemId, оба должны входить в соответствующие контексты.

| Relation | Значение |
|---|---|
| NOT_EVALUATED | Сравнение не выполнено или алгоритм отказался; score=null и matchedItems=[] |
| POSSIBLE_DUPLICATE | Предложение проверить повторное сообщение о той же проблеме; не доказанная общая неисправность |
| RELATED | Есть общий пункт/тема, но обращения могут содержать разный остаток |
| DIFFERENT | Анализ переданной пары не предложил общей проблемы; matchedItems=[] |

Для вычисленной relation score - конечное число 0..1, для NOT_EVALUATED - только null. Это оценка выбранного алгоритма, не вероятность физического совпадения. Нужны идентификаторы совпавших пунктов для POSSIBLE_DUPLICATE/RELATED. Сходство только двери не позволяет потерять свет из первого обращения.

Текущий [ответ](examples/similar-response.json) показывает успешный поиск Chroma без совпадений. Пустой results означает отсутствие совпадения в доступном индексе, а не доказательство отсутствия дубликатов.

## Приём, актуальность и отказ

Java проверяет query, echo версий, допустимые пары, score и отказ STUB/MANUAL. Новый itemId или чужой caseId из ответа не попадает в карточку. Перед выдачей Java сверяет query с БД; Chroma остаётся производным индексом.

422 INVALID_INTAKE_REQUEST для неверного scope/формы, 413 REQUEST_TOO_LARGE для тела. При сетевой ошибке/непригодном ответе Java выдаёт MANUAL/NOT_ANALYZED/ANALYSIS_UNAVAILABLE, сохраняя всех кандидатов с NOT_EVALUATED. Ни один отказ не отменяет сохранённое обращение.

## Следующий шаг участников

Никита заменит `similar_cases` содержательным алгоритмом без смены владения БД; сейчас подключать модель и считать векторы не требуется. Семён подключит выборку и job после K1/S1, сохранив права/версии и лимиты. Кирилл покажет подсказку и её ограничения. Решение о любых связях между обращениями потребует отдельного предметного сценария; автоматического merge в этом контракте нет.
