# 05. Отчёт по подтверждённым пунктам

Владельцы - Семён (Python-интерпретация, Java-клиент и актуальность), Кирилл (показ пунктов/цитат). Существующий `/internal/v1/compare` совместим: STUB по умолчанию, RULES включается отдельно. В rules-baseline-v2 предикаты разных субъектов разделены, неоднозначные сочетания дают отказ. Это покрыто test_rules_analyzer.py, но не заменяет независимый holdout. Обученная NLI-модель не подключена.

## Вход и смысл

Схема подтверждённого контекста описана в [03](03-author-review.md). Рабочий AnalysisWorker формирует Request из неизменяемого reportText и всех targetItemIds отчёта; для общей интеграции также существует `ConfirmedCaseContext.comparison`. Вход: caseId/sourceRevision/reportId/reportText/items. Для каждого item передаются itemId/contentVersion/workRound/category/location/symptom.

reportText - 1-5000 Unicode code points; items - 1-20 без дублей. Вызов относится к конкретному неизменяемому отчёту. Актуальность результата Java определяет по sourceRevision и contentVersion/workRound каждого анализируемого пункта; caseVersion не добавлена в wire-контракт и не является самостоятельным критерием устаревания подсказки.

[Пример запроса](examples/compare-request.json) содержит сообщение о замене лампы и два пункта - свет и дверь. Разные workRound допустимы: история работ у каждого пункта своя. Это отдельный учебный момент после подтверждения списка, а не тот же snapshot, что первоначальный confirm-пример 03.

## Выход

Те же caseId/sourceRevision/reportId, modelVersion, mode и ровно одна suggestion на каждый входной item. Suggestion: itemId/contentVersion/workRound/relation/evidence/reason.

- REPORTED_DONE: в тексте заявлено выполнение работы.
- PLANNED: работа только запланирована.
- SYMPTOM_PERSISTS: текст явно сообщает о сохраняющемся симптоме.
- INSUFFICIENT_INFORMATION: достоверных сведений для интерпретации недостаточно.
- UNRELATED: приведённый фрагмент относится к другому объекту/месту.
- CONFLICT: неразрешимо противоречивые утверждения в одном контексте.

Содержательный ответ требует точной evidence-цитаты `{start,end,quote}` в Unicode code points. Отсутствие упоминания двери само по себе не означает UNRELATED или доказанный отказ выполнить работу. Пункт двери обязательно остаётся в списке.

Текущий [STUB-ответ](examples/compare-response.json) отказывается от интерпретации обоих пунктов: INSUFFICIENT_INFORMATION, evidence=null, reason=MODEL_NOT_CONFIGURED. MANUAL при сбое тоже только отказывается, с ANALYSIS_UNAVAILABLE. RULES/NLI обозначают реально подключённый анализ, не настройку желаемого режима.

## Связь с предметной моделью

Подсказка не меняет workStatus, observation, административный статус, назначение или progress. Диспетчер отдельно подтверждает допустимые связи отчёта; только это создаёт новый workRound соответствующего пункта. Автор отдельно сообщает результат наблюдения. Отчёт про лампу не распространяется на дверь.

При работе с targetItemIds из отчёта UI/Java сохраняют полный разрешённый список: подсказка вне допустимой области не даёт права создать link. Проверки акторов/назначений принадлежат Java, не модели.

## Проверка и ошибки

`SuggestionValidator` проверяет полноту, уникальность, принадлежность IDs, echo версий, режим отказа и точную цитату. AnalysisWorker сохраняет ответ с контекстом, а CaseService.getSuggestions сверяет sourceRevision/contentVersion/workRound с актуальной БД при каждом чтении: устаревший результат отдаётся как STALE без содержимого. Проверка текущей видимости обращения выполняется до ответа. Положительная валидация JSON не означает подтверждение физического ремонта.

422 фактически возвращает `{detail:"INVALID_COMPARE_REQUEST"}`; OpenAPI исправлен на эту форму и проверяется по реальному ответу. 413 REQUEST_TOO_LARGE ограничивает вход 512 KiB. При timeout/непригодном ответе Java сохраняет ручной путь и все входные пункты. Сохранение самого отчёта не зависит от успешного анализа. При ANALYSIS_ENABLED=true создаётся durable job в той же транзакции; иначе новый отчёт получает MANUAL_REQUIRED. Worker делает максимум 3 попытки, backoff 15/60 секунд; STUB/MANUAL не становится READY. В release 27.09 включён RULES; frontend показывает реальные статусы job и сохраняет ручную форму.
